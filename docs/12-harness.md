## 1. 이 하네스가 무엇을 막으려 하는가

이 레포의 사고는 **거의 다 예외 없이** 일어났다.

| 사고 | 겉으로 보인 것 | 실제 |
|---|---|---|
| WEBP 전송 | HTTP 200, 정상 JSON | 모델이 이미지를 못 봤고 답은 환각이었다 |
| system turn 오염 | 아무 일 없음 | 프리픽스 캐시 사망. 그냥 느려졌다 |
| 덜 그려진 프레임 | 로그 깨끗 | 탐색이 다른 길로 샜다 |
| 경도 격자 미끄러짐 | 정상 동작 | 재방문 감지가 영영 안 걸렸다 |
| Metal OOM 좀비 | `/health` 200 | 서버는 죽어 있었다 |

그래서 **"예외가 안 났다" 는 아무것도 보장하지 않는다.** 테스트는 전부
불변식으로 걸려 있고, 각 파일 맨 위에 어느 사고에서 나왔는지 적혀 있다.

## 4. 커밋·PR 전 게이트 훅

`.claude/hooks/review-on-commit.py` · PreToolUse(Bash) · 타임아웃 540초.

```
git commit
   │
   ├─ git commit 이 아니면            → 즉시 통과 (거의 모든 Bash 호출)
   ├─ --no-verify 가 있으면           → 통과
   ├─ 리뷰 에이전트 안에서 온 것이면   → 통과 (재귀 차단)
   │
   ├─ 1단계  ruff + pytest           → 실패하면 **차단**
   │
   └─ 2단계  claude -p 리뷰 에이전트  → 스테이지된 diff 만, 읽기 전용
                ├─ blocking          → **차단**
                └─ advisory          → 통과시키되 본문에 붙여 보여준다
```

### 왜 두 단계인가

1단계는 **사실**이다. 깨진 테스트를 커밋할 이유가 없으니 무조건 막는다.
2단계는 **판단**이다. 판단으로 사람을 막을 때는 조심해야 한다.

### 과잉 차단은 훅을 죽인다

이 레포는 이 교훈을 이미 한 번 치렀다. `block-secret-reads.py` 의 첫 판은
`.env` 를 **언급**만 해도 막아서 커밋 메시지조차 못 쓰게 만들었다.
그런 훅은 곧 꺼지고, **꺼진 훅은 아무것도 막지 못한다.**

그래서 리뷰 단계는 이렇게 설계했다:

- **리뷰어가 고장나면 통과시킨다.** `claude` 가 없거나, 타임아웃이거나, JSON 이
  깨졌으면 커밋을 막지 않고 "리뷰가 안 돌았다" 는 사실만 알린다.
  리뷰 인프라 장애로 커밋이 막히면 사람이 훅부터 지운다
- **차단은 `blocking` 에만.** 스타일·취향은 절대 차단하지 않는다 (ruff 가 이미 돌았다)
- **`--no-verify` 는 언제나 존중한다.** 탈출구 없는 게이트는 게이트가 아니다
- diff 가 40KB 를 넘으면 에이전트 리뷰를 건너뛴다 (아래 속도 항목)

### 리뷰어에게 무엇을 시키는가

프롬프트에 이 프로젝트의 **위험 성격**을 먼저 알려준다. 일반적인 코드 리뷰가
아니라 조용한 실패를 찾게 한다:

1. 조용한 실패 — 예외 없이 틀린 결과가 나오는 경로
2. 비밀값 누출 — 키가 로그·예외·URL 에 들어가는가
3. 재현성 파괴
4. 명백한 버그
5. 문서와 코드의 어긋남

`--permission-mode plan` + `--allowedTools Read Grep Glob` 으로 **쓰기를 막는다.**
리뷰어가 코드를 고치기 시작하면 그건 리뷰가 아니다.

### 실제로 잡는가 — 두 번 검증했다

**(1) 심은 결함.** 네트워크 오류를 `False` 로 뭉개는 코드를 스테이징했다:

```python
except Exception:
    out.append(False)        # 실패와 "산책로 아님" 이 구분되지 않는다
```

> `[blocking]` bare except 가 네트워크 오류·HTTP 오류·JSON 파싱 실패·KeyError 를
> 모두 False 하나로 뭉갠다 → 서버가 500 을 반환해도 예외가 삼켜지고 호출자가
> 실패와 정상 부정 판정을 구분할 수 없다

**(2) 훅이 자기 자신을 리뷰했다.** 이쪽이 훨씬 유익했다. 이 훅의 첫 판을
리뷰시켰더니 **blocking 3건 + advisory 2건**이 나왔고 전부 진짜였다:

| 지적 | 실제 결과 |
|---|---|
| `"--no-verify" in cmd` 가 커밋 **메시지 본문**의 언급에 걸린다 | 이 훅을 설명하는 첫 커밋이 정확히 그래서 **리뷰 없이 통과**했다 |
| `GIT_COMMIT` 정규식이 `git -C <path> commit` 을 놓친다 | 훅이 아예 발동하지 않는다 |
| `-a` 감지 정규식이 `--all` 을 못 잡는다 | diff 가 비어 "커밋할 게 없다" 로 오인 → 조용히 통과 |
| `python -m ruff` 는 ruff 가 없어도 OSError 를 안 던진다 | "도구 없으면 통과" 라는 문서와 **정반대로** 커밋이 막힌다 |
| findings 추출 정규식이 greedy DOTALL | JSON 뒤에 중괄호가 있으면 파싱 실패 → **blocking 지적이 버려진다** |

고친 뒤 다시 돌렸더니 **수정본에서 두 건을 더 잡았다:**

- `-uno`(= `--untracked-files=no`)의 묶음 플래그에 `n` 이 들어 있어
  멀쩡한 커밋이 `--no-verify` 로 오판된다
- "그 줄만 본다" 로 바꾸면서 **역슬래시로 이어진 줄의 플래그를 놓치는
  회귀**가 새로 생겼다
- 뒤에 다른 명령이 붙으면(`... || git commit --no-verify ...` 같은 재시도
  패턴) **뒤 명령의 플래그가 앞 명령 판정에 섞인다**
- `git` 과 `commit` **사이**에 역슬래시 줄바꿈이 끼면 정규식이 매칭에 실패한다
- 공백 없이 붙은 구분자(`-m x||git ...`)는 shlex 가 `x||git` 한 토큰으로
  합쳐버려 절단이 안 된다
- 역슬래시 **뒤에 공백**이 있으면 bash 는 줄을 안 잇는데 `rstrip()` 때문에
  이어진 것으로 봤다 — 전달되지도 않은 플래그를 읽는다

뒤의 다섯은 훅이 자기 커밋을 실제로 막으면서 잡았다 — 설계대로 동작한 사례다.

열하나 중 열이 **"조용히 통과"** 유형이다. 훅이 틀리는 두 방향의 위험도가
다르다는 것이 여기서 그대로 드러난다:

```
과잉 차단 → 즉시 눈에 띈다. 사람이 짜증내고, 결국 훅을 꺼버린다
과잉 통과 → 아무 일도 안 일어난다. 검사가 안 돈다는 걸 아무도 모른다
```

그래서 훅 자신에게도 회귀 테스트를 붙였다 (`app/tests/test_review_hook.py`).
열한 지적이 전부 테스트로 굳어 있다.

> **셸 명령을 완벽히 파싱하는 것은 목표가 아니다.** 지적 열한 건 중 일곱이
> 셸 문법 예외였고, 더 파면 더 나올 것이다. 중요한 건 **애매하면 리뷰를 돌리는
> 쪽으로 틀리는 것**이다 — `skips_verify` 가 통제하는 것은 "건너뛸까" 하나뿐이고,
> 파싱이 불확실할 때의 정답은 항상 "건너뛰지 않는다" 이다.
>
> 리뷰를 여섯 바퀴 돌리며 배운 것: **에이전트는 계속 무언가를 찾아낸다.**
> 열한 건은 전부 진짜였지만 뒤로 갈수록 발생 가능성이 낮은 셸 문법 예외로
> 옮겨갔고, **열두 번째는 틀렸다** — `-Sa` 의 `a` 를 `--all` 로 봐야 한다고
> 했는데 git 에서 `-S[<keyid>]` 는 값이 붙는 형태라 그 `a` 는 키 이름이다.
> 시키는 대로 고쳤으면 없던 버그가 생겼을 것이다.
>
> 그래서 **`--no-verify` 로 넘기고 대신 올바른 의미를 테스트로 박아뒀다.**
> 리뷰어의 지적은 입력이지 명령이 아니다. 탈출구가 있어야 하는 이유가 이것이고,
> 이 훅이 blocking 을 좁게 잡는 이유이기도 하다.

### 속도 — 커밋당 4~8분

실측: **10KB diff → 230~290초.** 도구(Read/Grep)를 전부 빼도 230초라
병목은 탐색이 아니라 생성이다. 이 CLI 판에는 `--max-turns` 가 없어서
턴으로 묶을 수단도 없다.

그래서 `MAX_DIFF_BYTES = 40_000` 이다. 95KB 를 넣었더니 240초를 통째로
태우고 결국 아무 결과도 못 냈다 — **못 할 일이면 빨리 포기하는 편이 낫다.**
넘으면 리뷰를 건너뛰고 그 사실을 알린다.

> 솔직히 말해 커밋마다 5분은 길다. 1단계(ruff+pytest, 3초)가 실질적인
> 안전망이고 2단계는 그 위의 보너스로 보는 편이 맞다. 급하면 `--no-verify`
> 로 넘기고 나중에 몰아서 리뷰하는 것도 정당한 사용법이다.

### PR 본문 검증 — 처음 보는 사람이 알 수 있는가

`.claude/hooks/review-on-pr.py` · PreToolUse(Bash) · `gh pr create` 를 가로챈다.

커밋 훅이 **코드의 조용한 실패**를 잡는다면 이 훅은 **설명의 조용한 실패**를
잡는다. 둘 다 "에러 없이 틀린 것" 이라는 점이 같다. PR 본문은 대화 맥락이 없는
사람이 읽는데, 작성자에게 자명한 것이 읽는 사람에게는 허공을 가리키는 참조가
된다 — "다른 브랜치에 참조 구현이 있다"(어느 브랜치?), "§9"(어느 문서의?),
"이번에 지웠다"(무엇을?).

에이전트는 PR 제목·본문과 `base...HEAD` diff 만 받고 **이 저장소를 처음 보는
사람** 으로서 읽는다. `blocking` 은 확인 가능한 둘뿐이다:

1. **해석 불가능한 참조** — 가리키는 대상이 본문에도 diff 에도 저장소에도 없다
2. **본문과 diff 의 불일치** — 안 한 일을 했다고 하거나, 큰 변경을 안 적었다

"더 친절하게 써라"·문장 길이·용어 선택은 전부 advisory 다. 주관을 차단 사유로
삼으면 취향 싸움이 되고, 그런 훅은 곧 꺼진다 (위 "과잉 차단은 훅을 죽인다").

**실제로 잡는가 — 첫 PR 에서 검증했다 (2026-08-20).** PR #1 본문을 그대로
넣었더니 "다른 로컬 브랜치에 참조 구현이 있지만" 을 blocking 으로 잡았다.
브랜치 이름이 없어 찾아갈 수 없다는 지적이었고, 맞는 지적이었다.

**파싱이 이 훅의 급소다.** 본문을 못 꺼내면 검증이 조용히 안 돈다 — 이 훅에서
가장 나쁜 실패다. 여러 줄 본문의 흔한 형태인 `--body "$(cat <<'EOF' … EOF)"` 는
명령치환이라 `shlex` 가 풀지 못하므로, **실행하지 않고** 히어독 표식 사이만
꺼낸다. `--body-file` · `--fill`(커밋 메시지를 본문으로 쓴다) · `--web`(브라우저에서
쓰므로 건너뛴다)도 각각 다르게 다룬다. 이 부분만 `app/tests/test_review_on_pr.py`
가 잰다 — 커밋 훅과 같은 자리다(§2). 에이전트는 안 부른다: 느리고 비결정적이다.

**훅이 자기 커밋에서 오발동했다 (2026-08-20).** 커밋 메시지에 "`gh pr create`
를 가로챈다" 라고 적었더니, 그 글자가 명령 문자열에 그대로 들어오고 `shlex` 는
히어독을 모르므로 `gh`·`pr`·`create` 를 각각 토큰으로 쪼갰다 — 무관한 커밋마다
PR 검증이 돌았다. 그래서 **매칭은 히어독 본문을 지운 문자열로** 하고 본문
추출만 원본에서 한다. 훅을 설명하는 글이 훅을 깨우는 것은 이 레포에서 반복되는
함정이다 (`block-secret-reads.py` 1판이 커밋 메시지의 `.env` 언급을 막았다).

⚠️ **`review-on-commit.py` 에는 아직 같은 사각이 있다.** 히어독 안에
`git commit` 이 적힌 명령(이 문서를 쓰는 커밋이 그렇다)에서 리뷰가 헛돈다.
차단이 아니라 낭비라 급하지는 않지만, 한 번에 4~8분씩 태운다.

## 5. 알려진 한계

- **판정 품질에 대한 회귀 테스트가 없다.** 정답이 눈으로 확인한 7건뿐이다.
  코스 폴리라인(`app/docs/23-open-questions.md` §4)이 풀려야 생긴다
- **CI 가 없다.** 지금은 커밋 훅이 유일한 게이트라 `--no-verify` 로 그냥 지나간다
- **큰 커밋은 에이전트 리뷰를 못 받는다** (40KB 초과). 하필 큰 커밋일수록
  리뷰가 필요한데 시간이 안 맞는다. 나눠 커밋하는 수밖에 없다
- **리뷰·PR 검증 에이전트는 비결정적이다.** 같은 입력에 매번 같은 지적이 나오지 않는다.
  1단계(ruff/pytest)와 성격이 다르며, 그래서 차단 범위를 좁게 잡았다
- `equirect_to_view` 는 테스트는 있지만 **실제 파노라마로 검증된 적이 없다**
