# 비전 인코딩 제약 — 왜 직렬인가

이 프로젝트를 규정하는 **중심 제약**. `00-design.md` §4에서 참조.

"비전 인코딩은 직렬이다"라는 한 문장에 **성격이 전혀 다른 세 가지**가 섞여 있다.
하나는 수학적으로 불가피하고, 하나는 단순한 구현 미비이며, 셋째는 앞 둘의 귀결이다.
대응 방법이 각각 다르므로 분리해서 본다.

---

## (A) 이미지 1장을 쪼갤 수 없다 — 수학적, 우회 불가

### causal LM에서 청크 prefill이 되는 이유

causal attention은 **prefix-decomposable**하다. 토큰 i는 ≤ i만 본다.

```
청크 1 [0..511]   계산 → K,V 저장
청크 2 [512..1023] 계산 → 청크 1의 K,V가 필요하고, 그건 이미 갖고 있음
```

핵심은 **청크 1이 청크 2를 필요로 하지 않는다**는 것. 그래서 부분 계산 결과가
그 자체로 유효한 상태(= KV cache)가 되고, 나중에 이어붙일 수 있다.

### 비전 인코더는 그렇지 않다

SigLIP / ViT 계열은 **bidirectional (non-causal) attention**을 쓴다.
Gemma 4는 여기에 axial 2D-RoPE + non-causal attention을 명시한다.

```
causal LM              vision encoder
  ■ · · ·                ■ ■ ■ ■
  ■ ■ · ·                ■ ■ ■ ■
  ■ ■ ■ ·                ■ ■ ■ ■
  ■ ■ ■ ■                ■ ■ ■ ■
  lower-triangular       full
```

패치 5가 패치 500을 보고, 패치 500도 패치 5를 본다.
앞의 100개 패치만 먼저 계산하려 해도 **아직 계산되지 않은 뒤쪽 패치가 필요하다.**

> **유효한 부분 상태가 존재하지 않는다.** 저장할 것도, 이어붙일 것도 없다.

### 세 가지 귀결

1. **이미지 토큰 전체가 단일 forward pass = 단일 ubatch에 들어가야 한다.**
   → `-ub` ≥ 이미지 토큰 예산. 구현 제약이 아니라 정의상 그렇다.
   (토큰 예산 1120이면 `-ub 2048`. 기본 512로는 실패)

2. **비전 인코더에는 KV cache라는 개념 자체가 없다.**
   재사용할 증분 상태가 없으므로 매 요청마다 처음부터 전부 계산한다.

3. **프리픽스 캐시가 이미지에 대해 원리적으로 아무것도 못 해준다.**
   캐시 구현이 부실해서가 아니라, **캐시할 대상이 존재하지 않아서**다.
   → `00-design.md` §6에서 프리픽스 캐시를 보조 수단으로 강등한 근거.

### 대응

**받아들인다.** 우회로 없음. `-ub`를 토큰 예산에 맞춰 설정한다.

---

## (B) 이미지 N장을 함께 못 돌린다 — 구현 미비, 우회 가능

### 수학적 장벽은 없다

이미지끼리는 완전히 독립이다. batch 차원을 늘려 `[N, n_patches, d]`로 돌리면 되고,
block-diagonal이라 섞일 위험도 없다. (A)와 달리 **원리적 문제가 아니다.**

### llama.cpp가 안 할 뿐

```c
// TODO @ngxson : implement batch size > 1 as a loop
// we don't need true batching support because the cgraph will gonna be big anyway
→ batch_size > 1 이면 false 반환
```

issue #14530 (closed). 보고된 실측(Qwen2.5-VL): 이미지당 인코딩 470~600ms,
디코딩 3~4ms. 완전 직렬.

### 메인테이너 논리와, 그것이 이 프로젝트에서 깨질 가능성

논리: *"이미지 1장의 인코더 그래프만으로도 GPU가 이미 포화되니,
배치해봐야 그래프만 커지고 총 시간은 같다."*

이 판단은 **Qwen2.5-VL급(400M~1B 인코더, 1000+ 토큰)**을 염두에 둔 것이다.

이 프로젝트는 **150M 인코더 + 140~280 토큰**이다.
그 크기의 matmul은 10코어 M4 GPU에서도 compute-bound가 아니라
**커널 런치 오버헤드 / 메모리 대역폭 bound**일 가능성이 있다.
그 영역에서는 배치가 거의 선형으로 효과를 낸다.

> **즉 이 하드웨어 + 모델 조합에서는 (B)가 실제 처리량 손실일 수 있다.**

### 판별 방법

```
토큰 예산을 2배로 올렸을 때 (140 → 280, 280 → 560) 인코딩 시간이 2배가 되는가?

  선형 증가       → compute-bound  → 배치해도 이득 없음. 메인테이너 논리 성립
  덜 증가(sublinear) → 오버헤드-bound → 배치 여지 있음. (B)가 실제 손실
```

GPU 점유율도 함께 본다 (Instruments / `powermetrics`).

### 실측 결과 (2026-08-17) — 가설 확인됨, 그러나 카드가 없음

`04-b1-results.md` §2a:

| 구간 | 토큰 배수 | prefill 배수 |
|---|---|---|
| 70→140 | 2.0x | **1.55x** (sublinear) |
| 140→280 | 2.0x | **1.54x** (sublinear) |
| 280→560 | 2.0x | 2.08x (선형) |
| 560→1120 | 2.0x | 2.26x (superlinear, non-causal O(n²)) |

**고정 오버헤드 ~250–300ms + 약 5.7 ms/token.**
예산 70에서는 prefill 702ms 중 ~36%가 고정비다.
→ **가설대로 저예산 구간은 오버헤드-bound이고, 배칭이 가능하다면 이득이 크다.**

### 그런데 대응 카드가 죽었다

비전 인코더를 별도 서비스로 분리해 배치 인코딩하고 임베딩만 주입하는 방향은
[PR #20228](https://github.com/ggml-org/llama.cpp/pull/20228)이 정확히 그것을 제안했다
(`/vision/embedding` 엔드포인트 + `image_embedding` 필드).
**2026-04-25 저자가 브랜치를 삭제하며 미병합 종료.**

현재 llama-server의 비전 인코더를 우회할 방법은 **없다.**
되살리려면 그 PR을 직접 리베이스해야 한다.

> **(B)는 실재하는 손실이지만 지금은 쓸 수 있는 대응이 없다.**
> "알지만 못 쓰는 손실"로 기록하고, 최적화 예산은 §3(출력 스키마)과 토큰 예산에 쓴다.

## (C) 이미지 인코딩 = 원자적 GPU 점유 블록 — (A)+preemption 부재의 귀결

(A) 때문에 이미지 인코딩은 **쪼갤 수 없다**.
llama.cpp에는 **preemption이 없다** → **중단할 수도 없다**.

```
긴 텍스트 prefill  : 청크로 쪼개 decode와 섞을 수 있음 (완화책 존재)
이미지 인코딩       : 쪼갤 수 없음 (완화책 원리적으로 부재)
```

기존 `doc/llama_cpp_vs_vllm_batching.md`의 HoL blocking 분석이 그대로 적용되되,
**차단 단위가 "긴 프롬프트"가 아니라 "이미지 1장"**이고,
chunked prefill이라는 완화책이 **여기엔 존재하지 않는다.**

`-np 4`로 슬롯을 늘려도 슬롯 0이 이미지를 인코딩하는 동안
나머지 슬롯의 decode는 대기한다.

### 실측 결과 (2026-08-17) — 예측 적중

| `-np` | img/s | 처리량 | p50 지연 |
|---:|---:|---:|---:|
| 1 | 0.422 | — | 2.38 s |
| 2 | 0.442 | +4.7% | 4.41 s |
| 4 | 0.508 | **+20.4%** | **7.89 s (3.32x)** |

4배 동시성에 처리량 +20%, 지연 3.3배. 예측대로 거의 오르지 않는다.
+20%는 decode가 다음 요청의 비전 인코딩과 겹쳐지며 나온 것으로 보인다.

**결론: `-np 1`을 기본값으로 한다.** 20%는 출력 스키마 조정으로 얻는 이득(최대 3.6x)에
비하면 잡음이고, 지연 예측성만 잃는다.

## 종합 — 실측된 처리량 모델

```
total ≈ (250~300ms 고정) + (5.7ms × 이미지토큰) + (37ms × 출력토큰)
        └─── 비전 인코딩 + prefill ───┘   └──── decode ────┘
```

측정으로 확정된 것:

| 항 | 손잡이 | 실측 |
|---|---|---|
| 고정 오버헤드 | **없음** — (B)로 분할상환 불가, 카드도 없음 | ~250–300 ms |
| 이미지 토큰 | **토큰 예산** (70~1120) | 5.7 ms/token |
| 출력 토큰 | **출력 스키마** | 37 ms/token |

**이 문서의 원래 결론("t_vision이 지배적, 유일한 손잡이는 토큰 예산")은 부분적으로 틀렸다.**

decode는 예산과 무관하게 ~1700ms로 평평했고, 낮은 예산에서는 **decode가 전체의 71%**를
차지했다. 즉 목표 운영점(저예산)에서는 **출력 스키마가 토큰 예산보다 큰 레버다.**

엔진 튜닝(`-np`, `-b`)으로 얻을 것이 거의 없다는 결론은 **유지된다** (§C 실측: +20%).
