## 1. 비전 인코딩이 처리량 천장인가 (최우선)

`03-vision-encoding-constraint.md`의 결론이 실제로 맞는지 확인한다.
남은 질문은 **비전 인코딩이 전체 시간의 몇 %인가**다.

### 1a. 구간 분해

```
동일 이미지, 동일 프롬프트, 단일 요청에서:
  t_vision   비전 인코딩
  t_prefill  텍스트 + 이미지 토큰 prefill
  t_decode   출력 생성

토큰 예산 70 / 140 / 280 / 560 / 1120 각각에 대해
```

판단:
- `t_vision` 지배적 → **엔진 튜닝(`-np`, `-b`)은 헛수고.** 토큰 예산만 남는다
- `t_prefill` 지배적 → 배치 파라미터 튜닝에 의미 있음
- `t_decode`가 유의미 → 출력 스키마가 김. grammar로 조인다

### 1b. compute-bound인가 오버헤드-bound인가 (제약 (B) 판별)

1a 데이터에서 바로 읽어낼 수 있다.

```
토큰 예산 2배 → t_vision 이 2배가 되는가?

  선형        → compute-bound   → 배치해도 이득 없음. (B)는 무시해도 됨
  sublinear   → 오버헤드-bound  → (B)가 실제 손실. 별도 인코더 서비스 카드 검토
```

150M 인코더 + 140~280 토큰은 10코어 GPU를 포화시키지 못할 수 있다는 가설.
GPU 점유율도 함께 본다 (Instruments / `powermetrics`).

### 1c. 동시성 스케일링 (제약 (C) 확인)

```
-np 1 / 2 / 4 / 8 각각에서
N개 동시 요청의 aggregate images/sec 와 p50/p99 지연
```

**예상: aggregate throughput이 `-np`에 거의 무반응.**
반응이 있다면 decode/prefill이 비전 인코딩과 겹쳐지고 있다는 뜻 → 튜닝 여지 있음.
`-np`를 올릴 때 `-c`도 같이 올려야 한다 (`n_ctx_per_slot = n_ctx / n_parallel`).

### 1d. `-ub` 하한 확인 (제약 (A))

토큰 예산별로 `-ub`를 낮춰가며 어디서 실패하는지. (A)가 실제로 그렇게 동작하는지 검증.

## 2. 토큰 예산 — 정확도 vs 처리량 (최우선)

**이 워크로드에서 가장 큰 단일 레버.** 70 → 1120은 16배 차이다.

### 필요한 것: 평가 세트

로드뷰 이미지 **50~100장** + 라벨.
라벨 필드의 의미론은 애플리케이션 소유지만, **측정을 위해 최소 하나의 판정 필드가 필요**하다.

**이게 없으면 토큰 예산도, 양자화 수준도, 프롬프트도 결정할 수 없다.**
벤치 코드보다 이 데이터셋이 먼저다. → §2b 참조

### 측정

| 예산 | 판정 정확도 | images/sec | t_vision |
|---|---|---|---|
| 70 | | | |
| 140 | | | |
| 280 (기본) | | | |
| 560 | | | |
| 1120 | | | |

가설: 로드뷰는 사진이지 문서가 아니므로 **140~280에서 포화**될 것.
반증되면(예: 표지판 글씨를 읽어야 판단이 됨) 예산을 올리고 `-ub`도 함께 올려야 한다.

## 2b. 평가 세트 구축 (실질적 크리티컬 패스)

### 좌표 소스

[gil.seoul.go.kr 서울 테마산책길](https://gil.seoul.go.kr/trail/list.do?key=2406040004)은
150개 코스에 **이름 / 난이도 / 테마(숲·역사문화·조망·하천·계곡) / 거리 / 소요시간 /
자치구 / PDF / 지도 링크**를 제공한다.

**단, GPX·좌표는 없다.** PDF와 서울 GIS 지도 링크뿐이라 로드뷰 샘플링에 바로 못 쓴다.
좌표 보완이 필요하다:

- [한국관광공사 두루누비 정보서비스](https://www.data.go.kr/data/15101974/openapi.do) — 284개 코스 GPX Open API
- [전국 길관광정보 표준데이터](https://www.data.go.kr/data/15017321/standard.do) — 둘레길/골목길/숲길, 경로정보 포함
- [서울 열린데이터광장](https://data.seoul.go.kr/) — 두드림길 검색

### 선행 확인: 로드뷰 커버리지 (블로커일 수 있음)

**로드뷰는 차량 촬영이다. 숲길·계곡길에는 커버리지가 없을 가능성이 크다.**

gil.seoul.go.kr 테마 중 숲·계곡이 상당수인데 이게 비어 있으면:
- 평가 세트가 "차도 옆 산책로"로 편향된다
- **애플리케이션 자체의 적용 범위가 좁아진다**

→ 좌표 수집을 본격화하기 전에 각 테마별로 샘플 몇 개씩 로드뷰 존재 여부부터 확인한다.
결과에 따라 대상 테마를 명시적으로 제한하거나, 항공뷰/보행자뷰 등 다른 이미지 소스를 검토한다.

### 하드 네거티브가 진짜 어려운 부분

공식 산책로 좌표에서만 positive를 뽑으면 평가가 낙관적으로 나오고 현장에서 무너진다.
**걸을 수는 있지만 산책로는 아닌** 장면이 필요하다:

- 차도 옆 인도
- 주택가 골목
- 주차장 / 아파트 단지 내부 통로
- 공원 경계 밖
- 산책로 입구 바로 직전 지점 (경계 케이스)

positive : hard negative 비율을 최소 1:1로 잡는다.

## 3. 프리픽스 캐시 — 실효 이득

### 측정

```
동일 system turn + 서로 다른 이미지로 연속 요청 N회.
서버 로그의 캐시 히트 토큰 수 확인.

비교군:
  (a) 기본
  (b) --cache-reuse + --cache-ram 확대
  (c) (b) + --swa-full
```

### 확인할 것

1. 히트 토큰 수가 system turn 길이와 일치하는가
2. **wall-clock이 실제로 줄어드는가** — 토큰이 캐시돼도 비전 인코딩은 100% 재실행되므로
   절감폭이 토큰 비율보다 훨씬 작을 것으로 예상
3. `--swa-full`의 KV 메모리 증가량 (윈도우 512, 5:1 비율)
4. 서버가 `--swa-full` 필요 경고를 띄우는가
5. `--cache-ram` 한도 초과로 인한 메모리 압박 (issue #22629)
   — 이미지 1장당 1000+ KV 토큰, 직렬화 시 ~128MiB 보고됨.
   **캐시가 무한히 자라지 않도록 상한을 명시적으로 걸어야 한다.**

### 결정 규칙

- (a)에서 이미 히트가 나면 → 그대로 쓰고 끝. 추가 작업 없음.
- (c)가 필요한데 메모리가 빠듯하면 → **프리픽스 캐시를 포기**한다.
  주력이 아니므로 메모리를 비전/compute buffer에 쓰는 게 낫다.

## 4. 프롬프트 레이아웃 검증

3존 레이아웃(§5)이 실제로 둘 다 만족하는지.

  (평가 세트로 A/B. Google 권장이 실제로 이 태스크에서도 맞는지)

  "직전 요청과 system turn 바이트가 동일한가" 어서션을 넣는다. 조용히 깨지기 쉬운 부분.

## 7. 미결정 설계 항목 (레포 범위 내)

- **API 계약**: 요청/응답 형태, 에러 코드, 타임아웃, 동시성 상한.
  이미지 1장 / 1턴 / stateless로 고정되었으므로 단순함.
- **스키마 주입 방식**: 출력 필드 정의는 애플리케이션 소유. 이 레포는 강제 메커니즘만
  제공한다 → 설정 파일로 받을지, 요청 파라미터로 받을지, GBNF를 직접 받을지.
- **관측**: 구간별 타이밍(`t_vision`/`t_prefill`/`t_decode`), 캐시 히트율, 슬롯 점유율.
  §1의 측정을 **프로덕션에서도 상시** 볼 수 있어야 한다. 벤치 전용 코드로 만들지 않는다.
- **프롬프트 불변성 어서션**: system turn이 직전 요청과 바이트 동일한지 런타임 검사.
  조용히 깨지는 종류의 버그이므로 자동 검출이 필요하다.
- **실패 모드**: 스키마 밖 출력, `<unused49>` 같은 버그 토큰(#24146),
  이미지 디코드 실패, 큐 포화 시 거절 정책.
- **큐잉 / admission control**: 처리량 우선이므로 큐를 깊게 가져가되,
  무한 대기를 막는 상한이 필요.
- **다중 클라이언트 잡 큐 + 진행 스트리밍** (애플리케이션 쪽에서 넘어온 요구사항,
  2026-08-17): 웹 UI 가 붙으면 탐색 1건이 수 분짜리 잡이 되는데, 서버가 `-np 1`
  이라 전체 시스템의 동시 탐색은 1개다. 그래서 (a) 여러 클라이언트를 직렬화하는
  잡 큐(대기 순번 노출 포함), (b) 진행 상황을 밀어주는 스트리밍(잡 모델 + SSE 등)
  이 서빙/게이트웨이 쪽에 필요하다. **스택은 미정** — 게이트웨이 설계와 같이 정한다.
  요청 단위 API(이미지 1장 → 판정 1건)는 그대로 두고 그 위에 얹는다.

### 레포 범위 밖 (클라이언트)

`00-design.md` §1에 기록. 탐색 루프, 방향 결정, 스텝 진행, 지도 API 연동,

**이제 크리티컬 패스는 평가 세트 하나뿐이다.**

성능 축은 전부 측정됐고, 결론은 "예산 70 + tiny 스키마가 순진한 기본값 대비 3.6배"다.
그 조합을 채택할 수 있는지는 **오직 정확도가 결정**하며, 그건 라벨 없이는 알 수 없다.
§2b(커버리지 확인 → 좌표 수집 → 라벨링)가 다음 작업이다.
