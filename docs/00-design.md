## 1. 범위와 경계

### 이 레포가 하는 일

**로드뷰 이미지 1장을 받아 구조화된 시각 판정 1건을 돌려주는 stateless 서비스.**

```
POST  이미지 1장 + 소량의 동적 텍스트  →  JSON 판정 1건
```

상태 없음. 히스토리 없음. 세션 없음. 요청 간 의존 없음.

### 이 레포가 하지 않는 일 (클라이언트 책임)

- 어디로 갈지 결정 (방향 선택, 탐색 전략)
- 어떻게 이어갈지 (스텝 진행, 종료 조건, 막다른 길, 방문 중복 방지)
- 지도 API 연동, 로드뷰 수집, 위치 이동 버튼 조작
- 이미지 리사이즈 / 포맷 정규화
- **판정 결과의 의미론 (출력 스키마의 필드 정의)** — 애플리케이션이 소유.
  이 레포는 스키마를 **강제하는 메커니즘**(GBNF/json_schema)만 제공한다.

> 상위 애플리케이션은 "산책로 탐색"이지만, 그 탐색 루프는 클라이언트 단계에 속한다.
> 여기서는 **한 장면에 대한 판정**만 최대한 빠르게, 많이 처리하는 문제로 좁힌다.

### 워크로드 특성

| 항목 | 값 |
|---|---|
| 요청당 이미지 | **1장** |
| 턴 수 | **1턴** (대화 히스토리 없음) |
| 입력 | 로드뷰 이미지 1장 + 고정 프롬프트 + 소량의 동적 텍스트 |
| 출력 | 구조화 JSON, 짧음 |
| 우선 지표 | **처리량 (throughput)**. 지연 시간은 부차적 |
| 이미지 재사용 | 없음 (매번 다른 로드뷰) → 이미지 해시 캐시 불필요 |
| 배치의 실체 | **동시 요청** (여러 세션 / 좌표 큐). 요청 내부 배치는 없음 |

> 요청당 이미지가 1장으로 고정되므로, llama.cpp의 "이미지 간 배치 미지원"(§4-B)은
> **요청 내부**에서는 무의미하다. 여전히 **요청 간**에는 걸린다 — 동시 요청 N개는
> 여전히 이미지를 하나씩 순차 인코딩한다.

## 2. 하드웨어

Mac mini M4 / 10코어 CPU (4P+6E) / **10코어 GPU** / **16GB 통합 메모리** / macOS (Darwin 25.5)

- Metal wired limit 기본 약 10.6GB (`iogpu.wired_limit_mb`로 상향 가능하나 OS와 경합)
- **vLLM은 선택지가 아님** — macOS/Metal GPU 백엔드 없음
- 10코어 GPU는 소형. 이미지 1장 prefill로도 상당 부분 포화된다고 가정하고 설계

## 3. 모델

**`gemma-4-E4B-it`** (GGUF + mmproj)

| 항목 | 값 | 설계 함의 |
|---|---|---|
| 유효 파라미터 | 4.5B | |
| **총 파라미터** | **8B** (Per-Layer Embeddings 테이블 포함) | **GGUF 크기를 4B 기준으로 잡으면 안 됨** |
| 비전 인코더 | ~150M | 작음. 인코딩 자체는 비교적 저렴할 가능성 |
| 컨텍스트 | 128K | 이 워크로드에선 8K 이하로 충분 |
| Attention | 로컬 SWA **5:1** 글로벌, **윈도우 512** | Gemma 3(윈도우 1024)보다 작음 |
| 오디오 | 30초 지원 | **이 프로젝트에선 미사용** |

### Visual token budget (핵심 다이얼)

Gemma 4는 Gemma 3의 pan & scan을 폐기하고 **설정 가능한 토큰 예산**으로 대체했다.
종횡비를 유지한 채 bicubic 리사이즈로 목표 토큰 수에 맞춘다.

선택지: **70 / 140 / 280 / 560 / 1120** (기본 280)

- 70~280: 분류, 캡셔닝, 비디오 이해
- 560~1120: OCR, 문서 파싱, 작은 글씨

llama.cpp 제어: `--image-min-tokens` / `--image-max-tokens`

> **이 워크로드는 로드뷰 사진**이다. 지도 타일처럼 작은 글씨를 읽는 게 아니라 "보행로처럼 보이는가 / 어느 쪽으로 길이 이어지는가"를 판단한다. **낮은 예산(140~280)으로 충분할 가능성이 높다.** 이게 처리량에 가장 크게 작용하는 단일 변수이므로 반드시 실측으로 결정한다.

## 4. 서빙 스택 결정

**llama.cpp (`llama-server`) + Metal.** 그 제약을 받아들이고 그 위에서 설계한다.

`doc/llama_cpp_vs_vllm_batching.md`에 정리된 vLLM의 장점(PagedAttention, preemption, chunked prefill)은 **비교 대상이 아니라 사용 불가 항목**이다. 설계는 llama.cpp의 슬롯 기반 스케줄러를 전제로 한다.

### 받아들이는 제약

상세 분석은 **`03-vision-encoding-constraint.md`** 참조. 요약:

| | 성격 | 대응 |
|---|---|---|
| **(A)** 이미지 1장은 쪼갤 수 없다 | **수학적, 우회 불가**. 비전 인코더는 non-causal attention이라 부분 상태가 존재하지 않는다 | `-ub` ≥ 토큰 예산. 받아들인다 |
| **(B)** 이미지 N장을 함께 못 돌린다 | **구현 미비**. 수학적 장벽 없음 | 요청당 1장이므로 요청 내부에선 무관. 요청 간 손실은 측정 후 판단 |
| **(C)** 이미지 인코딩 = 원자적 GPU 점유 블록 | (A) + preemption 부재 | `-np`로 처리량 안 오를 것 예상 |

추가로:

- **Preemption / KV swap 없음.** 시작한 작업은 끝까지 간다.
- **슬롯당 KV 사전 할당.** `n_ctx_per_slot = n_ctx / n_parallel`.
- **비전 인코더에는 KV cache 개념 자체가 없다.** (A)의 귀결.
  → **프리픽스 캐시는 이미지에 대해 원리적으로 아무것도 못 해준다.**

> **이 서비스의 처리량은 `1 / 이미지당 인코딩 시간`에 수렴할 가능성이 높고,
> 그것을 움직이는 유일한 손잡이가 토큰 예산이다.**

### 벤치마크 대상 대안

`vllm-mlx` (MLX 네이티브, OpenAI 호환, continuous batching, 멀티모달).
텍스트 기준 llama.cpp 대비 21~87% 높은 처리량 주장. 처리량 우선 워크로드이므로 측정 가치 있음.
**출처 간 수치가 엇갈리므로 직접 재기 전엔 채택하지 않는다.**

## 5. 프롬프트 레이아웃 (3존)

두 요구가 충돌한다:

- **품질**: Google 공식 권장은 image-before-text. causal decoder에서 이미지 뒤 텍스트만 이미지를 attend할 수 있다.
- **캐시**: 정적 텍스트가 앞에 와야 프리픽스 재사용이 된다.

**해결: 존 분리.**

```
[system turn]   페르소나 + 산책로 판정 기준 + 출력 JSON 스키마      ← 정적, 캐시 대상
[user turn]     <image>                                          ← 매번 바뀜
                동적 질문 / 현재 위치 컨텍스트                      ← 이미지 뒤 (품질)
```

system turn은 chat template상 user turn보다 앞에 오므로 프리픽스로 캐시되고,
user turn 내부에서는 image-before-text가 지켜진다. 둘 다 만족.

### 불변 규칙

- **system turn은 바이트 단위로 완전히 동일해야 한다.** 타임스탬프, 요청 ID, 좌표가 섞이면 캐시 히트율 0.
- 모든 가변값은 이미지 뒤 존으로.

## 6. KV / 프리픽스 캐시 정책

### 판단 기준은 이득이 아니라 비용

| 메커니즘 | 비용 | 정책 |
|---|---|---|
| 슬롯 prompt cache (기본 동작) | 0 | 무조건 사용 |
| `--cache-reuse`, `--cache-ram` | 플래그 + RAM | 기본 사용 |
| `--swa-full` | KV 메모리 증가 | 실측 후 결정 |
| `/slots` save/restore, prefix 라우팅 | 코드 + 운영 복잡도 | 이득 클 때만 |

공짜인 것은 이득이 작아도 켠다. 임계값 판단은 마지막 줄에만 적용된다.

### 이득 상한 계산 시 주의

```
절감 = 캐시된 시스템 프롬프트 토큰의 prefill 시간
비절감 = 비전 인코딩 시간 (이미지가 매번 바뀌므로 100% 재실행)
       + 이미지 토큰 prefill
       + 질문 토큰 prefill
```

**프리픽스 캐시는 비전 인코딩 시간을 전혀 아껴주지 않는다.**
따라서 실제 wall-clock 절감은 토큰 비율보다 항상 작다.
이 워크로드에서 프리픽스 캐시는 보조 수단이지 주력이 아니다.

### SWA 주의

Gemma 4 E4B는 로컬 SWA 5:1 글로벌, 윈도우 512.
llama.cpp는 기본적으로 SWA 레이어의 윈도우 밖 KV를 버려 메모리를 아끼는데,
**버려진 KV는 복원/재사용이 불가능**하다. 캐시 기법이 필요하면 `--swa-full`이 요구될 수 있고
서버가 경고 로그를 띄운다. 윈도우가 512로 작아 Gemma 3보다 영향이 클 수 있다.

## 7. 아키텍처

```
━━━ 레포 밖 (클라이언트) ━━━━━━━━━━━━━━━━━━━━━━━━━━
지도 API 연동 · 로드뷰 수집 · 탐색 루프 · 방향 결정
이미지 리사이즈 / 포맷 정규화
판정 스키마의 의미론 정의
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  │  이미지 1장 + 동적 텍스트
  ▼
━━━ 이 레포 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
게이트웨이 (FastAPI)
  │  · 프롬프트 템플릿 고정 (system turn 바이트 동일성 보장 + 어서션)
  │  · 큐잉 / admission control / 동시성 제어
  │  · 구조화 출력 강제 (GBNF / json_schema) — 스키마는 설정으로 주입
  │  · 구간별 타이밍 계측 (t_vision / t_prefill / t_decode)
  ▼
llama-server (Metal, gemma-4-E4B-it + mmproj)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 결정 사항

- **이미지 리사이즈/포맷팅은 클라이언트에서.** 서버 단 전처리 비용 제거.
- **이미지 해시 캐시 없음.** 같은 로드뷰가 반복되지 않는다는 가정.
- **llama-server를 직접 노출하지 않는다.** 게이트웨이가 프롬프트 불변성을 소유한다.
- **출력 스키마는 설정으로 주입받는다.** 필드 *의미론*은 애플리케이션 관심사이므로
  코드에 하드코딩하지 않는다.
- **단, 스키마의 토큰 비용은 서빙 관심사다.** (실측: `04-b1-results.md` §3)
  decode는 ~37 ms/token이고 출력 토큰 수에만 비례한다. 자유텍스트 필드 하나가 요청당 1.3초다.
  게이트웨이는 스키마를 그대로 받기만 할 게 아니라 **출력 토큰 수를 계측하고 예산을 강제**한다.
- **thinking 모드를 끈다** (`--reasoning off --reasoning-budget 0`).
  Gemma 4는 기본 켜짐이며, 켜두면 요청당 수백 토큰을 추론에 태워 처리량이 무너진다.
- **배치 엔드포인트 없음.** 요청당 이미지 1장. 처리량은 동시 요청으로 낸다.
- **`-np 1`이 기본값.** 실측상 `-np 4`는 처리량 +20%에 지연 3.3배다 (§4).
  동시성 대신 게이트웨이 큐로 직렬화한다.

## 8. 메모리 예산 (초안, 검증 필요)

| 항목 | 비고 |
|---|---|
| gemma-4-E4B-it 가중치 | **총 8B 기준**으로 계산할 것. 실제 GGUF 파일 크기 확인 필요 |
| mmproj (~150M 비전 타워) | 양자화하지 말 것 |
| KV cache | SWA 최적화 여부 / `--swa-full` 여부에 따라 크게 다름 |
| compute buffer | `-ub`에 비례. 이미지 예산 1120이면 `-ub 2048` → 무시 못 할 크기 |
| OS + 여유 | 통합 메모리이므로 경합 |

Metal wired limit ~10.6GB 안에 들어가야 한다.
**양자화는 Q8_0에서 시작**하고, 필요할 때만 내린다. 로드뷰 판정은 사진 이해라
지도 타일보다 양자화 손실에 덜 민감할 수 있으나, 이것도 실측 대상.

## 9. 레포 구조

```
vlm_serving/
  bench/          # 최우선. 측정 하네스
  gateway/        # FastAPI: 템플릿 · 큐 · grammar · 계측  (미구현)
  models/         # GGUF + mmproj (.gitignore + 다운로드 스크립트)
  configs/        # llama.pin(엔진 커밋) · env.sh(경로) · smoke.sh(실행 프로파일)
  scripts/        # build-llama.sh — 핀 커밋 clone + Metal 빌드
  vendor/
    llama.cpp/    # 고정 커밋 체크아웃 + 빌드. .gitignore (소스 206MB + 빌드 174MB)
  docs/
```

**llama.cpp는 커밋 해시를 고정**한다 — `configs/llama.pin`이 유일한 진실이고
`scripts/build-llama.sh`가 그 커밋으로만 빌드한다. 체크아웃이 핀과 다르면 빌드가 멈춘다.

패키지 매니저 바이너리(brew)를 쓰지 않는 이유는 **버전을 핀할 수 없기 때문**이다.
mtmd API는 자주 바뀌고, `04-b1-results.md`의 모든 수치는 한 커밋에서 나온 값이다.
엔진이 조용히 갈리면 그 문서 전체가 무효가 된다. → `11-server-ops.md` §1
