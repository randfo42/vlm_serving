## 1. Gemma 4 라인업

| 변형 | 파라미터 | 비전 인코더 | 비고 |
|---|---|---|---|
| E2B | 유효 2.3B / 총 5.1B | ~150M | 오디오 30초 |
| **E4B** | **유효 4.5B / 총 8B** | **~150M** | 오디오 30초. **본 프로젝트 대상** |
| 12B (unified) | 11.95B | 인코더 없음 (35M 임베더) | raw 48×48×3 RGB 패치 직접 투영 |
| 26B A4B | 25.2B 총 / 3.8B 활성 | ~550M | MoE |
| 31B | 30.7B | ~550M | Dense |

- "Gemma 4 4B"라는 변형은 없다. E4B가 그 자리.
- E2B/E4B는 **Per-Layer Embeddings (PLE)** 사용 — 각 디코더 레이어가 토큰별 소형 임베딩을 가짐.
  임베딩 테이블은 크지만 룩업만 함. → **유효 파라미터와 총 파라미터가 크게 다르다.**
- 컨텍스트 128K.
- Attention: 로컬 SWA + 글로벌 인터리브. **E2B는 4:1, 그 외는 5:1.** E2B/E4B 윈도우 **512**.
  글로벌 레이어는 pp-RoPE (p=0.25), 로컬은 일반 RoPE. 마지막 레이어들은 항상 글로벌.

## 2. 비전 처리 — pan & scan 폐기

**Gemma 3 (구):** pan & scan. 비정방형/고해상도 이미지를 여러 크롭으로 분할,
각 크롭을 896×896에서 256토큰으로 인코딩 + 글로벌 뷰. 최대 1280토큰.

**Gemma 4 (신):** 종횡비 보존 동적 리사이즈 + **고정 토큰 예산**.

리사이즈 알고리즘:
1. 목표 토큰 수와 이미지 크기로부터 이상적 스케일 팩터 계산
2. pooled patch size의 배수로 내림
3. bicubic 보간으로 리사이즈

**토큰 예산 선택지: 70 / 140 / 280 / 560 / 1120** (기본 280)

| 예산 | 권장 용도 |
|---|---|
| 70 ~ 280 | 분류, 캡셔닝, 비디오 이해 |
| 560 ~ 1120 | OCR, 문서 파싱, 손글씨, 작은 글씨 |

위치 인코딩: 2D 좌표 기반 임베딩 + axial 2D-RoPE, non-causal attention.

기술 보고서 벤치마크는 Table 6(1120토큰)과 Table 12(280토큰)로 나뉘어 있어
**예산별 정확도 차이를 직접 비교 가능**하다. E2B @280: InfographicVQA 44.6%,
OmniDocBench 1.5 0.496(낮을수록 좋음). 예산을 낮추면 측정 가능한 열화가 있으나
OCR 특화 비교는 정량화되어 있지 않음.

> **본 프로젝트 함의:** 로드뷰 사진 판정은 OCR이 아니다. 낮은 예산에서 출발한다.

## 3. llama.cpp 멀티모달 (mtmd) 현황

### 지원 상태
- Gemma 4는 **day-one 지원**. 텍스트 GGUF + **mmproj GGUF** 2개 파일 필요.
- `-hf`로 받으면 mmproj가 자동 다운로드됨. 수동 지정은 `--mmproj-url`, 비활성화는 `--no-mmproj`.
- CLI: `llama-mtmd-cli`, `[img]path/to/image.jpg[/img]` 문법.

### 이미지 토큰 예산 제어 (확인 필요 — 가장 중요한 플래그)
```
--image-min-tokens N
--image-max-tokens N
```
동일 값으로 고정하면 예산이 고정된다. 예: `--image-min-tokens 280 --image-max-tokens 280`

관련: `--mtmd-batch-max-tokens` (env `LLAMA_ARG_MTMD_BATCH_MAX_TOKENS`), 기본 1024.

### **비전 인코딩은 배치되지 않는다 (확정)**

- ggml-org/llama.cpp issue **#14530** ("enable real batch for multiple images input of VLM") — closed.
- 코드에 `TODO @ngxson: implement batch size > 1 as a loop`.
  `batch_size > 1`이면 `false` 반환 → 순차 처리 강제.
- 보고된 실측(Qwen2.5-VL): 이미지당 인코딩 470~600ms, 디코딩 3~4ms. 완전 직렬.

**근본 원인 (중요):** 비전 인코더는 **non-causal masking**을 쓴다.
따라서 한 이미지는 반드시 **단일 forward call 안에 통째로** 인코딩되어야 하고,
continuous batching과 원리적으로 양립하지 않는다.

**파생 제약:** 이미지 토큰 전체가 **하나의 ubatch에 들어가야 한다.**
→ `-ub` ≥ 이미지 토큰 예산. 예산 1120이면 `-ub 2048` 필요 (기본 512로는 실패).
(Qwen3.5 등 다른 모델과 다른 지점이다.)

**이론적 개선 여지:** 별도 vision encoder 서비스가 여러 이미지를 모아 한 번의
forward pass로 인코딩하는 것은 가능하다(VRAM은 더 씀). llama.cpp는 안 하고 있음.

### 프롬프트 / KV 캐시
- 슬롯 단위 prompt caching이 기본 동작. 슬롯 재사용 시 공통 프리픽스만큼 prefill 스킵.
- **멀티모달 프롬프트도 캐싱된다** — issue #22629는 오히려 이미지 프롬프트 캐싱이
  `--cache-ram` 한도를 넘겨 OOM을 유발하는 문제. 이미지 1장당 1000+ KV 토큰,
  직렬화된 KV 상태 약 128MiB로 보고됨. **캐시가 작동한다는 증거이자 메모리 위험 신호.**
- 관련 플래그: `--cache-reuse`, `--cache-ram`, `--cache-idle-slots`,
  `--slot-save-path` + `/slots` save/restore API.
- `-sps` (기본 0.5): 슬롯 매칭 임계값. 프롬프트 컨텍스트가 50% 이상 일치하면 그 슬롯 선택.
  `"id_slot"`으로 클라이언트가 명시 지정 가능, `-sps 0.0`으로 자동 선택 끄기 가능.
  **`-sps`는 슬롯 전환이 일관되지 않다는 보고가 있어, 프로덕션에서는 클라이언트측 슬롯 관리 권장.**
- **SWA 주의:** Gemma 2/3 같은 SWA 모델은 캐시 기법이 제대로 동작하려면 `--swa-full`이
  필요할 수 있고, 서버가 필요 시 경고를 띄운다. Gemma 4도 SWA(윈도우 512)이므로 해당.
- `/slots` save/restore는 메인테이너가 "technically unsafe", 보안 고려 없이는
  프로덕션 부적합이라고 명시.

### 알려진 버그
- issue #26207: 요청별 `lora` 어댑터가 다른데 프리픽스가 같으면 캐시가 재사용되어
  **출력이 조용히 오염**됨. (본 프로젝트는 lora 미사용이지만, 캐시 키가 프롬프트 토큰만
  본다는 사실 자체가 교훈.)
- issue #24146: Gemma 4 12B 비전이 `<unused49>` 토큰을 출력하는 eval 버그.
  E4B에서도 재현되는지 확인 필요.

## 4. Apple Silicon 대안

**`vllm-mlx`** (github.com/waybarrios/vllm-mlx) — MLX 네이티브,
OpenAI/Anthropic 호환 서버, continuous batching, 멀티모달, MCP 툴 콜링.

주장하는 수치:
- 텍스트 모델에서 llama.cpp 대비 **처리량 21~87% 향상** (Qwen3-0.6B ~ Nemotron-30B)
- 16 동시 요청에서 **4.3배 aggregate throughput**

**`mlx-vlm`** — Mac용 VLM 추론/파인튜닝. `mlx-lm` 0.18(2026-01)부터
`mlx_lm.server`가 OpenAI 호환 API + continuous batching 제공.

**상충하는 데이터:** 다른 출처는 M5 Max / Llama 3.1 8B / batch 4에서
MLX **CPU 백엔드** 3~5 tok/s vs llama.cpp **Metal** 92 tok/s (20~30배 차이)를 보고.
백엔드가 달라 공정한 비교가 아니며, MLX가 단일 요청은 빠르나 배치 처리량 스케일링이
약하다는 평가도 있음.

> **결론: 직접 재기 전엔 어느 쪽도 채택하지 않는다.** 처리량 우선 워크로드이므로
> 벤치 대상에는 반드시 포함한다. 단, 비전 인코더가 천장이면 엔진 교체 이득이
> 텍스트 벤치만큼 나오지 않을 가능성이 크다.

## 5. 프롬프트 구성 — 공식 권장

Gemma 4 모델 카드: **"place Image content before the text in your prompt."**

causal decoder 구조상 이미지 뒤 텍스트만 이미지를 attend할 수 있으므로 일관된 권장.
프리픽스 캐시 요구(정적 텍스트가 앞)와 충돌하며, 해결은 `00-design.md` §5의 3존 레이아웃.
