# trailwalk 설계 — 로드뷰를 따라 산책로를 이어간다

작성: 2026-08-17
상태: Kakao 로드뷰로 end-to-end 검증됨 (청계천 실주행) · 판정 기준 v3 확정

## 1. 경계

서빙 레포(`../../docs/00-design.md` §1)가 이미 선을 그어놨다. 그 선을 그대로 받는다.

```
━━━ 서빙 (../../docs/) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
이미지 1장 + 약간의 동적 텍스트 → JSON 판정 1건. stateless.
"이 장면이 산책로인가" 만 답한다.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ▲  HTTP (OpenAI 호환)
  │
━━━ 애플리케이션 (여기) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
로드뷰 수집 · 이미지 전처리 · 탐색 루프 · 방향 결정 · 종료 조건
프롬프트와 출력 스키마의 **내용** · 평가와 레이블
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**VLM 에게 묻는 것은 오직 하나다: "이 장면이 산책로인가."**
어디로 갈지, 언제 멈출지, 갈림길에서 무엇을 고를지는 전부 이쪽에서 정한다.
이 경계를 흐리면 서빙 쪽의 stateless 가정과 프리픽스 캐시 설계가 같이 무너진다.

## 3. 탐색 한 노드의 모양

`explore.py` 가 하는 일은 **"이 지점에서 뻗는 산책로를 전부 마킹한다"** 다.
시작점을 pano 로 스냅하고, 거기서 갈 수 있는 갈래를 전부 큐에 넣어 너비
우선으로 소비한다. 웹 UI 의 "위치를 넣으면 주변 산책로가 그려진다" 가 이
루프 위에 선다.

```
                큐에서 꺼낸 pano + 들어온 방위
                    │  시작점에서 반경 밖이면 마킹만 하고 frontier: distance_budget
                    ▼
      provider.neighbors(pano)            ← 화면의 흰 화살표와 같은 것
                    │  못 얻으면 frontier: neighbors_missing (이 갈래만 접는다)
                    │  온 길·기방문 제외 → 없으면 그냥 갈 곳이 없는 것
                    │  들어온 방향에 가까운 순 정렬 (맨 앞이 "정면")
                    ▼
      후보마다:  capture → view_to_data_uri → vlm.assess (1턴)
                    │       JPEG 강제 · 16:9 · 1280×720      is_trail 하나
                    ▼
        판정과 무관하게 **전부** 큐에 넣는다 (아래 "아님 판정도 확장한다")
                    │
                    ▼
                큐가 빌 때까지 → stop: exhausted
```

### 후보를 전부 물어본다 — 비용이 거의 안 든다

한 지점에서 여러 방향이 동시에 산책로일 수 있다. 갈림길이 그런 곳이다.
그래서 첫 성공에서 멈추지 않고 후보를 전부 묻는다.

호출 하나가 2.2초라 비싸 보이지만, **온 길을 뺀 이웃은 직선 구간에서 개수가 1**
이다. 실측(청계천 18스텝, 2026-08-17): s2~s15 는 지점당 1호출이고, 2~3호출이
나간 곳은 s16~s18 의 진짜 갈림길뿐이었다. 늘어나야 할 곳에서만 늘어난다.

한때 첫 성공에서 멈추는 모드(`probe_all: false`)가 있었다. 지웠다 — 목적이
경로가 아니라 지도라서, 반경 안을 전부 본다는 정책과 정면으로 어긋난다.

### 시작 노드는 화살표를 전부 본다

시작점에는 "온 길" 이 없다. 그래서 후보를 **하나도 빼지 않는다** —
개수 상한(`max_candidates`)도 안 건다.
**호출 수 = 화살표 개수**이고, 하나라도 산책로면 그 지점은 산책로다.

### 출력 스키마에 방향 필드를 넣지 않은 이유

"어느 방향이 산책로인가" 를 모델에게 묻는 대신, 후보마다 그 방향을 정면에 두고
찍어서 각각 묻는다. 한 장에 화살표 여럿을 담아 고르게 하면 모델이 화살표와
방위를 대응시켜야 하고, 화각 밖의 방위는 애초에 표현할 수 없다. 방향은
클라이언트가 이미 알고 있고, 비용도 같다(직선 1호출).

### 이동은 이웃 pano 그래프 하나뿐이다 (2026-08-18 정리)

처음엔 인접 목록을 얻을 방법이 없다고 보고 좌표를 직접 미는 방식으로 짰다.
그런데 로드뷰 화면의 흰 화살표가 바로 그 정보였고 데이터로 꺼낼 수 있었다
(`21-roadview-providers.md` §1.3). 한동안 두 이동이 공존했고 — 그래프가 주력,
좌표 밀기가 폴백 — **폴백을 없앴다.**

없앤 이유는 한 문장이다: 좌표 밀기는 **우리가 좌표를 지어내고** 지도에게
"이 근처에 뭐 있냐" 고 묻는다. 그래서 방위가 추측(`bearing`, ±60°)이고,
스냅이 엉뚱한 데 붙어도 런은 멀쩡해 보이며, 이웃 로드가 실패해도 조용히
폴백으로 새서 **품질이 나빠지는데 증상이 안 보인다** (실측: 청계천 22노드 중
12개 → `23-open-questions.md` §7).

그래프가 나은 점은 그 뒤집힌 꼴이다:

- **보폭을 정할 필요가 없다.** 촬영 간격이 곧 보폭이다 (실측 6.4~16.0m)
- **방위가 정확하다.** 이웃마다 실측 방위각(91.36° 같은)이 딸려 온다
- **온 길을 정확히 뺀다.** 각도로 어림하지 않고 pano_id 로 지운다
- **막다른 길이 명확하다.** "스냅 실패인가 길의 끝인가" 를 구분할 필요가 없다

지금은 **지도가 알려준 지점으로만 걷는다.** 이동을 만들던 `geo.destination` 도
지웠다. fixture 는 격자가 곧 그래프이므로 4방향 이웃을 정직하게 준다.

빈 이웃 목록은 **"갈래 없음" 이 아니라 로드 실패**로 읽는다 — 그 갈래는
`neighbors_missing` 으로 frontier 에 남기고 접는다. 다른 갈래가 있으므로
탐색 전체가 멈추지는 않는다. 진짜 막다른 길은 "이웃은 있는데 전부 온 길/기방문"
이다.

로드 실패의 원인과 해결, 그리고 이 결정이 드러낸 **pano 계열 비연결**
문제(차도 계열에서 시작하면 보행로 계열에 못 간다)는 `23-open-questions.md`
§7 에 있다.

### "아님" 판정도 확장한다 (2026-08-18 결정, 2026-08-20 고정)

처음엔 산책로 갈래만 확장했는데, **차도 pano 에서 시작하면 2호출 만에
죽는다** — 모든 방향이 "아님" 이라 큐가 즉시 빈다. 실측으로 확인했고, 웹 UI
유저는 길가를 찍기 마련이다. 그래서 판정과 무관하게 반경 안에서는 계속 간다.

같은 차도 좌표에서 재실측 (50호출): 다리 노드 1개를 건너 하천으로 내려가
청계천 **양안** 보행로를 모두 마킹했다.

끄는 손잡이(`expand_non_trail`)를 뒀다가 지웠다. "반경 안을 전부 본다" 가
정책인 이상 끄면 그 정책이 깨지고, 끈 런과 안 끈 런의 결과를 비교할 수 없다.

### 큐는 하나다

한동안 호출이 차도 격자에 새지 않게 산책로 갈래 큐를 먼저 비웠지만
**하나로 되돌렸다.** 큐를 나누면 소비 순서가 depth 를 따르지 않아 너비
우선이 깨지고("아님" 갈래의 depth 2 가 산책로 갈래의 depth 8 뒤로 밀린다),
frontier 가 "시작점에서 가까운 순서로 잘린 경계" 가 아니게 되어 이어서
탐색할 때의 입력으로서 의미가 흐려진다. 예산 배분보다 **경계의 의미**를
택했다. 차도로 새는 것은 반경이 막는다.

### 예산 축은 둘이다: 시간과 거리

시작점에서의 **직선거리**가 탐색 범위를 정하고, 벽시계가 안전망이다.
한때 호출 수와 걸음 수(depth)도 예산이었는데, 넷을 두면 어느 것이 실제로
끊었는지가 런마다 달라져 결과를 읽을 때 "여기까지가 지도인가 예산인가" 를
매번 되짚어야 했다. 사용자가 정하는 것은 반경이다.

걸음 수가 아니라 미터로 재는 이유: pano 간격이 6.4~16.0m 로 두 배 넘게
흔들려서 같은 depth 라도 실제 반경이 코스마다 다르다. 웹 UI 는 "여기서
반경 N m" 를 보여줄 것이므로 미터가 계약에 맞다.

예산에 걸려 못 간 갈래는 버리지 않고 `frontier` 에 남긴다 — 같은 자리에서
이어 탐색할 때 그게 그대로 입력이다. `depth` 는 예산 축에서 빠졌지만 출력에는
남는다 (노드가 시작점에서 몇 홉인지는 그리는 쪽이 쓴다).

**값은 여기 적지 않는다.** 기본값과 그 근거는 `app/config/trailwalk.yaml` 에
있다 (→ 루트 `CLAUDE.md` "설정", `app/CLAUDE.md` "문서를 코드와 붙여 두는 규칙").

### 종료 조건

루프가 왜 끝났는지는 `stop_reason` 하나로 나온다.

| `stop_reason` | 뜻 |
|---|---|
| `exhausted` | 큐가 비었다 — **반경 안을 다 봤다.** 정상 종료 |
| `time_budget` | 벽시계 소진. 노드 경계와 후보마다 본다 |
| `no_coverage` | 시작점 반경 안에 pano 가 없다. **탐색 자체가 성립하지 않는다** |
| `provider_error` | 시작점 스냅이 provider 오류로 실패 |
| `vlm_error` | 복구 불가한 VLM 실패. 판정을 못 받았다 — "아님" 이 아니다 |
| `image_ignored` / `server_dead` | §5 |
| (예외) `ProviderError` | provider 가 원인을 규명해 터뜨린 실패 (노드 응답 형식 변경 등). 삼키지 않고 런을 죽인다 |

갈래 단위로 접히는 것은 `stop_reason` 이 아니라 **`frontier` 의 `reason`** 이다:
`distance_budget`(반경 밖) · `neighbors_missing`(이웃 로드 실패) ·
`time_budget`(예산 소진 시점의 큐 잔여).

### 경고는 세 번째 필드다 (2026-08-20)

`stop_reason` 도 `frontier` 도 답하지 못하는 것이 있다. 캡처 실패가 그랬다:
판정이 아니라서 `probes` 에 못 넣고("아니오" 와 섞인다), 갈래가 사라진 것도
아니라서 frontier 에도 안 넣었다. 그래서 한 노드의 후보가 전부 캡처 실패해도
런은 `exhausted` 로 정상 종료한 것처럼 보였고, `log=None` 이면 흔적조차 없었다.

그래서 축을 하나 더 뒀다 (→ `trailwalk/warn.py`):

| | 답하는 질문 | 개수 |
|---|---|---|
| `stop_reason` | 이 결과를 **완결된 것으로 읽어도 되나** | 정확히 하나 |
| `frontier[].reason` | **어느 갈래**를 왜 안 갔나 | 갈래마다 |
| `warnings[]` | 이 결과를 **믿어도 되나**, 사용자에게 뭐라고 말하나 | 0..n |

겹칠 때는 두 곳 모두에 넣는다 — 중복이 아니라 다른 질문에 답하는 필드다.
웹은 `stop_reason` 을 안 읽어도 되고, 이어탐색 로직은 `warnings` 를 안 읽어도
된다. 문구는 `warn.TEXT` 표 하나에 모여 있고, 표에 없는 code 는 터진다.

갈래마다 나는 것(`neighbors_missing`, `capture_failed`)은 집계해 런 끝에 한
줄로 올린다. 한 건씩 올리면 진짜 신호가 묻힌다 — 실주행에서 22노드 중
12개까지 나왔다.

`stop_reason` 이 **런이 성립하지 않았음**을 뜻하면(`image_ignored`,
`server_dead`, `vlm_error`, `provider_error`, `no_coverage`) 러너가 경고
문구를 stderr 로 찍고 **exit 2** 로 끝낸다. 무인 실행에서 exit 0 이면
실패를 감지할 수단이 없다.

> `no_coverage` 와 "갈 곳이 없음" 을 섞으면 안 된다. 앞은 지도 사업자가 안 찍은
> 것이고 뒤는 모델의 판정이다. 정확도를 볼 때 둘을 한 통에 넣으면 모델이 억울해진다.

결과를 눈으로 보려면 `run.dump` + `eval/plot_explore.py` (OSM 타일 위 SVG).

### 한 길만 따라가는 루프(walk)는 지웠다 (2026-08-20)

갈림길에서 하나를 고르고 나머지를 frontier 에 기록만 하는 루프가 따로 있었다.
그 "나머지" 를 실제로 가는 것이 여기이므로 walk 는 explore 의 부분집합이었고,
탐색 범위를 반경으로 정한 뒤로는 단일 경로 추적을 따로 둘 이유가 없어졌다.

산출물을 읽는 도구도 없었다 — `eval/` 셋 다 walk 런로그를 안 읽고,
`report_eval.py` 는 명시적으로 무시한다. 경로 순서도 잃지 않는다:
`nodes` 가 `parent`/`depth` 를 들고 있고 큐가 FIFO 다.

## 4. 프롬프트를 애플리케이션이 소유한다

원래 system 프롬프트가 서빙 쪽 `bench/sweep.py` 에 있었다. 옮겼다.

근거는 서빙 설계 문서 §7 이다 — 게이트웨이는 **바이트 동일성을 보장하는 메커니즘**을
갖고, 그 안에 무슨 말이 들어가는지와 출력 필드의 의미는 애플리케이션 관심사다.

### 파일 + 해시 핀

```
app/prompts/system_v*.txt   ← 사람이 고치는 곳
trailwalk/prompt.py: PINS   ← 버전별 sha256. 의도치 않은 변경을 잡는 핀
```

system turn 이 1바이트만 달라져도 프리픽스 캐시 적중률이 0 이 된다. 에러는 안 나고
**그냥 느려진다.** 문자열을 코드에 두면 f-string 하나, 공백 하나가 조용히 섞인다.
파일로 두고 `read_bytes()` 로 verbatim 읽은 뒤 해시를 비교하면 바뀐 순간 터진다.

프롬프트를 고치면 해시도 같이 고친다. **판정 기준이 바뀌면 새 버전 파일을
만든다** — 같은 파일을 덮어쓰면 예전 결과가 어느 프롬프트로 난 것인지 알 수 없게
된다. 기존 `PINS` 줄은 고치지 않는다. 고치는 순간 이전 런로그의 fingerprint 가
거짓이 된다.

지금 세 버전이 있고 `vlm.prompt_version` 으로 고른다. 왜 세 개인지는
`23-open-questions.md` §5 에 있다 — 요약하면 v1 은 질문이 애매했고, v2 는
정의는 맞았지만 너무 엄격해 진짜 산책로를 거부했다.

`bench/sweep.py` 에 비슷한 문자열이 남아 있지만 그건 **토큰 비용 측정용 픽스처**다.
동기화하지 않는다. 벤치 수치의 비교 가능성은 프롬프트를 **고정**하는 데서 오고,
판정 품질은 프롬프트를 **고치는** 데서 온다. 목적이 반대다.

### 출력 스키마 — 토큰이 곧 시간이다

decode 는 ~37 ms/token 이고 출력 토큰 수에만 비례한다. 그래서 용도별로 나눴다.

| 스키마 | 필드 | 실측 출력토큰 | 용도 |
|---|---|---:|---|
| `walk` | `is_trail` | **17** | 탐색 루프. 스텝마다 여러 번 부르므로 가장 싸야 한다 |
| `eval` | `+ confidence` (0~10 정수) | **26** | 평가. 임계값을 움직여 ROC 를 그린다 |

`confidence` 를 소수 실수가 아니라 0~10 정수로 둔 이유: 임계값 스윕에 11단계면
충분한데 소수점은 토큰을 더 먹는다. 자유 텍스트 `reason` 은 넣지 않는다 —
실측상 요청당 1.3초다.

### ⚠️ 정의하지 않은 필드는 쓰레기를 낸다

`confidence` 를 스키마에만 넣고 프롬프트에서 설명하지 않았더니 **`is_trail=true`
인데 `confidence=0`, `is_trail=false` 인데 `confidence=1`** 이 나왔다. 모델이
"산책로다움" 점수로 해석한 것이다. 스키마는 형식을 강제할 뿐 의미를 주지 않는다.

프롬프트에 한 문장을 넣자 방향이 잡혔다 ("방금 답한 is_trail 에 대한 확신도,
확신하는 '아니오'는 10이지 0이 아니다"). 다만 **지금은 전부 10 으로 포화**돼 있다.
합성 이미지라 그럴 수도 있고 교정이 안 된 것일 수도 있다 — 실제 로드뷰로
확인해야 한다 (`23-open-questions.md` §6).

## 5. 조용히 깨지는 것들

이 서비스의 실패는 대부분 **에러 없이** 일어난다. 클라이언트가 감시한다.

| 신호 | 뜻 | 코드 |
|---|---|---|
| `prompt_tokens` 가 임계 미만 | **이미지가 통째로 무시됐다** (WEBP 사고) | `vlm._parse` → `ImageIgnoredError` |
| 같은 지점인데 런마다 판정이 다름 | **덜 그려진 프레임을 찍었다** (아래) | `kakao.capture` 프레임 안정화 |
| `cached_tokens == 0` (첫 호출 제외) | system turn 에 가변값이 섞였다 | `Stats.cache_misses` → 요약에 경고 |
| `finish_reason != "stop"` | 출력이 잘렸다. thinking 모드 의심 | `vlm._parse` → `VlmError` |
| 500 이 `vlm.fatal_500_streak` 회 연속 | Metal OOM 좀비. **자체 복구 안 됨** | `ServerDeadError` — 재시도 중단 |

`prompt_tokens` 검사가 **JSON 파싱보다 먼저** 온다. 이미지가 무시되면 모델은
그럴듯한 JSON 을 만들어낸다. 파싱은 성공하고 값은 순전한 환각이다.
`prompt_tokens` 만이 이걸 잡는다.

임계값은 따로 적어 두지 않고 `image.expected_image_tokens` 에서 파생시킨다
(`settings.min_prompt_tokens`). 이미지 크기를 바꾸면 임계도 따라 움직여야
하는데, 숫자를 두 곳에 적으면 한쪽만 바뀌고 검사가 조용히 헐거워진다.

**`imaging.py` 를 우회해 data URI 를 만들지 말 것.** 그게 유일한 출구이고,
포맷·종횡비 규칙이 거기 한 군데에만 있어야 조용히 깨지지 않는다.

### 덜 그려진 프레임 — 이 종류의 대표 사례

같은 시작점에서 두 번 돌렸는데 경로가 갈렸다. 한 지점(pano `1039598393`,
방위 89.3°)에서 한 번은 `false`, 한 번은 `true` 가 나왔다. temperature 는 0 이다.

원인을 갈라보니:

| | 결과 |
|---|---|
| 같은 **바이트**를 두 번 보냈을 때 | 항상 같은 답 → **모델은 결정적이다** |
| 같은 pano·방위를 두 번 **찍었을 때** | 첫 회만 다른 PNG → **렌더가 비결정적이다** |

pano 를 바꾼 직후 첫 스크린샷이 타일이 덜 붙은 프레임인 경우가 있었다.
프레임 전이를 재보니 4개 중 3개는 즉시 안정되는데 문제의 pano 만 프레임 3개를
거쳐 **+300ms 에 확정**됐다.

그래서 **연속 두 스크린샷이 같아질 때까지** 찍게 했다. 두 런의 probe 24개가
일치했고 고쳤다고 판단했다. **그게 틀렸다.**

### 안정 판정을 세 번 고쳤다

같은 pano 를 5번 찍었더니 PNG 가 **4가지**로 나왔다. 5번 다 "연속 두 프레임
일치" 를 통과한 채로였고, 그중 1회는 판정까지 뒤집혔다.

| 통과한 조건 | 왜 뚫렸나 | 대응 |
|---|---|---|
| 연속 2프레임 일치 | 타일이 저해상도→고해상도로 덮어쓰는 **중간에 잠깐 멎는다**. 거기서 두 프레임이 일치해버린다 | 타일 요청이 끊길 때까지 먼저 기다리고(`_await_tiles`), 그다음 `render_settle_stable` 프레임 연속 일치 |
| 위 조건 + 요청 끊김 | 세션의 **첫 캡처**만 여전히 달랐다 (3.0s vs 1.15s — 브라우저·SwiftShader·HTTP 캐시가 전부 차 있다) | 첫 캡처는 찍고 **버린다** (~1.2s) |

고친 뒤 같은 pano 6회가 전부 동일 바이트, 같은 시작점의 walk 두 번이 probe
24개까지 완전히 일치한다.

> 이 버그가 위험한 이유는 **아무것도 실패하지 않기 때문**이다. HTTP 200 이고,
> JSON 도 멀쩡하고, 로그도 깨끗하다. 그냥 탐색이 다른 길로 샌다.
>
> 두 번째 교훈은 **"두 런이 일치했다" 가 결정성의 증거가 아니라는 것**이다.
> 두 런이 같은 중간 상태에서 멎으면 똑같이 일치한다. 반복 캡처의 바이트를
> 직접 비교해야 알 수 있다.

### 6.1 Kakao 로드뷰 — 청계천 (2026-08-17)

청계천 (37.5695, 127.0050) 에서 정동향으로 출발. 같은 구간을 두 방식으로 걸었다.

```
좌표 밀기   스텝 20 · 호출 23 ·  85s · 229m
이웃 그래프 스텝 25 · 호출 27 · 111s · 256m · pano 간격 6.4~16.0m (중앙 8.4m)
공통: 2.2 s/호출 · cached_tokens 300 고정 · 재시도 0 · 파싱실패 0 · 재방문 0
```

판정이 실제로 맞았다:

| 스텝 | 장면 | 판정 | |
|---|---|---|---|
| 0 (정동향) | 청계천**로** — 차량·상가·주차 | `false` | ✅ 맞다 |
| 0 (30°) | 하천 방향 | `true` | 방향 전환 |
| 2 | 직진·좌 실패, 우(90°) 성공 | | 보행로 진입 |
| 3~19 | 청계천 수변 보행로 | `true` ×17 | ✅ 캡처 확인 |

캡처를 눈으로 봤다 — 포장된 보행로, 보행자 다섯, 우측에 하천, 좌측에 담쟁이
석축. 시작 지점은 명백한 차도였고 모델이 그것을 거부했다.

**"정면 먼저" 가 실제로 값을 했다**: 25스텝을 27호출로 걸었다 (75호출이 아니라).
갈림길 두 곳(차도 → 하천 진입 램프)에서만 후보를 더 열었다.

그래프 쪽 방위각이 84.9°~93.6° 로 흔들리는 것이 길의 실제 곡률이다.
좌표 밀기에서는 내가 정한 30°/90° 두 값밖에 나올 수 없었다.

> ⚠️ 표본 몇 장을 눈으로 본 것은 정확도가 아니다. 정량 평가는 코스 폴리라인
> 위에서 뽑은 라벨 세트로 따로 한다 (`22-labels.md` §7).

### 6.2 fixture provider (배선 검증)

`bench/images` 를 로드뷰인 척 돌린 배선 검증. **판정 품질이 아니라 배선의 확인이다.**

```
스텝 6 · VLM 호출 7 · 26s
첫 호출 13,052ms  ← 콜드 스타트. 가이드 §7 의 "1.7s → 12.6s" 와 일치
이후    2,118~2,289ms  ← 문서값 2.13s 와 일치
prompt_tokens 523 (이미지 264 + system 232 + 사용자 텍스트)
cached_tokens 232 정상 유지 → system turn 바이트 고정이 실제로 작동
completion_tokens 17 (walk) / 26 (eval) → 문서값과 일치
```

`run.warmup: true` 면 콜드 스타트가 측정 밖으로 빠진다. 지연을 재는 런에서는 켤 것.

### 캡처와 VLM 을 겹친다 (2026-08-22)

한 판정에 드는 시간은 **로드뷰 캡처 + VLM 호출**이고 둘 다 대기다. 한때
캡처하고, 답을 기다리고, 다시 캡처했다. 그러면 둘 중 어느 쪽도 상대가 일하는
동안 놀고 있다.

실측(2026-08-22, 약수역 500m · 원격 vLLM · 191판정)에서 벽시계 854초가
**VLM 425초 · 캡처 429초로 정확히 반씩** 갈렸다. 어느 한쪽만 빠르게 해도
전체는 절반까지밖에 안 줄어든다는 뜻이다.

지금은 캡처한 즉시 서버로 띄우고 답을 기다리지 않은 채 다음 캡처로 간다.
이게 성립하는 이유는 위의 **"아님 판정도 확장한다"** 와 **"큐는 하나다"** 다
— 판정값은 확장 여부도 큐 순서도 바꾸지 않으므로, 답이 필요한 곳은 기록할
때뿐이다. 판정이 그래프 모양을 정하는 설계였다면 겹칠 수 없다.

기다리는 자리를 하나라도 핫패스에 남기면 겹치기가 통째로 사라진다. 처음엔
큐에서 노드를 꺼낼 때 그 노드의 판정을 기다리게 짰는데, 그게 다음 캡처보다
앞이라 속도가 **하나도** 안 붙었다. `nodes[].is_trail` 은 출력 전용이라
(루프의 어떤 판단도 읽지 않는다) 자리만 잡아 두고 런 끝에 채운다.

오프라인 측정(캡처·VLM 각 220ms 로 흉내, 21판정):

```
max_inflight=0   464 ms/판정      ← 겹치기 없음(옛 동작)
max_inflight=1   253 ms/판정  1.83배
max_inflight=2   250 ms/판정  1.86배  ← 더 띄워도 얻는 것이 없다
```

**워커 수는 그대로 `max_inflight` 다.** 서버가 직렬인 지금은 둘 이상 띄워도
VLM 끼리 큐에서 기다릴 뿐이라 위 표처럼 더 얻는 것이 없다. 그래도 여기서
조이지 않는다 — 조이면 큐가 vLLM 이 아니라 app 의 스레드풀로 옮겨올 뿐이고,
**줄을 세우는 것은 서버의 일이다** (→ 루트 CLAUDE.md). 서버를 동시 처리로
바꾸는 날 app 을 고칠 일이 없다는 뜻이기도 하다.

재현성은 워커 수가 아니라 **기록이 FIFO** 라는 데서 온다: `resolve` 를 보낸
순서로만 부르므로 probes 와 런로그의 순서·내용이 직렬로 돌 때와 같다.
`max_inflight=1000` 으로도 같은지 테스트가 못박는다.

**클라이언트 하나를 여러 스레드가 부른다.** 그래서 `VlmClient` 의 Stats
카운터와 500 연속 횟수는 락 뒤에 있다 (HTTP 는 락 밖이다). 안 걸면 조용히
틀린다 — 계측이 실제보다 적게 세이고, `fatal_500_streak` 서킷브레이커가
스케줄링에 따라 걸리거나 안 걸린다. 조용한 실패를 잡으려고 둔 계측이
조용히 틀리는 것이 제일 나쁘다.

값은 `vlm.max_inflight` 이고 `0` 이 옛 동작이다. 대가 둘:

- **예산을 max_inflight 개만큼 넘겨서 끊는다.** 시간을 확인하는 시점에 이미
  띄운 것은 되돌릴 수 없다.
- **실패를 그만큼 늦게 안다.** 그래서 `pump` 가 기다리기 전에 **이미 도착한
  답을 먼저 치운다** — 안 그러면 루프가 한 노드를 더 처리해서 없던
  `neighbors_missing` 경고를 만들어낸다. 경고는 사람이 읽는 것이다.

## 7. 결정 사항

- **VLM 동시 요청 없음.** 서버가 `-np 1` 이고 비전 인코딩이 원자적·직렬이라
  `-np 4` 는 처리량 +20% 에 지연 3.3배다. 병렬화는 여기가 아니라 서빙 쪽에서
  풀 문제다. 다만 **캡처와 VLM 은 겹친다** — 아래 참조. 겹치는 대상이 서로 다른
  VLM 호출이 아니라 서로 다른 종류의 대기라 위 근거와 부딪히지 않는다.
- **이미지는 기본적으로 저장하지 않는다.** 지도 사업자 약관상 회색지대다
  (`23-open-questions.md` §2). 런로그에는 pano_id 와 좌표만 남겨 재현 가능하게 한다.
- **좌표를 프롬프트에 넣지 않는다.** 모델이 좌표로 할 수 있는 일이 없고, 토큰만
  먹으며, 실수로 system 쪽에 새면 캐시가 죽는다. 진행 방위만 이미지 뒤에 붙인다.
- **provider 는 `nearest` / `capture` 두 메서드뿐.** 이웃 그래프를 전제하지 않는다.
- **fixture provider 를 1급으로 유지한다.** API 키 없이 전체 배선을 돌릴 수 있어야
  하고, temperature 0 이므로 프롬프트를 고쳤을 때 무엇이 뒤집혔는지 바로 보인다.

### 경로 필드는 엄격하게, Bash 는 좁게

Read/Edit/Write/Grep/Glob 의 경로 필드에 `.env` 가 오면 의도가 명확하므로 무조건
막는다. **Bash 는 다르다.** 명령줄에는 파일을 *읽는* 경우와 그냥 *언급하는*
경우가 섞인다.

```
읽음:   cat app/.env          grep KEY app/.env       source app/.env
언급:   git commit -m "... .env 를 gitignore 에 추가 ..."
```

언급까지 막으면 이 커밋 메시지조차 못 쓴다. 실제로 이 기능을 만들다 세 번
걸렸다. **그러면 사람이 훅을 꺼버리고, 꺼진 훅은 아무것도 못 막는다.**

그래서 Bash 는 명령을 셸 구획(`;` `&&` `||` `|` 줄바꿈)으로 쪼갠 뒤, `.env` 가
있는 구획에 **내용을 꺼낼 수 있는 명령어**(cat/grep/source/python/cp/git…)나
덮어쓰기 리다이렉트가 같이 있을 때만 막는다. 힙독 본문의 언급은 앞줄의
`cat <<EOF` 와 다른 구획이라 통과한다.

회귀 테스트가 양쪽을 다 잰다 — 못 막는 것과 과하게 막는 것 둘 다 실패다.

### 왜 "조심해서 읽기" 가 아니라 "못 읽게" 인가

비밀값은 한 번 대화 컨텍스트에 들어가면 **되돌릴 수 없다.** 트랜스크립트에 남고,
요약에 섞여 들어가고, 이후 모든 요청에 딸려 간다. 삭제한다는 개념이 없다.
따라서 "읽은 뒤 조심" 은 성립하지 않고 읽기 자체를 막아야 한다.

`.env.example` 은 값이 없는 형식 파일이라 막지 않는다.

### 이건 보안 경계가 아니다

작정하면 우회된다 (`cat app/'.'env`). 목적은 공격 방어가 아니라 **사고 방지**다.
진짜 보안은 키를 로테이트할 수 있게 두는 것이고, 훅은 무심코 하는 실수를
막는 난간이다.

`config.py` 의 규칙: **예외 메시지에도 값을 넣지 않는다.** "키가 이상한데 뭐가
들었나" 를 찍고 싶은 유혹이 반드시 생기는데, 예외는 스택트레이스에 남고
스택트레이스는 어디로든 간다. 확인이 필요하면 `keycheck.py` 를 쓴다.
