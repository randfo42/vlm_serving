# trailwalk 설계 — 로드뷰를 따라 산책로를 이어간다

작성: 2026-08-17
상태: Kakao 로드뷰로 end-to-end 검증됨 (청계천 실주행) · 판정 기준 v3 확정

---

## 1. 경계

서빙 레포(`../../docs/00-design.md` §1)가 이미 선을 그어놨다. 그 선을 그대로 받는다.

```
━━━ 서빙 (../../docs/) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
이미지 1장 + 약간의 동적 텍스트 → JSON 판정 1건. stateless.
"이 장면이 산책로인가" 만 답한다.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ▲  HTTP (OpenAI 호환)
  │
━━━ 애플리케이션 (여기) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
로드뷰 수집 · 이미지 전처리 · 탐색 루프 · 방향 결정 · 종료 조건
프롬프트와 출력 스키마의 **내용** · 평가와 레이블
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**VLM 에게 묻는 것은 오직 하나다: "이 장면이 산책로인가."**
어디로 갈지, 언제 멈출지, 갈림길에서 무엇을 고를지는 전부 이쪽에서 정한다.
이 경계를 흐리면 서빙 쪽의 stateless 가정과 프리픽스 캐시 설계가 같이 무너진다.

## 3. 한 스텝의 모양

```
                현재 pano + 진행 방위 bearing
                    │
      provider.neighbors(pano)            ← 화면의 흰 화살표와 같은 것
                    │  온 길·기방문 제외 → 없으면 stop: dead_end
                    │  진행 방향에 가까운 순 정렬 (맨 앞이 "정면")
                    ▼
      후보마다:  capture → view_to_data_uri → vlm.assess (1턴)
                    │       JPEG 강제 · 16:9 · 1280×720      is_trail 하나
                    ▼
        산책로 판정된 것 중 **가장 정면**으로 이동 (pano 로 직행)
        나머지 산책로 갈래는 frontier 에 남긴다
                    │  하나도 없으면 miss_tolerance 만큼 참고
                    ▼  그래도 안 되면 stop: dead_end
                다음 스텝
```

### 후보를 전부 물어본다 — 비용이 거의 안 든다

한 지점에서 여러 방향이 동시에 산책로일 수 있다. 갈림길이 그런 곳이다.
그래서 첫 성공에서 멈추지 않고 후보를 전부 묻는다.

호출 하나가 2.2초라 비싸 보이지만, **온 길을 뺀 이웃은 직선 구간에서 개수가 1**
이다. 실측(청계천 18스텝): s2~s15 는 스텝당 1호출이고, 2~3호출이 나간 곳은
s16~s18 의 진짜 갈림길뿐이었다. 늘어나야 할 곳에서만 늘어난다.

폴백(좌표 밀기)은 성격이 다르다. 후보가 실제 갈래가 아니라 추측(`bearing`, ±60°)
이고 항상 3개다. 전부 물으면 매 스텝 3배가 되는데 얻는 게 없다. 그래서
`probe_all=None`(기본)은 **그래프면 전부, 폴백이면 첫 성공에서 멈춤**이다.

### 출력 스키마에 방향 필드를 넣지 않은 이유

"어느 방향이 산책로인가" 를 모델에게 묻는 대신, 후보마다 그 방향을 정면에 두고
찍어서 각각 묻는다. 한 장에 화살표 여럿을 담아 고르게 하면 모델이 화살표와
방위를 대응시켜야 하고, 화각 밖의 방위는 애초에 표현할 수 없다. 방향은
클라이언트가 이미 알고 있고, 비용도 같다(직선 1호출).

### 왜 이웃 pano 그래프인가

처음엔 인접 목록을 얻을 방법이 없다고 보고 좌표를 직접 미는 방식으로 짰다.
그런데 로드뷰 화면의 흰 화살표가 바로 그 정보였고 데이터로 꺼낼 수 있었다
(`21-roadview-providers.md` §1.3). 그래프가 나은 점:

- **보폭을 정할 필요가 없다.** 촬영 간격이 곧 보폭이다 (실측 6.4~16.0m)
- **방위가 정확하다.** 이웃마다 실측 방위각(91.36° 같은)이 딸려 온다
- **온 길을 정확히 뺀다.** 각도로 어림하지 않고 pano_id 로 지운다
- **막다른 길이 명확하다.** "스냅 실패인가 길의 끝인가" 를 구분할 필요가 없다

이웃을 못 주는 provider(fixture 등)에서는 **자동으로 좌표 밀기로 되돌아간다.**

### 종료 조건

| 이유 | 뜻 |
|---|---|
| `max_steps` / `time_budget` | 예산 소진 |
| `no_coverage` | 반경 안에 pano 가 없음. **산책로의 끝과 구분되지 않는다** |
| `dead_end` | 어느 방향도 산책로가 아님이 `miss_tolerance` 회 연속 |
| `revisit_loop` | 같은 pano 를 `revisit_tolerance` 회 초과로 재방문 |
| `image_ignored` / `server_dead` / `vlm_error` | §5 |

> `no_coverage` 와 `dead_end` 를 섞으면 안 된다. 앞은 지도 사업자가 안 찍은 것이고
> 뒤는 모델의 판정이다. 정확도를 볼 때 둘을 한 통에 넣으면 모델이 억울해진다.

## 3.5 분기 탐색 — explore (2026-08-18)

walk 가 "한 길을 따라간다" 라면 `explore.py` 는 "이 지점에서 뻗는 산책로를
전부 마킹한다" 다. walk 가 frontier 에 기록만 하던 갈래를 큐에 넣어 너비 우선으로
소비한다. 웹 UI 의 "위치를 넣으면 주변 산책로가 그려진다" 가 이 루프 위에 선다.

한 판정의 모양(capture → imaging → vlm.assess)과 후보 생성(`walk._candidates`)은
walk 와 **같은 코드**다. 두 루프의 판정 조건이 갈라지면 결과를 비교할 수 없다.

walk 와 다른 결정들:

| | walk | explore | 이유 |
|---|---|---|---|
| 갈림길 | 정면 하나, 나머지 기록 | **전부 큐에** | 목적이 경로가 아니라 지도다 |
| 시작 방향 | `--bearing` 필수 | 모든 방향 | 시작점에는 "온 길" 이 없다 |
| U턴 방지 | `max_turn_deg=120` | 없음 (180) | 온 길은 visited 로 정확히 빠진다 |
| 실질 예산 | `max_steps` | **`max_vlm_calls`** | 갈림길 수에 따라 같은 depth 라도 비용이 다르다 |
| miss 허용 | 2회 밀어봄 | 없음 | 갈래마다 밀면 오판 하나가 가짜 가지를 만든다 |
| `no_coverage` | 탐색 종료 | 그 갈래만 접음 | 다른 갈래가 남아 있다 |
| 재방문 | tolerance 로 감지 | 원천 차단 (visited set) | pano 하나에 판정 하나 |

예산(depth·호출·시간)에 걸려 못 간 갈래는 버리지 않고 `frontier` 에 남긴다 —
같은 자리에서 이어 탐색할 때 그게 그대로 입력이다. 설정은 전부
`ExploreConfig` 에 있고 필드마다 주석으로 무엇을 하는지 적혀 있다.

## 4. 프롬프트를 애플리케이션이 소유한다

원래 system 프롬프트가 서빙 쪽 `bench/sweep.py` 에 있었다. 옮겼다.

근거는 서빙 설계 문서 §7 이다 — 게이트웨이는 **바이트 동일성을 보장하는 메커니즘**을
갖고, 그 안에 무슨 말이 들어가는지와 출력 필드의 의미는 애플리케이션 관심사다.

### 파일 + 해시 핀

```
app/prompts/system_v*.txt   ← 사람이 고치는 곳
trailwalk/prompt.py: PINS   ← 버전별 sha256. 의도치 않은 변경을 잡는 핀
```

system turn 이 1바이트만 달라져도 프리픽스 캐시 적중률이 0 이 된다. 에러는 안 나고
**그냥 느려진다.** 문자열을 코드에 두면 f-string 하나, 공백 하나가 조용히 섞인다.
파일로 두고 `read_bytes()` 로 verbatim 읽은 뒤 해시를 비교하면 바뀐 순간 터진다.

프롬프트를 고치면 해시도 같이 고친다. **판정 기준이 바뀌면 새 버전 파일을
만든다** — 같은 파일을 덮어쓰면 예전 결과가 어느 프롬프트로 난 것인지 알 수 없게
된다. 기존 `PINS` 줄은 고치지 않는다. 고치는 순간 이전 런로그의 fingerprint 가
거짓이 된다.

지금 세 버전이 있고 `--prompt` 로 고른다. 왜 세 개인지는
`23-open-questions.md` §5 에 있다 — 요약하면 v1 은 질문이 애매했고, v2 는
정의는 맞았지만 너무 엄격해 진짜 산책로를 거부했다.

`bench/sweep.py` 에 비슷한 문자열이 남아 있지만 그건 **토큰 비용 측정용 픽스처**다.
동기화하지 않는다. 벤치 수치의 비교 가능성은 프롬프트를 **고정**하는 데서 오고,
판정 품질은 프롬프트를 **고치는** 데서 온다. 목적이 반대다.

### 출력 스키마 — 토큰이 곧 시간이다

decode 는 ~37 ms/token 이고 출력 토큰 수에만 비례한다. 그래서 용도별로 나눴다.

| 스키마 | 필드 | 실측 출력토큰 | 용도 |
|---|---|---:|---|
| `walk` | `is_trail` | **17** | 탐색 루프. 스텝마다 여러 번 부르므로 가장 싸야 한다 |
| `eval` | `+ confidence` (0~10 정수) | **26** | 평가. 임계값을 움직여 ROC 를 그린다 |

`confidence` 를 소수 실수가 아니라 0~10 정수로 둔 이유: 임계값 스윕에 11단계면
충분한데 소수점은 토큰을 더 먹는다. 자유 텍스트 `reason` 은 넣지 않는다 —
실측상 요청당 1.3초다.

### ⚠️ 정의하지 않은 필드는 쓰레기를 낸다

`confidence` 를 스키마에만 넣고 프롬프트에서 설명하지 않았더니 **`is_trail=true`
인데 `confidence=0`, `is_trail=false` 인데 `confidence=1`** 이 나왔다. 모델이
"산책로다움" 점수로 해석한 것이다. 스키마는 형식을 강제할 뿐 의미를 주지 않는다.

프롬프트에 한 문장을 넣자 방향이 잡혔다 ("방금 답한 is_trail 에 대한 확신도,
확신하는 '아니오'는 10이지 0이 아니다"). 다만 **지금은 전부 10 으로 포화**돼 있다.
합성 이미지라 그럴 수도 있고 교정이 안 된 것일 수도 있다 — 실제 로드뷰로
확인해야 한다 (`23-open-questions.md` §6).

## 5. 조용히 깨지는 것들

이 서비스의 실패는 대부분 **에러 없이** 일어난다. 클라이언트가 감시한다.

| 신호 | 뜻 | 코드 |
|---|---|---|
| `prompt_tokens < 200` | **이미지가 통째로 무시됐다** (WEBP 사고) | `vlm._parse` → `ImageIgnoredError` |
| 같은 지점인데 런마다 판정이 다름 | **덜 그려진 프레임을 찍었다** (아래) | `kakao.capture` 프레임 안정화 |
| `cached_tokens == 0` (첫 호출 제외) | system turn 에 가변값이 섞였다 | `Stats.cache_misses` → 요약에 경고 |
| `finish_reason != "stop"` | 출력이 잘렸다. thinking 모드 의심 | `vlm._parse` → `VlmError` |
| 500 연속 3회 | Metal OOM 좀비. **자체 복구 안 됨** | `ServerDeadError` — 재시도 중단 |

`prompt_tokens` 검사가 **JSON 파싱보다 먼저** 온다. 이미지가 무시되면 모델은
그럴듯한 JSON 을 만들어낸다. 파싱은 성공하고 값은 순전한 환각이다.
`prompt_tokens` 만이 이걸 잡는다.

**`imaging.py` 를 우회해 data URI 를 만들지 말 것.** 그게 유일한 출구이고,
포맷·종횡비 규칙이 거기 한 군데에만 있어야 조용히 깨지지 않는다.

### 덜 그려진 프레임 — 이 종류의 대표 사례

같은 시작점에서 두 번 돌렸는데 경로가 갈렸다. 한 지점(pano `1039598393`,
방위 89.3°)에서 한 번은 `false`, 한 번은 `true` 가 나왔다. temperature 는 0 이다.

원인을 갈라보니:

| | 결과 |
|---|---|
| 같은 **바이트**를 두 번 보냈을 때 | 항상 같은 답 → **모델은 결정적이다** |
| 같은 pano·방위를 두 번 **찍었을 때** | 첫 회만 다른 PNG → **렌더가 비결정적이다** |

pano 를 바꾼 직후 첫 스크린샷이 타일이 덜 붙은 프레임인 경우가 있었다.
프레임 전이를 재보니 4개 중 3개는 즉시 안정되는데 문제의 pano 만 프레임 3개를
거쳐 **+300ms 에 확정**됐다.

그래서 **연속 두 스크린샷이 같아질 때까지** 찍게 했다. 두 런의 probe 24개가
일치했고 고쳤다고 판단했다. **그게 틀렸다.**

### 안정 판정을 세 번 고쳤다

같은 pano 를 5번 찍었더니 PNG 가 **4가지**로 나왔다. 5번 다 "연속 두 프레임
일치" 를 통과한 채로였고, 그중 1회는 판정까지 뒤집혔다.

| 통과한 조건 | 왜 뚫렸나 | 대응 |
|---|---|---|
| 연속 2프레임 일치 | 타일이 저해상도→고해상도로 덮어쓰는 **중간에 잠깐 멎는다**. 거기서 두 프레임이 일치해버린다 | 타일 요청이 끊길 때까지 먼저 기다리고(`_await_tiles`), 그다음 연속 **3**프레임 |
| 위 조건 + 요청 끊김 | 세션의 **첫 캡처**만 여전히 달랐다 (3.0s vs 1.15s — 브라우저·SwiftShader·HTTP 캐시가 전부 차 있다) | 첫 캡처는 찍고 **버린다** (~1.2s) |

고친 뒤 같은 pano 6회가 전부 동일 바이트, 같은 시작점의 walk 두 번이 probe
24개까지 완전히 일치한다.

> 이 버그가 위험한 이유는 **아무것도 실패하지 않기 때문**이다. HTTP 200 이고,
> JSON 도 멀쩡하고, 로그도 깨끗하다. 그냥 탐색이 다른 길로 샌다.
>
> 두 번째 교훈은 **"두 런이 일치했다" 가 결정성의 증거가 아니라는 것**이다.
> 두 런이 같은 중간 상태에서 멎으면 똑같이 일치한다. 반복 캡처의 바이트를
> 직접 비교해야 알 수 있다.

## 6. 실측

### 6.1 Kakao 로드뷰 — 청계천 (2026-08-17)

청계천 (37.5695, 127.0050) 에서 정동향으로 출발. 같은 구간을 두 방식으로 걸었다.

```
좌표 밀기   스텝 20 · 호출 23 ·  85s · 229m
이웃 그래프 스텝 25 · 호출 27 · 111s · 256m · pano 간격 6.4~16.0m (중앙 8.4m)
공통: 2.2 s/호출 · cached_tokens 300 고정 · 재시도 0 · 파싱실패 0 · 재방문 0
```

판정이 실제로 맞았다:

| 스텝 | 장면 | 판정 | |
|---|---|---|---|
| 0 (정동향) | 청계천**로** — 차량·상가·주차 | `false` | ✅ 맞다 |
| 0 (30°) | 하천 방향 | `true` | 방향 전환 |
| 2 | 직진·좌 실패, 우(90°) 성공 | | 보행로 진입 |
| 3~19 | 청계천 수변 보행로 | `true` ×17 | ✅ 캡처 확인 |

캡처를 눈으로 봤다 — 포장된 보행로, 보행자 다섯, 우측에 하천, 좌측에 담쟁이
석축. 시작 지점은 명백한 차도였고 모델이 그것을 거부했다.

**"정면 먼저" 가 실제로 값을 했다**: 25스텝을 27호출로 걸었다 (75호출이 아니라).
갈림길 두 곳(차도 → 하천 진입 램프)에서만 후보를 더 열었다.

그래프 쪽 방위각이 84.9°~93.6° 로 흔들리는 것이 길의 실제 곡률이다.
좌표 밀기에서는 내가 정한 30°/90° 두 값밖에 나올 수 없었다.

> ⚠️ 표본 몇 장을 눈으로 본 것은 정확도가 아니다. 정량 평가는 여전히
> 코스 폴리라인이 없어 막혀 있다 (`22-labels.md` §2).

### 6.2 fixture provider (배선 검증)

`bench/images` 를 로드뷰인 척 돌린 배선 검증. **판정 품질이 아니라 배선의 확인이다.**

```
스텝 6 · VLM 호출 7 · 26s
첫 호출 13,052ms  ← 콜드 스타트. 가이드 §7 의 "1.7s → 12.6s" 와 일치
이후    2,118~2,289ms  ← 문서값 2.13s 와 일치
prompt_tokens 523 (이미지 264 + system 232 + 사용자 텍스트)
cached_tokens 232 정상 유지 → system turn 바이트 고정이 실제로 작동
completion_tokens 17 (walk) / 26 (eval) → 문서값과 일치
```

`--warmup` 을 켜면 콜드 스타트가 측정 밖으로 빠진다. 지연을 재는 런에서는 켤 것.

## 7. 결정 사항

- **동시 요청 없음.** 순차 호출만 한다. 서버가 `-np 1` 이고 비전 인코딩이 원자적·
  직렬이라 `-np 4` 는 처리량 +20% 에 지연 3.3배다. 병렬화는 여기가 아니라
  서빙 쪽에서 풀 문제다.
- **이미지는 기본적으로 저장하지 않는다.** 지도 사업자 약관상 회색지대다
  (`23-open-questions.md` §2). 런로그에는 pano_id 와 좌표만 남겨 재현 가능하게 한다.
- **좌표를 프롬프트에 넣지 않는다.** 모델이 좌표로 할 수 있는 일이 없고, 토큰만
  먹으며, 실수로 system 쪽에 새면 캐시가 죽는다. 진행 방위만 이미지 뒤에 붙인다.
- **provider 는 `nearest` / `capture` 두 메서드뿐.** 이웃 그래프를 전제하지 않는다.
- **fixture provider 를 1급으로 유지한다.** API 키 없이 전체 배선을 돌릴 수 있어야
  하고, temperature 0 이므로 프롬프트를 고쳤을 때 무엇이 뒤집혔는지 바로 보인다.

## 9. 비밀값

지도 API 키는 `app/.env` 에 있고 **Claude 는 그 파일을 읽지 못한다.**

```
.claude/hooks/block-secret-reads.py        PreToolUse 훅
.claude/hooks/test-block-secret-reads.sh   회귀 테스트 24케이스
.claude/hooks/keycheck.py                  값 없이 상태만 보여주는 점검 창구
app/trailwalk/config.py                    코드가 값을 쓰는 유일한 경로
```

### 경로 필드는 엄격하게, Bash 는 좁게

Read/Edit/Write/Grep/Glob 의 경로 필드에 `.env` 가 오면 의도가 명확하므로 무조건
막는다. **Bash 는 다르다.** 명령줄에는 파일을 *읽는* 경우와 그냥 *언급하는*
경우가 섞인다.

```
읽음:   cat app/.env          grep KEY app/.env       source app/.env
언급:   git commit -m "... .env 를 gitignore 에 추가 ..."
```

언급까지 막으면 이 커밋 메시지조차 못 쓴다. 실제로 이 기능을 만들다 세 번
걸렸다. **그러면 사람이 훅을 꺼버리고, 꺼진 훅은 아무것도 못 막는다.**

그래서 Bash 는 명령을 셸 구획(`;` `&&` `||` `|` 줄바꿈)으로 쪼갠 뒤, `.env` 가
있는 구획에 **내용을 꺼낼 수 있는 명령어**(cat/grep/source/python/cp/git…)나
덮어쓰기 리다이렉트가 같이 있을 때만 막는다. 힙독 본문의 언급은 앞줄의
`cat <<EOF` 와 다른 구획이라 통과한다.

회귀 테스트가 양쪽을 다 잰다 — 못 막는 것과 과하게 막는 것 둘 다 실패다.

### 왜 "조심해서 읽기" 가 아니라 "못 읽게" 인가

비밀값은 한 번 대화 컨텍스트에 들어가면 **되돌릴 수 없다.** 트랜스크립트에 남고,
요약에 섞여 들어가고, 이후 모든 요청에 딸려 간다. 삭제한다는 개념이 없다.
따라서 "읽은 뒤 조심" 은 성립하지 않고 읽기 자체를 막아야 한다.

`.env.example` 은 값이 없는 형식 파일이라 막지 않는다.

### 이건 보안 경계가 아니다

작정하면 우회된다 (`cat app/'.'env`). 목적은 공격 방어가 아니라 **사고 방지**다.
진짜 보안은 키를 로테이트할 수 있게 두는 것이고, 훅은 무심코 하는 실수를
막는 난간이다.

`config.py` 의 규칙: **예외 메시지에도 값을 넣지 않는다.** "키가 이상한데 뭐가
들었나" 를 찍고 싶은 유혹이 반드시 생기는데, 예외는 스택트레이스에 남고
스택트레이스는 어디로든 간다. 확인이 필요하면 `keycheck.py` 를 쓴다.
