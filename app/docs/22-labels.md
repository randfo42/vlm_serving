# 레이블 — 무엇이 산책로인가

출처: 서울시 「서울, 테마산책길」 https://gil.seoul.go.kr/trail/list.do?key=2406040004
수집: 2026-08-17 · `labels/fetch_gil_seoul.py` → `labels/trails.json`

## 1. 얻은 것

**150개 산책로, 총 421.3km.** 사이트가 밝힌 "5개 테마 총 150개소" 와 개수·테마별
분포가 정확히 일치한다 (2015~2018년 선정).

| 테마 | 개수 |
|---|---:|
| 숲이 좋은 길 | 75 |
| 역사문화길 | 24 |
| 한강·하천이 좋은 길 | 23 |
| 전망이 좋은 길 | 23 |
| 계곡이 좋은 길 | 5 |

28개 지역에 걸쳐 있다 (종로 12, 노원 11, 마포·강서·강북 각 8 …).

항목 하나:

```json
{
  "trail_sn": 184,
  "name": "홍릉 두물길",
  "theme": "한강·하천이 좋은 길",
  "difficulty": "중급",
  "distance_km": 6.2,
  "duration": "2시간 10분",
  "gu": "동대문구",
  "detail_url": "https://gil.seoul.go.kr/trail/view.do?key=2405200010&sc_trailSn=184&sc_trailSeCd=SE004",
  "smgis_url": "https://map.seoul.go.kr/smgis/short2.jsp?p=6Pn4G"
}
```

`--detail` 을 주면 상세 페이지까지 훑어 **경유지 이름**(신설동역 → 안암2교 →
성북천교 → 청계천 → …)과 진입 방법, 코스 지도 PDF 링크가 붙는다.

목록 페이지 하나에 이름·테마·난이도·거리·시간·자치구·지도링크가 전부 들어 있어서,
기본 대장을 만드는 데는 상세 페이지 150건을 훑을 필요가 없다 (15요청, ~15초).

## 2. ⚠️ 없는 것 — 좌표

**어디에도 경로 폴리라인이 없다.** 이게 지금 평가의 가장 큰 구멍이다.

확인한 것들:

| 후보 | 결과 |
|---|---|
| 상세 페이지의 "코스자료 다운로드" | **GPX 가 아니라 코스 지도 PDF** (2쪽) |
| 공공데이터포털 「전국길관광정보표준데이터」 | 길명·총길이·시종점 **이름**·경로정보(텍스트)뿐. **위경도 없음** |
| 「서울특별시 양천구_둘레길 현황」 등 자치구 데이터 | 일부 구만. 전 시 커버 안 됨 |
| 스마트서울맵 `map.seoul.go.kr` | **코스 선을 실제로 그린다.** 여기 있다 |

레이블 항목마다 `smgis_url` 을 남겨둔 이유가 이것이다. 지금은 사람이 눌러 보는
용도이지만, 좌표를 꺼낼 때 유일한 손잡이가 된다.

## 3. 좌표를 얻는 세 가지 길

아직 고르지 않았다. `23-open-questions.md` §4.

### (a) 스마트서울맵에서 꺼낸다

단축 링크가 `poiViewMap?ti=100715&pi=<poi_id>` 로 리다이렉트한다.
`ti=100715` 이 테마산책길 테마 id 이고, 150건이 같은 테마에 들어 있다.
일부 항목은 `pi` 가 타임스탬프가 아니라 **안정적인 id**(`A_015`, `C_039`)로 나온다.

페이지 JS 에서 `smgis2ContextJs + '/qry/THEME'` 라는 질의 엔드포인트를 찾았다.
GET 은 400, POST 는 500 을 준다 — **존재하지만 페이로드 형식을 아직 모른다.**
브라우저 개발자도구에서 실제 요청을 한 번 보면 풀린다.

- 장점: 정확히 이 150개 코스의 공식 선형이다. 레이블과 1:1
- 단점: 비공식 스크래핑. 언제든 깨진다

공공데이터포털에 「서울특별시_스마트서울맵」 OpenAPI 가 등록돼 있다. 이게 같은
데이터를 공식 창구로 준다면 그쪽이 낫다. **미확인.**

### (b) OpenStreetMap 으로 대체한다

Overpass API 로 서울 영역의 `highway=footway|path|pedestrian|steps` 를 받는다.

- 장점: 무료·개방·즉시 사용 가능. 서울 보행로 커버리지가 좋다
- 단점: **서울시가 지정한 150개 코스와 다른 대상이다.** OSM 의 보행로에는
  테마산책길이 아닌 것이 대량으로 섞이고, 반대로 코스 일부가 빠질 수 있다.
  "산책로 판정" 의 정의가 미묘하게 달라진다

### (c) 손으로 시드만 찍는다

각 코스의 **출발점 좌표 하나 + 초기 방위**만 수동으로 정한다. 경유지 이름
(예: "신설동역 1번 출구")이 이미 있으니 지오코딩으로 상당 부분 자동화된다.

- 장점: 오늘 당장 된다. 탐색 루프의 입력으로는 **이것으로 충분하다**
- 단점: 스텝별 정답이 없다. "얼마나 잘 식별하는가" 를 재려면 결국 (a)나 (b)가 필요

## 4. 평가를 어떻게 할 것인가

정답의 형태가 두 가지로 갈린다. 섞지 말 것.

**형태 1 — 점 단위 정확도.** `(lat, lng, heading)` 마다 정답 라벨을 붙이고
`is_trail` 을 맞추는지 본다. 정밀도·재현율·ROC 가 나온다.
필요한 것: 코스 폴리라인(양성) + 일반 차도 표본(음성). → §3 (a) 또는 (b)

**형태 2 — 경로 단위 커버리지.** 코스 시작점에서 탐색을 돌려 실제 코스를 얼마나
따라갔는지 본다. 폴리라인과의 거리·중첩 길이로 잰다.
이쪽이 실제 목표("로드뷰를 진행하며 산책로를 이어간다")에 더 가깝지만,
채점하려면 역시 폴리라인이 있어야 한다.

**§3 (c) 만으로 지금 할 수 있는 것**: 탐색을 돌려 경로를 뽑고 지도에 올려
사람이 눈으로 보는 것. 정량 지표는 안 나오지만 **"완전히 헛짚는가" 는 바로 보인다.**
Kakao 커버리지 확인(§`23-open-questions.md` §1)과 같이 하면 첫 실측으로 충분하다.

---

## 5. 음성 표본이 필요하다

양성(산책로)만으로는 아무것도 못 잰다. 전부 `is_trail=true` 라고 답해도 만점이다.

음성 후보:
- 산책로에서 멀리 떨어진 일반 차도 (코스 폴리라인에서 200m 이상)
- 주차장, 교차로, 대로변
- 같은 좌표에서 **산책로 반대 방향**을 본 화각 — 가장 값싸고 가장 어려운 음성이다.
  탐색 루프가 실제로 헷갈리는 지점이기도 하다

마지막 항목이 특히 중요하다. 좌표가 같으므로 폴리라인이 없어도 만들 수 있다.
