## ✅ 1. Kakao 로드뷰가 서울 산책로를 실제로 찍었는가 — **해결됨 (2026-08-17)**

**찍었다.** 프로젝트의 전제가 성립한다.

`check_kakao.py` 로 서울 6개 좌표를 실측:

| 좌표 | pano | 스냅 거리 | 렌더 |
|---|---|---:|---|
| 시청 앞 대로 (대조군: 차도) | 잡힘 | 18m | 정상 |
| 청계천 산책로 | 잡힘 | 2m | 정상 |
| 서울숲 공원길 | 잡힘 | 5m | 정상 |
| 한강 반포 수변길 | 잡힘 | 8m | 정상 |
| 남산 둘레길 | **없음** | - | - |
| 홍릉 두물길 (신설동역 부근) | 잡힘 | 15m | 정상 |

**산책로 표본 4/5 에서 커버리지가 있다.** 남산 둘레길만 미촬영이다.

그리고 **도보 촬영이 실재한다.** 청계천에서 pano 계열이 둘로 갈린다 —
`1212370258` 은 청계천'로'(차도) 위에서 찍힌 것이고, `10395983xx` 계열은
하천 바닥의 **보행로에서 걸으며 찍은 것**이다. 배낭형 장비 도보 촬영이라는
2차 자료(`21-roadview-providers.md` §1.4)가 실측으로 뒷받침됐다.

### 판정도 맞았다

탐색 20스텝을 돌린 결과가 그대로 증거다 (`20-app-design.md` §6):

- 출발 지점 정동향 = 청계천로. 차량·상가·주차된 차. 모델 판정 **`false`** — 맞다
- 방향을 틀어 하천 보행로로 내려간 뒤 17스텝 연속 **`true`** — 맞다.
  캡처를 눈으로 확인했다: 포장된 보행로, 보행자 다섯, 우측에 하천

**남은 것은 정량 평가다.** 표본 몇 장을 눈으로 본 것과 정확도를 재는 것은 다르다.
폴리라인은 확보됐고(§4) 라벨 세트도 있지만, 지금 세트는 **양성 전용**이라
나오는 것은 재현율뿐이다 (`22-labels.md` §4).

### 설정 (전부 통과)

| | 상태 |
|---|---|
| Playwright + chromium | ✅ headless/headed 둘 다 기동 |
| Kakao **JavaScript** 키 | ✅ `KAKAO_MAP_JS_API_KEY` 로 분리해 등록 |
| 플랫폼 Web 도메인 등록 | ✅ `http://127.0.0.1:8731` |
| 카카오맵 제품 활성화 | ✅ 콘솔 > 제품 설정 > 카카오맵 |

여기까지 오는 데 걸린 것들을 남겨둔다 — 같은 자리에서 또 막힐 만한 것들이다.

#### 카카오맵 제품 활성화는 별도 스위치다

```
HTTP 403  NotAuthorizedError
{"message": "App(...) disabled OPEN_MAP_AND_LOCAL service."}
```

키를 발급하고 도메인을 등록해도 **제품을 따로 켜야 한다.**
콘솔 > 내 애플리케이션 > 제품 설정 > 카카오맵 > 활성화 설정.

#### 도메인 등록 — 127.0.0.1 ≠ localhost

같은 요청을 Referer 만 바꿔 보내면 갈린다:

| Referer | 응답 |
|---|---|
| `http://127.0.0.1:8731` | 403 `disabled OPEN_MAP_AND_LOCAL service` |
| `http://localhost:8731` | 401 `domain mismatched! ... check out registered web domains` |

127.0.0.1 이 등록돼 있다는 증거다(등록이 안 됐다면 여기도 401 이 났을 것).
동시에 **Kakao 는 `127.0.0.1` 과 `localhost` 를 다른 도메인으로 취급한다.**
provider 가 `127.0.0.1` 로 고정하는 이유다.

#### ⚠️ 브라우저 안에서는 이 에러가 보이지 않는다 — 중요

인증에 실패하면 Kakao 는 JS 대신 **JSON 에러**를 돌려준다. 크롬은 그 응답을
`<script>` 로 받기를 거부하고 `net::ERR_BLOCKED_BY_ORB` 로 통째로 막는다.
**에러 내용이 사라진다.** 남는 것은 "SDK 가 안 뜬다" 는 침묵뿐이다.

이걸 모르면 원인 넷(키·도메인·서비스 활성화·커버리지)을 구분할 방법이 없다.
그래서 `providers/kakao.py` 의 `diagnose_sdk()` 가 **같은 URL 을 같은 Referer 로
파이썬에서 한 번 더 받아** 본문을 읽는다. 20초 침묵 대신 위의 403 메시지가 나온다.

### 확인 순서

서비스를 켠 뒤, 탐색을 돌리기 전에 진단부터:

```bash
python app/check_kakao.py            # 좌표 6곳 · VLM 없이 · 20초
python app/check_kakao.py --headed   # 검은 화면이 의심되면
```

차도 대조군을 포함한 6개 표본에서 pano 가 잡히는지, 실제로 그려지는지
(픽셀 분산으로 판정), 스냅 거리가 얼마인지를 표로 준다. **차도까지 실패하면
커버리지 문제가 아니다** — 이 구분이 진단의 핵심이다.

그 다음:

```bash
# 설정에서 provider: kakao, start: [37.5768, 127.0246], bearing: 90, headed: true
# 로 고치고, budget.max_distance_m 을 줄여 몇 걸음만 보게 한다
python app/run_explore.py --config app/config/my.yaml
```

`run.headed: true` 로 시작할 것. 완전 headless 에서 WebGL 이 안 그려져 **검은
화면**이 찍히는 경우가 있고, 그러면 모델은 "산책로 아님" 을 정직하게 답해서
원인이 로드뷰가 아니라 렌더에 있다는 걸 놓치기 쉽다.

확인할 것 세 가지:

| 증상 | 뜻 |
|---|---|
| 브라우저 콘솔에 SDK 인증 오류 / 아무것도 안 뜸 | **키 종류나 도메인 등록 문제.** 커버리지가 아니다 |
| `stop_reason: no_coverage` 가 즉시 | 그 좌표에 로드뷰가 없다. 커버리지 문제 |
| 화면이 검다 | 렌더 문제(WebGL). 로드뷰 탓이 아니다 |
| 모두 `is_trail=false` 인데 그림은 멀쩡 | 프롬프트/판정 문제 |

**네 가지가 겉으로는 다 "안 된다" 로 보인다.** `run.headed` 로 브라우저를 띄워
직접 보는 것이 이들을 가르는 가장 빠른 방법이다.

**표본은 테마별로 고를 것.** "한강·하천이 좋은 길"(하천변, 차도와 가까움)과
"숲이 좋은 길"(산속, 차량 진입 불가)은 커버리지가 정반대일 가능성이 크다.
`labels/trails.json` 에 테마가 붙어 있다.

## ✅ 3. Kakao `zoom 0` 의 실제 화각 — **가로 90.9°** (2026-08-18 실측)

Kakao 의 `zoom` 은 −3~3 의 **이산 배율**이라 "90도" 를 지정할 방법이 없다
(Naver 는 `fov` 를 20~100 도로 직접 준다). 그래서 `zoom 0` 을 그대로 쓰는데,
그게 몇 도인지 문서에 없었다. **쟀다.** → `check_fov.py`

### 방법 — 회전량 대비 픽셀 이동

정사영에서 중심 기준 각 θ 인 점은 `x = cx + f·tan(θ)` 에 찍힌다. 카메라를
오른쪽으로 Δ 돌리면 중앙에 있던 것이 `cx − f·tan(Δ)` 로 간다. 그 이동을
템플릿 매칭(NCC)으로 재서 `f` 를 얻고, `fov = 2·atan(W / 2f)`.

Δ 를 하나만 쓰지 않는 이유는 **모델 자체를 검산하기 위해서**다. 정사영이면
Δ 가 달라도 `f` 가 일정해야 한다.

| Δ회전 | 이동 px | NCC | f(px) | 화각 |
|---:|---:|---:|---:|---:|
| 4° | 44 | 0.99 | 629.2 | 91.0° |
| 8° | 88 | 0.94 | 626.2 | 91.3° |
| 12° | 134 | 0.88 | 630.4 | 90.9° |
| 16° | 185 | 0.79 | 645.2 | 89.5° |
| 20° | 227 | 0.70 | 623.7 | 91.5° |
| 25° | 294 | 0.62 | 630.5 | 90.9° |
| 30° | 371 | 0.58 | 642.6 | 89.8° |

**가로 90.9° (편차 1.9°)**, 세로 59.5° (뷰포트 1280×720). `f` 가 Δ 전 구간에서
630±10 으로 붙어 있으므로 정사영 가정이 맞다 — 숫자를 믿어도 된다.

### ⚠️ 화각을 정하는 것은 `zoom` 이 아니라 **뷰포트 종횡비**다

뷰포트를 바꿔가며 다시 쟀다. `zoom 0` 은 고정인 채로:

| 뷰포트 | 종횡비 | 가로 화각 | 세로 화각 |
|---|---:|---:|---:|
| 1280×720 | 1.78 | 91.1° | 59.7° |
| 720×720 | 1.00 | 59.2° | 59.2° |
| 640×720 | 0.89 | 54.1° | 59.8° |
| 1280×360 | 3.56 | 126.3° | 58.1° |

**세로 화각이 ~59.5° 로 고정이고 가로는 종횡비에서 파생된다.**
`가로 = 2·atan((W/H)·tan(세로/2))` 가 네 줄 전부에 맞는다.

즉 `zoom` 은 세로 화각의 이산 단계이고, 우리가 실제로 쥐고 있는 연속 손잡이는
`VIEW_W`/`VIEW_H` 다. 그런데 그 값은 화각을 보고 정한 것이 아니라 **이미지
토큰 수를 264 로 고정하려고** `imaging.TARGET_SIZE` 에 맞춘 것이다
(`kakao.py:42`). **지금의 가로 화각 90.9° 는 토큰 예산 결정의 부산물이다.**

이게 (a)/(b) 선택을 바꾼다:

- **(b) 가 실현 가능해졌다.** zoom 표를 안 재도 종횡비로 원하는 가로 화각을
  연속적으로 맞출 수 있다. 대신 16:9 를 벗어나면 토큰 상수가 흔들린다 —
  화각과 토큰 예산을 맞바꾸는 셈이다
- **(a) 가 더 정직해졌다.** provider 가 신고할 값이 매직 상수가 아니라
  **계산식**이 된다: 세로 59.5°(zoom 0 실측) + 자기 뷰포트 → 가로 화각

측정 시 화살표는 **끈다**(`hide_arrows`). 화살표는 세상에 안 붙어 있다 (→ 아래).

### ✅ 결론 — `fov_deg` 를 계약에서 뺐다 (2026-08-19)

`WalkConfig.fov_deg` / `ExploreConfig.fov_deg` 의 90.0 이 실측 90.9° 와 사실상
같았다. **판정 결과를 다시 볼 필요는 없다.** 다만 그 일치가 근거 있는 것이 아니라
우연이었고, 값은 `capture()` 로 넘어가 버려지고 있었다.

**(a) 를 골랐다: 인자를 지웠다.** `capture(pano, heading)` 이다.

호출자가 화각을 지시하는 모양이었는데 **지시할 수 있는 provider 가 하나도
없었다.** Kakao 는 각도를 받을 수단 자체가 없고(zoom 은 −3~3 이산 배율),
fixture 는 원본 사진의 화각을 그대로 돌려준다. 지시할 수 없는 것을 지시하는
계약이라 지웠다. 화각은 이제 **provider 가 정하고, 문서가 그 값을 기록한다** —
`kakao.py` 의 `VIEW_W`/`VIEW_H` 주석과 이 절이다.

(b)(도 → 가장 가까운 zoom 단계로 매핑)는 안 골랐다. zoom −3~3 일곱 단계를
전부 재야 하고, 종횡비 쪽이 더 정밀한 손잡이인데다(위 표) 그건 토큰 상수와
맞물린다. **필요해지면 그때 재면 된다.**

> `imaging.equirect_to_view` 는 `fov_deg` 를 그대로 갖고 있다. 거기서는 진짜로
> 쓰인다 — 등장방형 360° 이미지를 한 화각으로 자를 때의 실제 계산이다. 원본
> 파노라마를 주는 provider 가 생기면(Naver) 그때 살아난다 (§8).

### provider 마다 화각이 다르다 — fixture 와 kakao 를 섞지 말 것

| provider | 화각 |
|---|---|
| **kakao** | 90.9° 고정 (zoom 0 + 1280×720). pano·방위·depth 와 무관하다 |
| **fixture** | **불명. 이미지마다 다르다** — 원본 사진이 갖고 있던 값이다 |

fixture 판정과 kakao 판정을 화각 축에서 비교하면 안 된다. §6 의 confidence
포화 원인 후보 중 "fixture 가 합성 이미지라 실제로 쉬운 문제다" 가 여기와
맞닿아 있다.

### ✅ `side_offsets` 문제는 사라졌다 — 그 각도를 쓰는 코드가 없다

원래 걱정은 "±60° 가 화각과 안 맞아 사각지대/중복이 생긴다" 였다. 확인해 보니
`side_offsets` 는 **이웃 그래프가 없을 때만 타는 폴백 전용**이었고, 그
폴백 자체를 없앴다 (→ `20-app-design.md` §3). 후보각은 이제 전부 이웃의
실측 방위각이다. **우리가 각도를 지어내는 자리가 없다.**

기록으로 남기면, 폴백이 살아 있었대도 문제는 아니었다: 화각 90.9° 에 ±60° 면
화면끼리 약 31° 겹친다. 사각지대도, "절반씩 겹침" 도 아니다.

### 화살표는 랜드마크로 쓸 수 없다

같은 실측에서 나온 부수 결과다. 화면의 흰 화살표는 이웃 방위에 **정사영되지
않는다.** 정면(pan=이웃 방위)에서는 화면 중앙에 정확히 오지만, 카메라를 돌리면
프레임 안에 남으려고 끌려온다:

```
이웃 '동' = 실측 방위 91.37°.  pan 을 돌리며 화살표 라벨의 화면 x 좌표:

  pan      1.4°   31.4°   61.4°   91.4°  121.4°  151.4°  181.4°
  축 기준   +90°    +60°    +30°     0°     −30°    −60°    −90°
  실측 x    848     794     721     640     559     486     432
  정사영   (밖)    (밖)    1004     640     276    (밖)    (밖)     ← f=630 기준
```

축에서 +30° 인 pan 61.4° 는 정사영상 x=1004 여야 하는데 721 이다. ±60° 부터는
아예 화면 밖(1731 / −451)이어야 하는데 여전히 보인다. 실측 x 는 pan 에 대해
거의 선형(180° 에 416px, ~2.3px/도)이라 **투영이 아니라 UI 배치**다.
방위가 필요하면 노드 JSON 의 `spot[].pan`(소수점 방위각)을 쓸 것 — §7.

## ✅ 4. 코스 폴리라인 — 확보했다 (2026-08-19)

## 🟡 5. 프롬프트 — 축이 두 번 바뀌었고, **경계는 아직이다**

`system_v1.txt` 는 "보행 가능한 연속된 노면이 보이는가" 를 묻는데, 이게
두 가지로 읽혔다:

| 해석 | 청계천로(차도) 위에서 |
|---|---|
| **프레임 안에 산책로가 보이는가** | `true` — 갓길에 빨간 자전거도로가 보인다 |
| **카메라가 산책로 위에 있는가** | `false` — 차선·주차 차량·오토바이 한복판이다 |

프롬프트는 둘 중 무엇인지 말한 적이 없었다. 모델이 틀린 게 아니라 안 정해져
있었다. **후자로 정했다** (2026-08-17). 탐색 루프는 "저기 길이 있다" 가 아니라
"여기로 한 칸 가도 되는가" 를 물어야 한다.

### v2 는 실패했고 v3 가 됐다

`system_v2.txt` 는 정의를 바꾸는 데는 성공했지만 **진짜 산책로를 거부했다.**
같은 이미지 24장으로 재판정한 결과:

| | 확인된 7건 중 정답 | 전체 true |
|---|---|---|
| v1 (보이는가) | 5 | 17/24 |
| v2 (위에 있는가, 1차) | **4** | 11/24 |
| v3 (위에 있는가, 수정) | **7** | 15/24 |

v2 가 거부한 4건은 전부 청계천 하천변 보행로였다. 원인은 내가 넣은 두 문구다:

- `"a streambed that is not a maintained route"` — 이 길은 **하천 바닥에 있다**
- `"a continuous walkable surface"` — 폭이 1인용이고 노면이 돌·흙이다

즉 v2 는 "차도인가" 가 아니라 **"충분히 산책로답게 생겼는가"** 를 묻고 있었다.
v3 는 폭·노면 조건을 판정에서 빼고 하나만 남겼다: *정의된 길이 카메라 아래로
이어지는가.* 보행자가 그 노면 위를 걷고 있으면 강한 증거라는 문장도 넣었다.

v1·v2 는 지우지 않는다. 설정의 `vlm.prompt_version` 으로 아직 고를 수 있다.

> **부수 발견:** `walk` 스키마(is_trail 만)와 `eval` 스키마(+confidence)는
> 판정을 바꾸지 않는다. 4개 pano × 2프롬프트에서 8/8 일치. 평가에서 잰
> 정확도를 탐색 루프의 정확도로 읽어도 된다는 뜻이다.
> ⚠️ **v4 에서 다시 재야 한다.** 이건 불리언 스키마에서 잰 것이고, v4 는
> 범주를 낸다 (`surface` ↔ `surface_eval`).

### v3 도 실패했다 — 골목을 전부 산책로로 셌다 (2026-08-23)

v3 는 확인된 7건을 다 맞혔지만 그 7건에 **골목이 없었다.**

약수동 500장(`app/runs/images/yaksu-1000`, 차도·골목뿐이고 진짜 산책로는
사실상 없는 세트)을 v3 로 돌려 True 판정 8건을 전부 눈으로 봤다.
**8건 전부 카메라가 차도 위**였고, 그 중 여섯은 프레임 안에 결정적 증거가
찍혀 있었다 — 황색 중앙선, 노란 빗금(안전지대), **30 제한속도 표지**,
"어린이보호구역" 노면표시. 차가 다닌다는 사실이 사진 안에 있는데
**프롬프트가 그걸 보라고 한 적이 없었다.**

원인은 v3 의 핵심 문장 자체다:

> *Width and surface do not decide it… What decides it is that a defined
> route runs under the camera and continues ahead.*

골목은 이 조건을 정확히 만족한다. 이 문장은 v2 가 거부한 청계천 하천
보행로(1인용 폭, 돌·흙)를 되살리려고 넣은 것이고 그 목적은 달성했는데,
**같은 문장이 모든 이면도로에 yes 를 준다.** 남은 판별자는 두 개뿐이었고
둘 다 사진에서 안 보이거나 역방향이었다:

| v3 의 판별자 | 왜 안 먹히나 |
|---|---|
| `pedestrian-only street` | **법적 사실이지 시각적 사실이 아니다.** 한 프레임은 "지금 움직이는 차가 없다" 만 말한다 |
| `wide tree-lined sidewalk` | 골목마다 화분·가로수가 있다. 게다가 금지 목록이 보도의 실격 사유를 "no buffer or **greenery**" 로 적어 두어 **화분이 산책로 쪽 증거로 읽혔다** |

즉 v1·v2·v3 는 느슨/엄격 **한 축에서만 왕복**했다.

### v4 — 축을 하나 더 놓고, 경계를 프롬프트 밖으로 뺐다

**새 축: 이 노면을 차와 공유하는가.** 프롬프트가 관찰 항목으로 적는다 —
중앙선·측선·빗금·정지선·횡단보도·노면숫자 / 제한속도 표지·어린이보호구역 /
이 노면 위 주차·주차장 진출입구. 배제 증거는 볼라드·계단·차선 없는 전폭
보행포장. 그리고 못 박는다: *"An absence of cars is not evidence."*

**불리언을 버렸다.** v4 는 `camera_surface` 범주 하나를 낸다:

| | |
|---|---|
| 차량 공유 | `roadway` `shared_alley` |
| 보행 | `sidewalk` `pedestrian_way` `park_path` `waterside` |
| 그 외 | `open_ground` `unclear` |

`is_trail` 은 서버가 아니라 **설정**이 만든다 — `vlm.trail_surfaces`
(값과 근거는 `config/trailwalk.yaml`). 왜 그랬나: **어디가 경계인지는 라벨
없이 못 정한다.** 보행자우선 골목(신당동 곱창골목처럼 볼라드 + 전폭 벽돌
포장)을 산책로로 셀 것인가가 실제 경계인데, 이걸 프롬프트 문장에 새기면
경계를 옮길 때마다 새 프롬프트 버전이 되고 **이미 받아 둔 판정을 못 쓴다.**
설정에 두면 `camera_surface` 를 다시 해석하는 것만으로 A/B 가 된다.

런로그·벤치 JSONL 이 `is_trail` 과 `camera_surface` 를 **둘 다** 남기는
이유가 이것이다. 유도된 값만 남기면 경계를 옮긴 순간 옛 런이 무의미해진다.

### v4 도 실패했다 — 터널이 산책로가 됐다 (2026-08-24)

약수역 반경 1km explore(판정 1,916건, `skip 4/5`)에서 `is_trail` True 가
**2건**이었고, 둘 다 재캡처해서 눈으로 봤다:

| | 실제 |
|---|---|
| `1212529924` h147, 574m | **터널 안 차도.** 차선 도색·터널 조명·주행 차량·유리 방음벽. `park_path` 로 판정됐다 |
| `1212637312` h198, 468m | 남산 자락 숲길. 실제로 걷기 좋아 보이지만 **포장 도로**이고 승용차가 주차돼 있다 — v4 자신의 정의로는 `roadway`/`shared_alley` 다 |

즉 1,916건에서 쓸 만한 것을 하나도 못 건졌다. 노면만 보면 **터널 바닥과
공원 길이 둘 다 "차선 없는 회색 면"** 이라 헷갈릴 자리가 있다.

같은 런에서 `unclear` 6건도 나왔는데, 재캡처해 보니 아파트 단지 내 도로·
사거리 횡단보도처럼 **대낮에 또렷한 장면**이었다. 프롬프트가 *"choose
unclear only when you genuinely cannot see the surface, not when the choice
is a hard one"* 이라고 못 박았는데도 **"애매하면 여기" 통**이 됐다.

### v5 — 축을 자연으로 바꿨다. 그것도 하나로는 부족했다

노면을 아예 안 보고 **주변 자연을 0~3** 으로만 묻는다(등급은 사람이 정했다:
가로수만 1 · 큰 나무 많으면 2 · 완전히 공원 같으면 3. 0 은 프롬프트를 쓰며
더했다). 같은 1km 를 다시 돌렸다 — 판정 1,971건, 74분, `exhausted`:

| 등급 | 건수 | | v4 대비 |
|---|---:|---:|---|
| 0 거의 없음 | 580 | 29.4% | v4 는 1,916건 중 1,744건(91%)을 `roadway` 한 칸에 몰아넣었다 |
| 1 가로수만 | 1,215 | 61.6% | v5 는 0/1/2 에 30/62/8 로 퍼진다 |
| 2 큰 나무 많음 | 173 | 8.8% | |
| 3 완전히 공원 | 3 | 0.2% | |

**True 176건** (임계 2). v4 는 같은 구역에서 2건이었다. 등급 2 표본 20건을
방위·거리로 흩어 뽑아 눈으로 보니 대체로 납득이 갔다(아파트 진입로 산울타리,
남산 자락 숲길, 석축 위 수목). 축이 실제로 일한다.

**그런데 등급 3 세 건 중 하나가 콘크리트 골목이었다.** 화강암 건물·실외기·
아스팔트·주차 차량뿐이고 담쟁이가 가장자리에 조금 있는 장면이다. v4 가
터널을 `park_path` 로 부른 것과 같은 급의 폭주가 극단 등급에 남아 있다.

그리고 더 근본적으로, **v5 는 "걸을 데가 있는가" 를 아예 안 묻는다.** 차도
한복판에서 찍어도 녹지만 많으면 높은 점수가 나온다.

### v6 — 응답을 둘로 나눈다 (기본값)

`nature_level`(0~3)은 **v5 와 바이트 동일한 문구**를 쓰고, `footway`(0/1)를
따로 묻는다. 한 필드에 두 뜻을 섞지 않는 것이 요점이다 — 섞으면 낮은 판정이
"자연이 없다" 인지 "걸을 데가 없다" 인지 구별할 수 없고, 그게 v1~v4 가
반복해서 밟은 함정이다.

`footway` 의 근거는 셋이고 **어느 하나만 있어도 1** 이다:

| 근거 | |
|---|---|
| 물리적 분리 | 연석 턱 · 다른 포장 · 볼라드 · 난간 · 완충 식재 · 도로를 벗어난 길 |
| 보행 공간을 지정한 도색 | 가장자리 색띠 · 보행 차로 표시 |
| 그 길을 따라 걷는 사람 | |

도색과 보행자를 근거로 넣은 것은 **사람의 결정**이다 — 첫 초안은 둘 다
배제했었다. 다만 두 군데를 좁혔다: **차량용 도색은 안 센다**(중앙선·차선·
빗금·정지선. 안 그러면 황색 중앙선 하나로 1 이 되어 이 필드가 상수가 된다),
**횡단하는 사람은 안 센다**(세면 사거리가 전부 1 이 된다).

**터널 차로는 0 이다.** 차선을 도색 근거로 인정하지 않는 것이 그 근거이고,
위의 v4 오답이 여기서 걸린다.

`is_trail` 은 **`min_nature_level` AND `require_footway`** 로 유도한다. 둘 다
설정이라(`config/trailwalk.yaml`) `require_footway: false` 한 줄로 v5 동작
(녹지만)으로 되돌려 **재판정 없이** A/B 할 수 있다. 런로그가 `nature_level`
과 `footway` 를 둘 다 남기는 이유다.

> ⚠️ **`require_footway: true` 가 실제로 무엇을 거르는지는 아직 모른다.**
> 도색과 보행자가 근거에 들어가 있어 서울 골목에서 1 이 흔할 수 있고,
> 그러면 AND 가 사실상 아무것도 안 거른다. 돌려 보고 판단할 것.

### 🟡 그래서 v4 가 연 질문 — 경계는 어디인가

지금 정본은 `trail_surfaces: [park_path, waterside]` 다. 뺀 것 둘:

- **`pedestrian_way`** — "걷기 좋은 길" 이지만 "산책하러 가는 곳" 은 아니라고
  봤다. 근거가 관찰이 아니라 판단이므로 **라벨로 확인해야 한다.**
- **`sidewalk`** — 라벨 코스가 보도로 지나가는 구간(경복궁둘레길 등)이 전부
  False 가 된다. 리포트에서 이건 오탐이 아니라 **정의 차이**로 읽어야 한다
  (→ `22-labels.md` §11.3).

이 둘은 §4 의 라벨 세트가 서야 정해진다. 그때까지 정본 값은 **가설**이다.

**남은 것:** 확인된 정답이 7건뿐이다. 이건 프롬프트를 고르기엔 충분해도
정확도를 주장하기엔 부족하다 — §4(코스 폴리라인)가 풀려야 제대로 된 평가가 된다.
v4 가 골목 오탐을 고쳤는지는 약수동 500장으로 확인할 수 있지만(진짜 산책로가
없는 세트라 `park_path`/`waterside` 가 0에 가까워야 한다), **정확도는 여전히
못 잰다** — 음성만 있는 세트로는 재현율이 안 나온다.

## 🟡 6. confidence 가 포화돼 있다

`eval` 스키마의 `confidence` 가 fixture 이미지에서 **전부 10** 이 나온다.

프롬프트에 정의를 넣기 전에는 더 나빴다 — `is_trail=true` 인데 `0`, `false` 인데
`1` 이었다. 스키마는 형식만 강제하고 의미를 주지 않는다는 걸 확인한 사례다
(`20-app-design.md` §4).

지금은 방향은 맞지만 변별력이 없다. 원인 후보:

- fixture 가 합성 이미지라 실제로 쉬운 문제다 (실제 로드뷰로 다시 볼 것)
- 모델이 교정되지 않았다 (LLM 의 일반적 성질)
- 0~10 정수 스케일이 너무 거칠다

**변별력이 없으면 ROC 를 못 그리고, 그러면 `eval` 스키마가 `walk` 보다 비쌀 이유가
없다.** 실제 로드뷰로 다시 잴 것.

### ❌ 대안이던 "여러 화각 다수결" 은 반증됐다 (2026-08-18)

한때 여기 대안으로 "같은 장면을 여러 화각에서 물어 다수결" 을 적어뒀다.
런로그로 시뮬레이션했더니 **정확히 반대로 작동한다.**

같은 `pano_id` 를 여러 방위로 찍은 쌍을 kakao 런 전체에서 모아 각도차별로
일치율을 봤다:

| 두 판정의 각도차 | 쌍 | 일치율 |
|---|---:|---:|
| ~60° (진행축에서 벗어남) | 53 | **26%** |
| ~120° (좌우 후보끼리) | 23 | 65% |
| **~180° (정반대 = 축 위)** | **19** | **100%** |

**정반대로 돌려 찍은 19쌍이 예외 없이 일치한다.** 진행축 위에서는 판정이
방위에 안 흔들린다 — 한 장이면 된다. 그래프 전용 런 60장에서도 pano 계열
(도보 `103959…` / 차량 `121237…`)과 58/60 이 맞는다.

흔들리는 것은 **축을 벗어난 각도뿐이고, 그건 모델이 틀린 게 아니다.**
±60° 뷰는 하천·벽·건물을 보고 있어서 "여기 길 아님" 이 맞는 답이다. 즉 그
판정은 *"이 지점이 산책로인가"* 가 아니라 *"저쪽으로 길이 뻗어 있는가"* 의
답이다 (실제 캡처로 확인 — `check_fov.py` 의 `sweep_+060.png` 는 온통 물이다).

그래서 다수결을 돌리면:

> 3방향 이상 찍힌 pano 12개에서 **12개 전부**, 진행 방향의 정답 `T` 가
> 다수결에서 `F` 로 뒤집힌다. 12개 모두 도보 촬영 계열(=실제 보행로)이다.

축 밖 뷰를 표에 섞으면 **진짜 산책로만 골라서 부순다.** 운영점이 필요하면
다른 방법을 찾아야 한다.

교훈은 화각 얘기가 아니라 **질문의 단위**다. 판정은 *지점*에 대한 것인데
캡처는 *방향*에 대한 것이라, 둘을 같은 표에 넣으면 안 된다.

## 🟡 7. 이웃 목록은 문서화된 계약이 아니다

`neighbors()` 는 SDK 가 pano 마다 스스로 받아오는
`rv.map.kakao.com/roadview-search/v2/node/{panoId}` 응답의 `spot[]` 을 읽는다
(→ `21-roadview-providers.md` §1.3).

**우리가 그 엔드포인트를 직접 부르지는 않는다.** 정상적으로 페이지를 렌더하는
과정에서 SDK 가 이미 보낸 요청의 응답을 가로챌 뿐이라, Kakao 로 나가는 요청 수가
늘지 않는다. 문서화되지 않은 API 를 따로 두드리는 것과는 성격이 다르다.

### ✅ 로드 실패의 주원인은 규명·해결됐다 (2026-08-18)

SDK 는 **띄운 적이 있는 pano** 의 노드 응답만 받아온다. explore 의 BFS 가
큐에서 꺼낸 pano 를 아직 안 띄운 채 이웃부터 물어서, 청계천 실주행에서
노드 22개 중 12개가 실패해 좌표 밀기로 샜다 (호출 34/50). `neighbors()` 가
없으면 직접 띄워 받아오게 고쳤다 — 재실주행에서 실패 0. 그리고 explore 는
그래프 provider(`uses_graph`)의 빈 이웃을 갈래 없음이 아니라 **로드 실패**
로 취급해 좌표 밀기로 새지 않는다 (`neighbors_missing` frontier).

### ⚠️ pano 계열은 그래프로 이어져 있지 않다 (같은 날 발견)

차량 촬영(차도, `121237…`)과 도보 촬영(보행로, `103959…`)은 **별도 그래프**다.
차도에서 시작한 그래프 전용 런은 depth 15 양방향을 다 돌아도 보행로에 못
내려갔다 — 이전 런이 보행로를 찾았던 것은 폴백이 민 좌표가 우연히 아래
계열로 스냅된 덕이었다. **시작점이 어느 계열에 스냅되느냐가 결과를 가른다**
— 웹 UI 의 시작점 처리(§8)가 풀어야 한다 (예: 반경 안 여러 계열 pano 를
시드로 얹기).

### 실측 — GS25 청계천패션2점 반경 500m 에 계열이 24개 있다 (2026-08-23)

"시작점이 어느 계열에 스냅되느냐가 결과를 가른다" 에 숫자를 붙였다.
노드 API 의 `spot[]` 이 곧 이웃 그래프라 **캡처 없이** BFS 로 셀 수 있다
(2,549개 조회에 573초, 브라우저 불필요. **조회 실패 0 · 노드 없음 0**).

| 반경 500m 안 pano **2,493개** | | |
|---|---:|---:|
| 차량 촬영 | 1,742 | **69.9%** |
| 도보 촬영 | 751 | 30.1% |
| └ 그 중 **하천 보행로**(`103959…`) | **118** | **4.7%** |

다시 세는 법 (`check_pano_census.py`, ~10분, 캡처·브라우저 없음):

```sh
python app/check_pano_census.py --lat 37.5701282 --lng 127.0155282 \
    --radius 500 --seed 1198162403 --seed 1039597110 --seed 1028513706
```

> ⚠️ **census 자체가 시드에 의존한다 — 이 절의 논지가 census 에도 적용된다.**
> 시드 2개(`1198162403` 차량 · `1039597110` 하천)로 돌리면 2,458개, 위처럼
> 3개(+`1028513706` 도심 보도)면 2,493개다. 하천 계열도 99 → 118 로 달라진다.
> **위 표는 3시드 값이다.** 시드를 더 얹으면 또 늘 수 있다 — 인용할 때는
> 어느 시드로 돌린 것인지 같이 적을 것.
>
> ⚠️ **쓰로틀 하나가 12개를 조용히 깎았다.** 같은 3시드로 2,481개가 나온
> 판이 있었는데, 그건 반경 밖 노드에서 `continue` 가 `time.sleep` 앞에 있어
> 경계 구간의 요청이 쓰로틀 없이 나가던 스크립트였고 그 실패를
> `except: continue` 로 삼켰다. 고친 뒤 실패 0으로 2,493개다.
> **이래서 실패 건수를 세고 리포트에 띄운다** — 안 세면 언더카운트가
> 그래프의 성질처럼 보인다.
>
> `-o` 로 JSON 을 남길 수 있지만 **커밋하지 않는다**: 지도 사업자에게서 받은
> pano 좌표·주소라 이미지와 같은 회색지대다 (→ §2).

계열이 **24개**로 갈려 있고 서로 이어져 있지 않다. 가장 큰 도보 계열은
하천이 아니라 `102851…`(275) `102873…`(182) `102874…`(174) 인데, 그 계열의
`1028513706` 을 찍어 보니 **다산로 대로 교차점 인도**였다. `st_type` 은
이면도로 1,698개가 압도적이고 도로명은 청계천로 236 · 마장로 163 · 다산로
104 · 골목(마장로9길 98 · 종로44길 91 · 퇴계로83길 90 …) 순이다.

**주소를 믿으면 안 된다.** "청계천로 341" 이라는 도로명 주소가 스냅되는
pano 는 `1198162403` 이고 `shot_tool=202`(차량) · `st_type=이면도로` ·
창신동 종로50라길이다. 청계천로 위도 아니다.

그래서 같은 좌표·같은 반경에서 두 가지가 나온다:

| 시드 | 나오는 것 |
|---|---|
| GS25 좌표를 그대로 (= explore 와 같은 스냅) | 창신동·신당동 골목. `cheonggye-gs25-collect.yaml` |
| 하천 보행로 pano 를 직접 박음 | 하천 보행로만 109장, `exhausted`. `cheonggye-collect.yaml` |

뒤쪽은 **explore 가 도달할 수 없는 경로**다. 산책로 양성 표본을 얻는
방법이지, explore 가 저기서 시작한다는 뜻이 아니다. 두 설정 파일의 머리말이
이 구분을 적고 있다 — 섞으면 "청계천에서 모았다" 가 두 개의 다른 뜻이 된다.

> 선형이라 109장에서 멈춘다. 하천 보행로는 노드당 갈래가 1.01개다
> (108 pano → 109장, depth 0~55). 격자형 골목이 훨씬 많이 나오는 것과 다르다.

**그래프가 실제로 안 이어져 있다는 것을 큰 표본에서 확인했다.** GS25 좌표로
돌린 수집이 계열 **17개 · pano 887개 · 1000장**을 밟았는데 하천 보행로
계열(`103959…`)은 **0개**였다. 두 세트의 pano 교집합도 0이다. 물리적으로는
30m 옆인데 닿지 않는다.

> ⚠️ 그 1000장짜리 런은 `collect.max_views` 로 끊긴 것이고, **그 손잡이는
> 그래서 없앴다** (2026-08-23). 1000장에서 끊기니 도달 거리가 398m 였고
> 반경 안 2,493개 pano 중 35.4% 만 밟았다 — "500m 를 모았다" 가 아니었다.
> collect 의 예산 축은 이제 explore 와 같은 둘뿐이다: 시간과 거리.
> 옛 세트는 `cheonggye-gs25-500m--maxviews1000/` 에 남겨 뒀다.

그래도 남는 위험:

- **형식이 바뀌면 깨진다.** 공개 계약이 아니므로 예고 없이 바뀔 수 있다.
  `_sniff_node` 는 파싱에 실패하면 **`ProviderError` 로 런을 멈춘다**
  (2026-08-19). 예전에는 조용히 포기했는데, 그러면 spot 하나만 깨져도 실재하는
  갈래가 그래프에서 증발한 채 탐색이 계속 돌았다 — 시끄럽게 죽는 쪽을 택했다.
- **약관.** §2 와 같은 회색지대다. 로컬 연구 범위를 넘기기 전에 같이 검토할 것.
- 외부 조사에 따르면 `past[]` 의 오래된 panoId 는 `/node/{id}` 로 조회되지 않을
  수 있다. 지금은 `past` 를 쓰지 않으므로 무관하다.

대안이 있다면 그쪽이 낫다. 지금까지 확인된 바로는 공개 API 에 대안이 없다 —
`Roadview`/`RoadviewClient`/`Viewpoint`/`RoadviewOverlay` 어디에도 없고,
네 이벤트는 전부 페이로드가 없다.

  클라이언트에서 병렬화해봐야 줄만 선다. 병렬화는 서빙 쪽 문제이고, 게이트웨이가

- **`equirect_to_view` 검증.** 구현은 했지만 원본 파노라마를 주는 provider 가

- ✅ **분기 탐색 — 됐다 (2026-08-18).** `trailwalk/explore.py` + `run_explore.py`.
  프론티어 큐 BFS. 예산은 시간과 시작점 반경 둘뿐이다 (`20-app-design.md` §3)
- **웹 UI (로컬 전용).** 위치를 넣으면 explore 가 돌고 주변 산책로가 지도에
  그려지는 것. 정한 것들 (2026-08-18):
  - **로컬에서만 돌린다.** §2(약관)는 그래서 당장은 블로커가 아니다 —
    배포·공개로 범위가 넓어지는 순간 §2 부터 다시 본다
  - 위치 입력은 주소 → 좌표 지오코딩 API 를 쓴다. ⚠️ 지오코딩은 **REST 키**인데
    `config.py` 는 JS/REST 키 혼동을 막으려고 이름을 갈라놨다 — 붙일 때 REST 키를
    별도 이름으로 추가해야 하고, 로드뷰 쪽에 새면 안 된다
  - 다중 클라이언트 잡 큐와 진행 스트리밍은 **서빙 쪽 관심사로 넘겼다** (스택 미정).
    app 은 탐색 1건을 돌리고 결과를 내는 것까지만 한다
  - **시작점 스냅이 미결이다** (§7 계열 비연결). 유저가 찍은 좌표가 차도 계열에
    스냅되면 보행로 계열에 영영 못 간다. 반경 안의 여러 계열 pano 를 시드로
    얹는 식의 처리가 필요하다
- ~~**`st_type` / `shot_tool` 활용.**~~ **측정했다 (2026-08-20)** —
  `21-roadview-providers.md` §1.3b. 강한 사전 정보가 맞다:
  `shot_tool ∈ {205,100}` → 산책로 예측이 **정확도 96%** (n=98).
  ⚠️ 다만 여기 적어뒀던 **"202(Insta Titan, 배낭형)는 차량이 못 가는 길" 은
  틀렸다.** 카카오 뷰어 번들(`panorama.js`)에 판정 함수가 평문으로 있고,
  거기서 `INSTA_TITAN(202)` 은 `isCar` 세 개 중 하나다 — **차량 탑재**다.
  배낭형에 가까운 것은 `205 = SEOUL`(촬영: 서울특별시, 대부분 서울둘레길)이다.

  남은 일은 이 필터를 캡처 파이프라인에 넣는 것이다
- **재방문 판정의 정밀화.** 지금은 `pano_id` 완전 일치만 본다. 같은 길을 반대

- **`past[]`.** 같은 자리의 과거 파노라마(2008~2026)가 딸려 온다. 같은 장소를

## 🟡 9. 공개 경계층이 없다 — 웹이 부를 함수가 없다

**미결.** 지금 앱을 밖에서 부르는 방법은 CLI 뿐이다.

`explore()` 의 시그니처는 `(provider, client, start, start_bearing, cfg, log)` 고,
provider 와 client 는 호출자가 직접 만들어 넘겨야 한다. 그 배선은 지금
`run_explore.py` 안에 있는데 그건 stdout 에 찍고 종료 코드를 돌려주는 CLI 라
웹 서버가 부를 수 있는 물건이 아니다. 웹을 붙이는 순간 아래를 어딘가에 또
쓰게 된다 — 그리고 그 "어딘가" 가 두 곳이 되는 순간 갈라진다.

- `VlmClient` 생성 (프롬프트 해시 어긋남 → `PromptDriftError`)
- `providers.make()` (앱키·도메인 → `ProviderError`)
- `explore()` 도중의 `ProviderError` · `VlmError` · `ServerDeadError` ·
  `ImageIgnoredError`
- **어느 경로로 끝나든 `prov.close()`** — Playwright 브라우저가 안 닫히면 샌다

### 경계가 해야 할 일 셋

1. **배선을 감춘다.** 사용자가 정하는 것은 "어디서, 몇 미터" 둘뿐이다.
   `trailwalk.yaml` 은 **튜닝 기본값**이지 사용자 인터페이스가 아니다.
2. **예외를 밖으로 내보내지 않는다.** 웹 UI 가 500 을 뱉는 것보다 "이 위치에는
   로드뷰가 없습니다" 가 낫다. 단 **조용히 삼키면 안 된다** — 이 레포의 사고는
   전부 에러 없이 일어났고, traceback 을 버리면 같은 함정을 하나 더 파는 것이다.
   런로그에 전문을 남기고 사유로도 구분한다.
3. **실패를 하나로 합치되 구분은 보존한다.** 내부에서는 `no_coverage`(지도
   사업자가 안 찍었다)와 `dead_end`(모델이 아니라고 판정했다)를 끝까지 구분해야
   한다 — 섞으면 지도에 없는 것을 모델 탓으로 돌리게 되고 평가가 망가진다.
   하지만 사용자에게는 답이 하나다. **합치는 자리가 루프 안이 아니라 경계다.**

결과는 **실패해도 모양이 같아야** 한다. 웹이 분기 없이 같은 필드를 읽으면 된다.

### 정할 것 — 실패 메시지를 무엇으로 나르나

`stop_reason` 은 닫힌 집합이라 그대로 쓰면 되지만, **진단 원문**이 문제다.
이 레포의 설정 예외는 여러 줄에 걸쳐 해결 방법을 적는다 (`config.kakao_appkey`
의 "REST 키만 있다 → JS 키를 추가할 것", `kakao.diagnose_sdk` 의 403/401 원인
규명). **첫 줄만 남기면 증상만 남고 해결책이 사라진다.**

지금 `warnings[]`(→ `trailwalk/warn.py`)가 구조화된 채널이므로 원문을
`warn.make()` 의 `detail` 에 통째로 실어 나르는 쪽이 맞아 보인다. 별도의 단일
`error` 문자열 필드를 새로 두면 같은 것을 나르는 통이 둘이 된다.

### ⚠️ `app/CLAUDE.md` 규칙 2와 충돌한다

사용자용 진입점을 새로 만들면 그 인자는 `--config` 하나가 아니라 좌표와 반경이
된다. 규칙 2는 **런 진입점**을 겨냥한 것이고 이건 성격이 다르지만, 예외를 두려면
규칙 쪽에 그 구분을 적어야 한다 — 안 그러면 다음 사람이 규칙을 어긴 코드로 읽는다.

### 함께 볼 것

`ExploreResult` 에 **스냅된 시작 좌표가 없다.** 예산이 즉시 끊겨 `nodes` 가
비어도 지도에 원점은 그려야 하므로 경계가 이 값을 필요로 한다.

§8 의 "웹 UI (로컬 전용)" 항목이 이 절의 소비자다.

## 🟡 10. 후보 개수 컷이 갈래를 조용히 지운다

**미결.** `candidates.max_candidates` 를 없앨지 정해야 한다.

`_candidates` 가 하는 일은 이제 둘뿐이다 — 정면에 가까운 순 정렬, 그리고 상위
N개 컷. **각도 필터(`max_turn_deg`)는 없앴다** (→ `explore.py` 의 주석: 시작
노드에서 사용자가 준 bearing 이 지도의 갈래를 지웠던 청계천 실측). 남은 것이
개수 컷이다.

### 없애자는 쪽

화살표는 지도가 "여기서 갈 수 있다" 고 알려준 곳이다. 그중 일부만 보면 실재하는
갈래가 결과에서 빠지고, **안 본 것과 없는 것이 구분되지 않는다.** 잘린 후보는
`frontier` 에도 안 남아 흔적이 없다.

이것은 `distance_budget` 처리와 어긋난다 — 거기서는 반경 밖 노드를 굳이
`frontier` 에 남기며 *"반경 밖은 안 본 것이지 없는 것이 아니다"* 라고 적어 뒀다.
같은 원칙이라면 개수 컷도 같은 대접을 받아야 한다.

비용도 폭증하지 않는다. 화살표 하나 = 이미지 한 장 = 호출 한 번인데, 실측
이웃 수는 직선 구간에서 **온 길을 빼고 1개**(`20-app-design.md`), 관찰된
`spot[]` 표본이 **2개**(`21-roadview-providers.md` §1.3c, 2026-08-20)다. 컷이 현재 기본값에서
발동하려면 화살표가 이례적으로 많아야 하고, **하필 그런 곳이 갈래가 많은
교차로다.**

### 남기자는 쪽

예산이 시간과 반경 둘뿐이라 노드당 호출 수에 하드캡이 없다. 이웃 목록이 이상하게
길게 오는 pano 를 만나면 그 노드 하나가 시간 예산을 통째로 먹는다.

### 절충안

컷은 남기되 잘린 후보를 `frontier` 에 `reason="candidate_cap"` 으로 남긴다.
폭주 방어를 유지하면서 "안 본 것" 이 기록된다. `frontier[].reason` 은 이미
"어느 갈래를 왜 안 갔나" 에 답하는 필드이므로 새 개념이 아니다.

**정하기 전에 재야 할 것:** 실주행에서 이웃 수 분포. 지금 근거는 표본 두 건이라
꼬리가 어떻게 생겼는지를 모른다 — 컷이 실제로 몇 번이나 발동했는지는 런로그로
셀 수 있다.
