## ✅ 1. Kakao 로드뷰가 서울 산책로를 실제로 찍었는가 — **해결됨 (2026-08-17)**

**찍었다.** 프로젝트의 전제가 성립한다.

`check_kakao.py` 로 서울 6개 좌표를 실측:

| 좌표 | pano | 스냅 거리 | 렌더 |
|---|---|---:|---|
| 시청 앞 대로 (대조군: 차도) | 잡힘 | 18m | 정상 |
| 청계천 산책로 | 잡힘 | 2m | 정상 |
| 서울숲 공원길 | 잡힘 | 5m | 정상 |
| 한강 반포 수변길 | 잡힘 | 8m | 정상 |
| 남산 둘레길 | **없음** | - | - |
| 홍릉 두물길 (신설동역 부근) | 잡힘 | 15m | 정상 |

**산책로 표본 4/5 에서 커버리지가 있다.** 남산 둘레길만 미촬영이다.

그리고 **도보 촬영이 실재한다.** 청계천에서 pano 계열이 둘로 갈린다 —
`1212370258` 은 청계천'로'(차도) 위에서 찍힌 것이고, `10395983xx` 계열은
하천 바닥의 **보행로에서 걸으며 찍은 것**이다. 배낭형 장비 도보 촬영이라는
2차 자료(`21-roadview-providers.md` §1.4)가 실측으로 뒷받침됐다.

### 판정도 맞았다

탐색 20스텝을 돌린 결과가 그대로 증거다 (`20-app-design.md` §6):

- 출발 지점 정동향 = 청계천로. 차량·상가·주차된 차. 모델 판정 **`false`** — 맞다
- 방향을 틀어 하천 보행로로 내려간 뒤 17스텝 연속 **`true`** — 맞다.
  캡처를 눈으로 확인했다: 포장된 보행로, 보행자 다섯, 우측에 하천

**남은 것은 정량 평가다.** 표본 몇 장을 눈으로 본 것과 정확도를 재는 것은 다르다
(→ §4 폴리라인, `22-labels.md` §4).

### 설정 (전부 통과)

| | 상태 |
|---|---|
| Playwright + chromium | ✅ headless/headed 둘 다 기동 |
| Kakao **JavaScript** 키 | ✅ `KAKAO_MAP_JS_API_KEY` 로 분리해 등록 |
| 플랫폼 Web 도메인 등록 | ✅ `http://127.0.0.1:8731` |
| 카카오맵 제품 활성화 | ✅ 콘솔 > 제품 설정 > 카카오맵 |

여기까지 오는 데 걸린 것들을 남겨둔다 — 같은 자리에서 또 막힐 만한 것들이다.

#### 카카오맵 제품 활성화는 별도 스위치다

```
HTTP 403  NotAuthorizedError
{"message": "App(...) disabled OPEN_MAP_AND_LOCAL service."}
```

키를 발급하고 도메인을 등록해도 **제품을 따로 켜야 한다.**
콘솔 > 내 애플리케이션 > 제품 설정 > 카카오맵 > 활성화 설정.

#### 도메인 등록 — 127.0.0.1 ≠ localhost

같은 요청을 Referer 만 바꿔 보내면 갈린다:

| Referer | 응답 |
|---|---|
| `http://127.0.0.1:8731` | 403 `disabled OPEN_MAP_AND_LOCAL service` |
| `http://localhost:8731` | 401 `domain mismatched! ... check out registered web domains` |

127.0.0.1 이 등록돼 있다는 증거다(등록이 안 됐다면 여기도 401 이 났을 것).
동시에 **Kakao 는 `127.0.0.1` 과 `localhost` 를 다른 도메인으로 취급한다.**
provider 가 `127.0.0.1` 로 고정하는 이유다.

#### ⚠️ 브라우저 안에서는 이 에러가 보이지 않는다 — 중요

인증에 실패하면 Kakao 는 JS 대신 **JSON 에러**를 돌려준다. 크롬은 그 응답을
`<script>` 로 받기를 거부하고 `net::ERR_BLOCKED_BY_ORB` 로 통째로 막는다.
**에러 내용이 사라진다.** 남는 것은 "SDK 가 안 뜬다" 는 침묵뿐이다.

이걸 모르면 원인 넷(키·도메인·서비스 활성화·커버리지)을 구분할 방법이 없다.
그래서 `providers/kakao.py` 의 `diagnose_sdk()` 가 **같은 URL 을 같은 Referer 로
파이썬에서 한 번 더 받아** 본문을 읽는다. 20초 침묵 대신 위의 403 메시지가 나온다.

### 확인 순서

서비스를 켠 뒤, 탐색을 돌리기 전에 진단부터:

```bash
python app/check_kakao.py            # 좌표 6곳 · VLM 없이 · 20초
python app/check_kakao.py --headed   # 검은 화면이 의심되면
```

차도 대조군을 포함한 6개 표본에서 pano 가 잡히는지, 실제로 그려지는지
(픽셀 분산으로 판정), 스냅 거리가 얼마인지를 표로 준다. **차도까지 실패하면
커버리지 문제가 아니다** — 이 구분이 진단의 핵심이다.

그 다음:

```bash
python app/run_walk.py --provider kakao \
    --start 37.5768,127.0246 --bearing 90 --steps 5 --headed
```

`--headed` 로 시작할 것. 완전 headless 에서 WebGL 이 안 그려져 **검은 화면**이
찍히는 경우가 있고, 그러면 모델은 "산책로 아님" 을 정직하게 답해서 원인이
로드뷰가 아니라 렌더에 있다는 걸 놓치기 쉽다.

확인할 것 세 가지:

| 증상 | 뜻 |
|---|---|
| 브라우저 콘솔에 SDK 인증 오류 / 아무것도 안 뜸 | **키 종류나 도메인 등록 문제.** 커버리지가 아니다 |
| `stop_reason: no_coverage` 가 즉시 | 그 좌표에 로드뷰가 없다. 커버리지 문제 |
| 화면이 검다 | 렌더 문제(WebGL). 로드뷰 탓이 아니다 |
| 모두 `is_trail=false` 인데 그림은 멀쩡 | 프롬프트/판정 문제 |

**네 가지가 겉으로는 다 "안 된다" 로 보인다.** `--headed` 로 브라우저를 띄워
직접 보는 것이 이들을 가르는 가장 빠른 방법이다.

**표본은 테마별로 고를 것.** "한강·하천이 좋은 길"(하천변, 차도와 가까움)과
"숲이 좋은 길"(산속, 차량 진입 불가)은 커버리지가 정반대일 가능성이 크다.
`labels/trails.json` 에 테마가 붙어 있다.

## 🔴 2. 이미지 저장이 약관상 가능한가

Kakao 운영정책 제5조는 받은 데이터의 캐싱을 원칙적으로 금지하고 "인앱 UX 개선이며

`.gitignore` 에 `app/runs/images/` 를 미리 넣어뒀다.

**로컬 연구 범위를 넘기기 전에** (배포·공개·대량 수집) Kakao 에 명시적으로 문의할 것.

Naver 는 해당 약관 조항 자체를 아직 확인하지 못했다.

## ✅ 3. Kakao `zoom 0` 의 실제 화각 — **가로 90.9°** (2026-08-18 실측)

Kakao 의 `zoom` 은 −3~3 의 **이산 배율**이라 "90도" 를 지정할 방법이 없다
(Naver 는 `fov` 를 20~100 도로 직접 준다). 그래서 `zoom 0` 을 그대로 쓰는데,
그게 몇 도인지 문서에 없었다. **쟀다.** → `check_fov.py`

### 방법 — 회전량 대비 픽셀 이동

정사영에서 중심 기준 각 θ 인 점은 `x = cx + f·tan(θ)` 에 찍힌다. 카메라를
오른쪽으로 Δ 돌리면 중앙에 있던 것이 `cx − f·tan(Δ)` 로 간다. 그 이동을
템플릿 매칭(NCC)으로 재서 `f` 를 얻고, `fov = 2·atan(W / 2f)`.

Δ 를 하나만 쓰지 않는 이유는 **모델 자체를 검산하기 위해서**다. 정사영이면
Δ 가 달라도 `f` 가 일정해야 한다.

| Δ회전 | 이동 px | NCC | f(px) | 화각 |
|---:|---:|---:|---:|---:|
| 4° | 44 | 0.99 | 629.2 | 91.0° |
| 8° | 88 | 0.94 | 626.2 | 91.3° |
| 12° | 134 | 0.88 | 630.4 | 90.9° |
| 16° | 185 | 0.79 | 645.2 | 89.5° |
| 20° | 227 | 0.70 | 623.7 | 91.5° |
| 25° | 294 | 0.62 | 630.5 | 90.9° |
| 30° | 371 | 0.58 | 642.6 | 89.8° |

**가로 90.9° (편차 1.9°)**, 세로 59.5° (뷰포트 1280×720). `f` 가 Δ 전 구간에서
630±10 으로 붙어 있으므로 정사영 가정이 맞다 — 숫자를 믿어도 된다.

### ⚠️ 화각을 정하는 것은 `zoom` 이 아니라 **뷰포트 종횡비**다

뷰포트를 바꿔가며 다시 쟀다. `zoom 0` 은 고정인 채로:

| 뷰포트 | 종횡비 | 가로 화각 | 세로 화각 |
|---|---:|---:|---:|
| 1280×720 | 1.78 | 91.1° | 59.7° |
| 720×720 | 1.00 | 59.2° | 59.2° |
| 640×720 | 0.89 | 54.1° | 59.8° |
| 1280×360 | 3.56 | 126.3° | 58.1° |

**세로 화각이 ~59.5° 로 고정이고 가로는 종횡비에서 파생된다.**
`가로 = 2·atan((W/H)·tan(세로/2))` 가 네 줄 전부에 맞는다.

즉 `zoom` 은 세로 화각의 이산 단계이고, 우리가 실제로 쥐고 있는 연속 손잡이는
`VIEW_W`/`VIEW_H` 다. 그런데 그 값은 화각을 보고 정한 것이 아니라 **이미지
토큰 수를 264 로 고정하려고** `imaging.TARGET_SIZE` 에 맞춘 것이다
(`kakao.py:42`). **지금의 가로 화각 90.9° 는 토큰 예산 결정의 부산물이다.**

이게 (a)/(b) 선택을 바꾼다:

- **(b) 가 실현 가능해졌다.** zoom 표를 안 재도 종횡비로 원하는 가로 화각을
  연속적으로 맞출 수 있다. 대신 16:9 를 벗어나면 토큰 상수가 흔들린다 —
  화각과 토큰 예산을 맞바꾸는 셈이다
- **(a) 가 더 정직해졌다.** provider 가 신고할 값이 매직 상수가 아니라
  **계산식**이 된다: 세로 59.5°(zoom 0 실측) + 자기 뷰포트 → 가로 화각

측정 시 화살표는 **끈다**(`hide_arrows`). 화살표는 세상에 안 붙어 있다 (→ 아래).

### ✅ 결론 — `fov_deg` 를 계약에서 뺐다 (2026-08-19)

`WalkConfig.fov_deg` / `ExploreConfig.fov_deg` 의 90.0 이 실측 90.9° 와 사실상
같았다. **판정 결과를 다시 볼 필요는 없다.** 다만 그 일치가 근거 있는 것이 아니라
우연이었고, 값은 `capture()` 로 넘어가 버려지고 있었다.

**(a) 를 골랐다: 인자를 지웠다.** `capture(pano, heading)` 이다.

호출자가 화각을 지시하는 모양이었는데 **지시할 수 있는 provider 가 하나도
없었다.** Kakao 는 각도를 받을 수단 자체가 없고(zoom 은 −3~3 이산 배율),
fixture 는 원본 사진의 화각을 그대로 돌려준다. 지시할 수 없는 것을 지시하는
계약이라 지웠다. 화각은 이제 **provider 가 정하고, 문서가 그 값을 기록한다** —
`kakao.py` 의 `VIEW_W`/`VIEW_H` 주석과 이 절이다.

(b)(도 → 가장 가까운 zoom 단계로 매핑)는 안 골랐다. zoom −3~3 일곱 단계를
전부 재야 하고, 종횡비 쪽이 더 정밀한 손잡이인데다(위 표) 그건 토큰 상수와
맞물린다. **필요해지면 그때 재면 된다.**

> `imaging.equirect_to_view` 는 `fov_deg` 를 그대로 갖고 있다. 거기서는 진짜로
> 쓰인다 — 등장방형 360° 이미지를 한 화각으로 자를 때의 실제 계산이다. 원본
> 파노라마를 주는 provider 가 생기면(Naver) 그때 살아난다 (§8).

### provider 마다 화각이 다르다 — fixture 와 kakao 를 섞지 말 것

| provider | 화각 |
|---|---|
| **kakao** | 90.9° 고정 (zoom 0 + 1280×720). pano·방위·depth 와 무관하다 |
| **fixture** | **불명. 이미지마다 다르다** — 원본 사진이 갖고 있던 값이다 |

fixture 판정과 kakao 판정을 화각 축에서 비교하면 안 된다. §6 의 confidence
포화 원인 후보 중 "fixture 가 합성 이미지라 실제로 쉬운 문제다" 가 여기와
맞닿아 있다.

### ✅ `side_offsets` 문제는 사라졌다 — 그 각도를 쓰는 코드가 없다

원래 걱정은 "±60° 가 화각과 안 맞아 사각지대/중복이 생긴다" 였다. 확인해 보니
`side_offsets` 는 **이웃 그래프가 없을 때만 타는 폴백 전용**이었고, 그
폴백 자체를 없앴다 (→ `20-app-design.md` §3). 후보각은 이제 전부 이웃의
실측 방위각이다. **우리가 각도를 지어내는 자리가 없다.**

기록으로 남기면, 폴백이 살아 있었대도 문제는 아니었다: 화각 90.9° 에 ±60° 면
화면끼리 약 31° 겹친다. 사각지대도, "절반씩 겹침" 도 아니다.

### 화살표는 랜드마크로 쓸 수 없다

같은 실측에서 나온 부수 결과다. 화면의 흰 화살표는 이웃 방위에 **정사영되지
않는다.** 정면(pan=이웃 방위)에서는 화면 중앙에 정확히 오지만, 카메라를 돌리면
프레임 안에 남으려고 끌려온다:

```
이웃 '동' = 실측 방위 91.37°.  pan 을 돌리며 화살표 라벨의 화면 x 좌표:

  pan      1.4°   31.4°   61.4°   91.4°  121.4°  151.4°  181.4°
  축 기준   +90°    +60°    +30°     0°     −30°    −60°    −90°
  실측 x    848     794     721     640     559     486     432
  정사영   (밖)    (밖)    1004     640     276    (밖)    (밖)     ← f=630 기준
```

축에서 +30° 인 pan 61.4° 는 정사영상 x=1004 여야 하는데 721 이다. ±60° 부터는
아예 화면 밖(1731 / −451)이어야 하는데 여전히 보인다. 실측 x 는 pan 에 대해
거의 선형(180° 에 416px, ~2.3px/도)이라 **투영이 아니라 UI 배치**다.
방위가 필요하면 노드 JSON 의 `spot[].pan`(소수점 방위각)을 쓸 것 — §7.

1. **공공데이터포털 「서울특별시_스마트서울맵」 OpenAPI 를 먼저 본다.**
   공식 창구로 같은 데이터가 나오면 스크래핑을 안 해도 된다
2. 안 되면 `map.seoul.go.kr` 개발자도구로 `/smgis2/qry/THEME` 의 실제 페이로드를
   확인한다. 엔드포인트는 존재한다 (GET 400 / POST 500 — 404 가 아니다)
3. 그래도 안 되면 OSM Overpass 로 대체하되, **대상이 달라진다는 점을 명시**한다

당장 탐색을 돌리는 데는 시작점 좌표만 있으면 되므로 (1~3)이 §1 을 막지는 않는다.

## ✅ 5. 프롬프트의 핵심 질문 — **결정됨: "카메라가 산책로 위에 있는가"**

`system_v1.txt` 는 "보행 가능한 연속된 노면이 보이는가" 를 묻는데, 이게
두 가지로 읽혔다:

| 해석 | 청계천로(차도) 위에서 |
|---|---|
| **프레임 안에 산책로가 보이는가** | `true` — 갓길에 빨간 자전거도로가 보인다 |
| **카메라가 산책로 위에 있는가** | `false` — 차선·주차 차량·오토바이 한복판이다 |

프롬프트는 둘 중 무엇인지 말한 적이 없었다. 모델이 틀린 게 아니라 안 정해져
있었다. **후자로 정했다** (2026-08-17). 탐색 루프는 "저기 길이 있다" 가 아니라
"여기로 한 칸 가도 되는가" 를 물어야 한다.

### v2 는 실패했고 v3 가 됐다

`system_v2.txt` 는 정의를 바꾸는 데는 성공했지만 **진짜 산책로를 거부했다.**
같은 이미지 24장으로 재판정한 결과:

| | 확인된 7건 중 정답 | 전체 true |
|---|---|---|
| v1 (보이는가) | 5 | 17/24 |
| v2 (위에 있는가, 1차) | **4** | 11/24 |
| v3 (위에 있는가, 수정) | **7** | 15/24 |

v2 가 거부한 4건은 전부 청계천 하천변 보행로였다. 원인은 내가 넣은 두 문구다:

- `"a streambed that is not a maintained route"` — 이 길은 **하천 바닥에 있다**
- `"a continuous walkable surface"` — 폭이 1인용이고 노면이 돌·흙이다

즉 v2 는 "차도인가" 가 아니라 **"충분히 산책로답게 생겼는가"** 를 묻고 있었다.
v3 는 폭·노면 조건을 판정에서 빼고 하나만 남겼다: *정의된 길이 카메라 아래로
이어지는가.* 보행자가 그 노면 위를 걷고 있으면 강한 증거라는 문장도 넣었다.

v1·v2 는 지우지 않는다. `--prompt system_v1` 로 아직 고를 수 있다.

> **부수 발견:** `walk` 스키마(is_trail 만)와 `eval` 스키마(+confidence)는
> 판정을 바꾸지 않는다. 4개 pano × 2프롬프트에서 8/8 일치. 평가에서 잰
> 정확도를 탐색 루프의 정확도로 읽어도 된다는 뜻이다.

**남은 것:** 확인된 정답이 7건뿐이다. 이건 프롬프트를 고르기엔 충분해도
정확도를 주장하기엔 부족하다 — §4(코스 폴리라인)가 풀려야 제대로 된 평가가 된다.

## 🟡 6. confidence 가 포화돼 있다

`eval` 스키마의 `confidence` 가 fixture 이미지에서 **전부 10** 이 나온다.

프롬프트에 정의를 넣기 전에는 더 나빴다 — `is_trail=true` 인데 `0`, `false` 인데
`1` 이었다. 스키마는 형식만 강제하고 의미를 주지 않는다는 걸 확인한 사례다
(`20-app-design.md` §4).

지금은 방향은 맞지만 변별력이 없다. 원인 후보:

- fixture 가 합성 이미지라 실제로 쉬운 문제다 (실제 로드뷰로 다시 볼 것)
- 모델이 교정되지 않았다 (LLM 의 일반적 성질)
- 0~10 정수 스케일이 너무 거칠다

**변별력이 없으면 ROC 를 못 그리고, 그러면 `eval` 스키마가 `walk` 보다 비쌀 이유가
없다.** 실제 로드뷰로 다시 잴 것.

### ❌ 대안이던 "여러 화각 다수결" 은 반증됐다 (2026-08-18)

한때 여기 대안으로 "같은 장면을 여러 화각에서 물어 다수결" 을 적어뒀다.
런로그로 시뮬레이션했더니 **정확히 반대로 작동한다.**

같은 `pano_id` 를 여러 방위로 찍은 쌍을 kakao 런 전체에서 모아 각도차별로
일치율을 봤다:

| 두 판정의 각도차 | 쌍 | 일치율 |
|---|---:|---:|
| ~60° (진행축에서 벗어남) | 53 | **26%** |
| ~120° (좌우 후보끼리) | 23 | 65% |
| **~180° (정반대 = 축 위)** | **19** | **100%** |

**정반대로 돌려 찍은 19쌍이 예외 없이 일치한다.** 진행축 위에서는 판정이
방위에 안 흔들린다 — 한 장이면 된다. 그래프 전용 런 60장에서도 pano 계열
(도보 `103959…` / 차량 `121237…`)과 58/60 이 맞는다.

흔들리는 것은 **축을 벗어난 각도뿐이고, 그건 모델이 틀린 게 아니다.**
±60° 뷰는 하천·벽·건물을 보고 있어서 "여기 길 아님" 이 맞는 답이다. 즉 그
판정은 *"이 지점이 산책로인가"* 가 아니라 *"저쪽으로 길이 뻗어 있는가"* 의
답이다 (실제 캡처로 확인 — `check_fov.py` 의 `sweep_+060.png` 는 온통 물이다).

그래서 다수결을 돌리면:

> 3방향 이상 찍힌 pano 12개에서 **12개 전부**, 진행 방향의 정답 `T` 가
> 다수결에서 `F` 로 뒤집힌다. 12개 모두 도보 촬영 계열(=실제 보행로)이다.

축 밖 뷰를 표에 섞으면 **진짜 산책로만 골라서 부순다.** 운영점이 필요하면
다른 방법을 찾아야 한다.

교훈은 화각 얘기가 아니라 **질문의 단위**다. 판정은 *지점*에 대한 것인데
캡처는 *방향*에 대한 것이라, 둘을 같은 표에 넣으면 안 된다.

## 🟡 7. 이웃 목록은 문서화된 계약이 아니다

`neighbors()` 는 SDK 가 pano 마다 스스로 받아오는
`rv.map.kakao.com/roadview-search/v2/node/{panoId}` 응답의 `spot[]` 을 읽는다
(→ `21-roadview-providers.md` §1.3).

**우리가 그 엔드포인트를 직접 부르지는 않는다.** 정상적으로 페이지를 렌더하는
과정에서 SDK 가 이미 보낸 요청의 응답을 가로챌 뿐이라, Kakao 로 나가는 요청 수가
늘지 않는다. 문서화되지 않은 API 를 따로 두드리는 것과는 성격이 다르다.

### ✅ 로드 실패의 주원인은 규명·해결됐다 (2026-08-18)

SDK 는 **띄운 적이 있는 pano** 의 노드 응답만 받아온다. explore 의 BFS 가
큐에서 꺼낸 pano 를 아직 안 띄운 채 이웃부터 물어서, 청계천 실주행에서
노드 22개 중 12개가 실패해 좌표 밀기로 샜다 (호출 34/50). `neighbors()` 가
없으면 직접 띄워 받아오게 고쳤다 — 재실주행에서 실패 0. 그리고 explore 는
그래프 provider(`uses_graph`)의 빈 이웃을 갈래 없음이 아니라 **로드 실패**
로 취급해 좌표 밀기로 새지 않는다 (`neighbors_missing` frontier).

### ⚠️ pano 계열은 그래프로 이어져 있지 않다 (같은 날 발견)

차량 촬영(차도, `121237…`)과 도보 촬영(보행로, `103959…`)은 **별도 그래프**다.
차도에서 시작한 그래프 전용 런은 depth 15 양방향을 다 돌아도 보행로에 못
내려갔다 — 이전 런이 보행로를 찾았던 것은 폴백이 민 좌표가 우연히 아래
계열로 스냅된 덕이었다. **시작점이 어느 계열에 스냅되느냐가 결과를 가른다**
— 웹 UI 의 시작점 처리(§8)가 풀어야 한다 (예: 반경 안 여러 계열 pano 를
시드로 얹기).

그래도 남는 위험:

- **형식이 바뀌면 깨진다.** 공개 계약이 아니므로 예고 없이 바뀔 수 있다.
  `_sniff_node` 는 파싱에 실패하면 조용히 포기하고, walk.py 는 좌표 밀기로
  되돌아간다. **탐색이 멈추지는 않지만 품질이 조용히 나빠진다** —
  런로그 요약의 "이웃 그래프 사용 / 좌표 밀기 폴백" 표시를 볼 것.
- **약관.** §2 와 같은 회색지대다. 로컬 연구 범위를 넘기기 전에 같이 검토할 것.
- 외부 조사에 따르면 `past[]` 의 오래된 panoId 는 `/node/{id}` 로 조회되지 않을
  수 있다. 지금은 `past` 를 쓰지 않으므로 무관하다.

대안이 있다면 그쪽이 낫다. 지금까지 확인된 바로는 공개 API 에 대안이 없다 —
`Roadview`/`RoadviewClient`/`Viewpoint`/`RoadviewOverlay` 어디에도 없고,
네 이벤트는 전부 페이로드가 없다.

## 🟢 8. 나중에

- **병렬 처리.** 지금은 순차 전용이다. 서버가 `-np 1` 이고 비전 인코딩이 직렬이라
  클라이언트에서 병렬화해봐야 줄만 선다. 병렬화는 서빙 쪽 문제이고, 게이트웨이가
  생긴 뒤에 다시 볼 것 (`../../docs/00-design.md` §7)
- **Naver provider.** Kakao 커버리지가 나쁘면 대안. `fov` 를 각도로 줄 수 있어
  §3 문제가 없다는 장점이 있다
- **`equirect_to_view` 검증.** 구현은 했지만 원본 파노라마를 주는 provider 가
  없어서 한 번도 안 돌려봤다. 렌더된 뷰포트만 쓰는 동안은 죽은 코드다
- ✅ **분기 탐색 — 됐다 (2026-08-18).** `trailwalk/explore.py` + `run_explore.py`.
  프론티어 큐 BFS, 예산은 호출 수(`max_vlm_calls`)가 실질 상한이다
  (`20-app-design.md` §3.5)
- **웹 UI (로컬 전용).** 위치를 넣으면 explore 가 돌고 주변 산책로가 지도에
  그려지는 것. 정한 것들 (2026-08-18):
  - **로컬에서만 돌린다.** §2(약관)는 그래서 당장은 블로커가 아니다 —
    배포·공개로 범위가 넓어지는 순간 §2 부터 다시 본다
  - 위치 입력은 주소 → 좌표 지오코딩 API 를 쓴다. ⚠️ 지오코딩은 **REST 키**인데
    `config.py` 는 JS/REST 키 혼동을 막으려고 이름을 갈라놨다 — 붙일 때 REST 키를
    별도 이름으로 추가해야 하고, 로드뷰 쪽에 새면 안 된다
  - 다중 클라이언트 잡 큐와 진행 스트리밍은 **서빙 쪽 관심사로 넘겼다** (스택 미정).
    app 은 탐색 1건을 돌리고 결과를 내는 것까지만 한다
  - **시작점 스냅이 미결이다** (§7 계열 비연결). 유저가 찍은 좌표가 차도 계열에
    스냅되면 보행로 계열에 영영 못 간다. 반경 안의 여러 계열 pano 를 시드로
    얹는 식의 처리가 필요하다
- **`st_type` / `shot_tool` 활용.** 노드 응답에 도로 종별과 촬영 장비가 들어 있다.
  `shot_tool=202`(Insta Titan, 배낭형)는 차량이 못 가는 길이라는 뜻이라
  산책로의 강한 사전 정보일 수 있다. VLM 판정과 얼마나 일치하는지 재볼 가치가 있다
- **재방문 판정의 정밀화.** 지금은 `pano_id` 완전 일치만 본다. 같은 길을 반대
  방향으로 되짚어 오는 경우는 잡지만, 평행한 옆길은 못 잡는다
- **`past[]`.** 같은 자리의 과거 파노라마(2008~2026)가 딸려 온다. 같은 장소를
  연도별로 판정하면 프롬프트 안정성을 재는 공짜 데이터가 된다
