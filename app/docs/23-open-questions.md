## ✅ 1. Kakao 로드뷰가 서울 산책로를 실제로 찍었는가 — **해결됨 (2026-08-17)**

**찍었다.** 프로젝트의 전제가 성립한다.

`check_kakao.py` 로 서울 6개 좌표를 실측:

| 좌표 | pano | 스냅 거리 | 렌더 |
|---|---|---:|---|
| 시청 앞 대로 (대조군: 차도) | 잡힘 | 18m | 정상 |
| 청계천 산책로 | 잡힘 | 2m | 정상 |
| 서울숲 공원길 | 잡힘 | 5m | 정상 |
| 한강 반포 수변길 | 잡힘 | 8m | 정상 |
| 남산 둘레길 | **없음** | - | - |
| 홍릉 두물길 (신설동역 부근) | 잡힘 | 15m | 정상 |

**산책로 표본 4/5 에서 커버리지가 있다.** 남산 둘레길만 미촬영이다.

그리고 **도보 촬영이 실재한다.** 청계천에서 pano 계열이 둘로 갈린다 —
`1212370258` 은 청계천'로'(차도) 위에서 찍힌 것이고, `10395983xx` 계열은
하천 바닥의 **보행로에서 걸으며 찍은 것**이다. 배낭형 장비 도보 촬영이라는
2차 자료(`21-roadview-providers.md` §1.4)가 실측으로 뒷받침됐다.

### 판정도 맞았다

탐색 20스텝을 돌린 결과가 그대로 증거다 (`20-app-design.md` §6):

- 출발 지점 정동향 = 청계천로. 차량·상가·주차된 차. 모델 판정 **`false`** — 맞다
- 방향을 틀어 하천 보행로로 내려간 뒤 17스텝 연속 **`true`** — 맞다.
  캡처를 눈으로 확인했다: 포장된 보행로, 보행자 다섯, 우측에 하천

**남은 것은 정량 평가다.** 표본 몇 장을 눈으로 본 것과 정확도를 재는 것은 다르다
(→ §4 폴리라인, `22-labels.md` §4).

### 설정 (전부 통과)

| | 상태 |
|---|---|
| Playwright + chromium | ✅ headless/headed 둘 다 기동 |
| Kakao **JavaScript** 키 | ✅ `KAKAO_MAP_JS_API_KEY` 로 분리해 등록 |
| 플랫폼 Web 도메인 등록 | ✅ `http://127.0.0.1:8731` |
| 카카오맵 제품 활성화 | ✅ 콘솔 > 제품 설정 > 카카오맵 |

여기까지 오는 데 걸린 것들을 남겨둔다 — 같은 자리에서 또 막힐 만한 것들이다.

#### 카카오맵 제품 활성화는 별도 스위치다

```
HTTP 403  NotAuthorizedError
{"message": "App(...) disabled OPEN_MAP_AND_LOCAL service."}
```

키를 발급하고 도메인을 등록해도 **제품을 따로 켜야 한다.**
콘솔 > 내 애플리케이션 > 제품 설정 > 카카오맵 > 활성화 설정.

#### 도메인 등록 — 127.0.0.1 ≠ localhost

같은 요청을 Referer 만 바꿔 보내면 갈린다:

| Referer | 응답 |
|---|---|
| `http://127.0.0.1:8731` | 403 `disabled OPEN_MAP_AND_LOCAL service` |
| `http://localhost:8731` | 401 `domain mismatched! ... check out registered web domains` |

127.0.0.1 이 등록돼 있다는 증거다(등록이 안 됐다면 여기도 401 이 났을 것).
동시에 **Kakao 는 `127.0.0.1` 과 `localhost` 를 다른 도메인으로 취급한다.**
provider 가 `127.0.0.1` 로 고정하는 이유다.

#### ⚠️ 브라우저 안에서는 이 에러가 보이지 않는다 — 중요

인증에 실패하면 Kakao 는 JS 대신 **JSON 에러**를 돌려준다. 크롬은 그 응답을
`<script>` 로 받기를 거부하고 `net::ERR_BLOCKED_BY_ORB` 로 통째로 막는다.
**에러 내용이 사라진다.** 남는 것은 "SDK 가 안 뜬다" 는 침묵뿐이다.

이걸 모르면 원인 넷(키·도메인·서비스 활성화·커버리지)을 구분할 방법이 없다.
그래서 `providers/kakao.py` 의 `diagnose_sdk()` 가 **같은 URL 을 같은 Referer 로
파이썬에서 한 번 더 받아** 본문을 읽는다. 20초 침묵 대신 위의 403 메시지가 나온다.

### 확인 순서

서비스를 켠 뒤, 탐색을 돌리기 전에 진단부터:

```bash
python app/check_kakao.py            # 좌표 6곳 · VLM 없이 · 20초
python app/check_kakao.py --headed   # 검은 화면이 의심되면
```

차도 대조군을 포함한 6개 표본에서 pano 가 잡히는지, 실제로 그려지는지
(픽셀 분산으로 판정), 스냅 거리가 얼마인지를 표로 준다. **차도까지 실패하면
커버리지 문제가 아니다** — 이 구분이 진단의 핵심이다.

그 다음:

```bash
python app/run_walk.py --provider kakao \
    --start 37.5768,127.0246 --bearing 90 --steps 5 --headed
```

`--headed` 로 시작할 것. 완전 headless 에서 WebGL 이 안 그려져 **검은 화면**이
찍히는 경우가 있고, 그러면 모델은 "산책로 아님" 을 정직하게 답해서 원인이
로드뷰가 아니라 렌더에 있다는 걸 놓치기 쉽다.

확인할 것 세 가지:

| 증상 | 뜻 |
|---|---|
| 브라우저 콘솔에 SDK 인증 오류 / 아무것도 안 뜸 | **키 종류나 도메인 등록 문제.** 커버리지가 아니다 |
| `stop_reason: no_coverage` 가 즉시 | 그 좌표에 로드뷰가 없다. 커버리지 문제 |
| 화면이 검다 | 렌더 문제(WebGL). 로드뷰 탓이 아니다 |
| 모두 `is_trail=false` 인데 그림은 멀쩡 | 프롬프트/판정 문제 |

**네 가지가 겉으로는 다 "안 된다" 로 보인다.** `--headed` 로 브라우저를 띄워
직접 보는 것이 이들을 가르는 가장 빠른 방법이다.

**표본은 테마별로 고를 것.** "한강·하천이 좋은 길"(하천변, 차도와 가까움)과
"숲이 좋은 길"(산속, 차량 진입 불가)은 커버리지가 정반대일 가능성이 크다.
`labels/trails.json` 에 테마가 붙어 있다.

## 🔴 2. 이미지 저장이 약관상 가능한가

Kakao 운영정책 제5조는 받은 데이터의 캐싱을 원칙적으로 금지하고 "인앱 UX 개선이며
최신 상태 유지" 만 예외로 둔다. 연구·ML 목적의 명시적 예외는 확인되지 않았다.

**현재 대응:** 이미지를 디스크에 남기지 않는다. 런로그에는 `pano_id` 와 좌표만
남긴다 — 필요하면 다시 받아올 수 있으니 재현성은 유지된다.
`.gitignore` 에 `app/runs/images/` 를 미리 넣어뒀다.

**로컬 연구 범위를 넘기기 전에** (배포·공개·대량 수집) Kakao 에 명시적으로 문의할 것.
포럼에 공익 조사 목적으로 문의한 선례가 있다.

Naver 는 해당 약관 조항 자체를 아직 확인하지 못했다.

## 🟡 3. Kakao `zoom 0` 의 실제 화각이 몇 도인가

Kakao 의 `zoom` 은 −3~3 의 **이산 배율**이라 "90도" 를 지정할 방법이 없다
(Naver 는 `fov` 를 20~100 도로 직접 준다). 지금은 `zoom 0` 을 그대로 쓴다.

왜 알아야 하나: 좌우 탐색 각도 `side_offsets`(현재 ±60°)가 화각과 맞물린다.
화각이 60도인데 ±60도로 재면 두 화면 사이에 사각지대가 생기고, 화각이 120도면
좌우 화면이 절반씩 겹쳐 같은 길을 두 번 묻는 셈이 된다.

측정: 렌더 이미지에서 알려진 방위의 지형지물 두 개가 몇 픽셀 떨어져 있는지로 역산.
아니면 `pan` 을 5도씩 돌려가며 같은 물체가 화면 밖으로 나가는 각도를 본다.

정량 평가의 전제다. 세 후보의 장단은 `22-labels.md` §3.

권장 순서:

1. **공공데이터포털 「서울특별시_스마트서울맵」 OpenAPI 를 먼저 본다.**
   공식 창구로 같은 데이터가 나오면 스크래핑을 안 해도 된다
2. 안 되면 `map.seoul.go.kr` 개발자도구로 `/smgis2/qry/THEME` 의 실제 페이로드를
   확인한다. 엔드포인트는 존재한다 (GET 400 / POST 500 — 404 가 아니다)
3. 그래도 안 되면 OSM Overpass 로 대체하되, **대상이 달라진다는 점을 명시**한다

당장 탐색을 돌리는 데는 시작점 좌표만 있으면 되므로 (1~3)이 §1 을 막지는 않는다.

## 🟡 5. confidence 가 포화돼 있다

`eval` 스키마의 `confidence` 가 fixture 이미지에서 **전부 10** 이 나온다.

프롬프트에 정의를 넣기 전에는 더 나빴다 — `is_trail=true` 인데 `0`, `false` 인데
`1` 이었다. 스키마는 형식만 강제하고 의미를 주지 않는다는 걸 확인한 사례다
(`20-app-design.md` §4).

지금은 방향은 맞지만 변별력이 없다. 원인 후보:

- fixture 가 합성 이미지라 실제로 쉬운 문제다 (실제 로드뷰로 다시 볼 것)
- 모델이 교정되지 않았다 (LLM 의 일반적 성질)
- 0~10 정수 스케일이 너무 거칠다

**변별력이 없으면 ROC 를 못 그리고, 그러면 `eval` 스키마가 `walk` 보다 비쌀 이유가
없다.** 실제 로드뷰로 재보고, 그래도 포화면 confidence 를 버리고 다른 방법으로
운영점을 정한다 (예: 같은 장면을 여러 화각에서 물어 다수결).

## 🟢 6. 나중에

- **병렬 처리.** 지금은 순차 전용이다. 서버가 `-np 1` 이고 비전 인코딩이 직렬이라
  클라이언트에서 병렬화해봐야 줄만 선다. 병렬화는 서빙 쪽 문제이고, 게이트웨이가
  생긴 뒤에 다시 볼 것 (`../../docs/00-design.md` §7)
- **Naver provider.** Kakao 커버리지가 나쁘면 대안. `fov` 를 각도로 줄 수 있어
  §3 문제가 없다는 장점이 있다
- **`equirect_to_view` 검증.** 구현은 했지만 원본 파노라마를 주는 provider 가
  없어서 한 번도 안 돌려봤다. 렌더된 뷰포트만 쓰는 동안은 죽은 코드다
- **분기 탐색.** 지금은 갈림길을 기록만 하고 직진한다. 실제로 갈래를 다 훑으려면
  프론티어 큐가 필요한데, 호출 예산이 급격히 는다. 필요해지면 그때
- **재방문 판정의 정밀화.** 지금은 `pano_id` 완전 일치만 본다. 같은 길을 반대
  방향으로 되짚어 오는 경우는 잡지만, 평행한 옆길은 못 잡는다
