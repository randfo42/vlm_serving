## 1. Kakao 로드뷰

### 1.1 REST 가 없다

Kakao 의 REST API 목록에 로드뷰가 없다. 로컬 검색, 좌표 변환, 주소 검색은 REST 인데
로드뷰만 없다. 로드뷰는 `kakao.maps.Roadview` 가 **브라우저에서 WebGL 로 그리는 것**
으로만 존재한다. Google 의 Street View Static API 같은 정적 이미지 URL 패턴은
문서·포럼 어디에서도 확인되지 않았다.

### 1.2 쓸 수 있는 JS 표면

| 호출 | 주는 것 |
|---|---|
| `RoadviewClient.getNearestPanoId(pos, radius, cb)` | **panoId 숫자 하나뿐.** 좌표도, 방위도, 이웃도 없음 |
| `Roadview.setPanoId(panoId, position)` | 화면을 그 pano 로 |
| `Roadview.getPosition()` | 현재 pano 의 실제 좌표 |
| `Roadview.setViewpoint({pan, tilt, zoom})` | `pan` 0~360(0=북), `tilt` −90~90, `zoom` −3~3 |
| `event: 'init'` | ⚠️ **로드뷰 최초 초기화 때 딱 한 번.** pano 를 바꿀 때마다 오지 **않는다** |

세 가지가 설계를 결정한다.

**(a) `getNearestPanoId` 는 좌표를 돌려주지 않는다.** 스냅된 실제 위치를 알려면
로드뷰에 올려놓고 `getPosition()` 을 읽어야 한다. 요청 좌표를 그대로 다음 스텝의
기준으로 쓰면 스냅 오차가 누적되어 경로가 실제 길에서 밀려난다.
→ `kakao.py` 의 `nearest()` 가 pano 를 올려놓고 좌표를 읽는 이유.

**(b) `init` 은 최초 1회뿐이다.** 두 번째 pano 부터 `init` 을 기다리면 영영 오지
않는다. 실제로 이 함정에 빠져 **첫 좌표만 성공하고 나머지는 전부 타임아웃**했다.
pano 전환 이벤트 이름은 SDK 버전에 따라 갈리므로, `kakao.py` 는 이벤트를 기다리지
않고 `getPanoId()` 가 목표값이 되는지 **폴링한다.** 이름 추측보다 튼튼하다.

**(c) `zoom` 은 각도가 아니라 −3~3 의 이산 배율이다.** "화각 90도" 를 지정할 방법이
없다. `zoom 0` 의 기본 화각을 그대로 쓴다. 실측 결과 **가로 90.9° / 세로 59.5°**
(→ `23-open-questions.md` §3).

### 1.3 이웃 pano 목록 — 공개 API 에는 없지만, 데이터는 SDK 안에 흐른다

**공개 API 에는 정말로 없다.** `Roadview` / `RoadviewClient` / `Viewpoint` /
`RoadviewOverlay` 의 모든 메서드·속성·이벤트를 훑어도 인접 파노라마를 주는 것이
하나도 없다. 네 이벤트(`init`, `panoid_changed`, `viewpoint_changed`,
`position_changed`)는 전부 **페이로드가 없다** — 바뀌었다는 사실만 알려준다.
`RoadviewOverlay` 는 지도 위에 로드뷰 커버리지 선을 **그리기만** 하고 질의 수단이
없다.

**그런데 화면에는 흰 화살표가 그려진다.** 그리는 이상 데이터는 어딘가에 있다.

pano 를 띄울 때 SDK 가 스스로 이 요청을 보낸다:

```
GET https://rv.map.kakao.com/roadview-search/v2/node/{panoId}
```

응답의 `street_view.street.spot[]` 이 그 화살표다:

```json
"spot": [
  {"id": 1039598314, "pan": "91.36",  "wgsx": 127.006538, "wgsy": 37.569707, "st_name": "청계천로"},
  {"id": 1039598318, "pan": "271.37", "wgsx": 127.006361, "wgsy": 37.569711, "st_name": "청계천로"}
]
```

이웃 panoId · **정확한 방위각**(화면 라벨의 8방위 버킷이 아니라 소수 — 아래) · WGS84 좌표 ·
도로명. Google 의 `StreetViewPanoramaData.links[]` 에 해당하는 것이 여기 있다.
`past[]` 에는 같은 자리의 과거 파노라마(2008/2009/2010/2015/2026…)도 들어 있다.

같은 응답의 다른 필드도 쓸모가 있다:

| 필드 | 값 예 | 쓸모 |
|---|---|---|
| `st_type` | `주요도로2` | 도로 종별. 산책로 판정의 사전 정보가 될 수 있다 |
| `shot_tool` | `100` / `202` | 촬영 장비. **차량은 `{102, 200, 202}` 세 개뿐이고 나머지가 도보다** → §1.3b |
| `shot_date` | `2015-04-02` | 오래된 파노라마는 판정이 틀려도 모델 탓이 아닐 수 있다 |

#### DOM/CSS 의 화살표는 **정확한 방위로 그려진다** (2026-08-19 정정)

> ⚠️ 이 절은 2026-08-18 에 "CSS 에는 8방위 버킷뿐" 이라고 적었다가 **틀린 것으로
> 판명돼 고쳤다.** 슬롯 id 는 버킷이 맞지만 그 안의 3D 변환은 정확한 각도다.

SDK 는 8방위 슬롯을 **미리 만들어 둔다.** 이웃이 있는 방향만 켠다:

```
_ar_0_/_at_0_  북      _ar_8_/_at_8_   남
_ar_2_/_at_2_  북서    _ar_10_/_at_10_ 남동
_ar_4_/_at_4_  서      _ar_12_/_at_12_ 동      ← 인덱스 i → 방위 (360 − i·22.5)°
_ar_6_/_at_6_  남서    _ar_14_/_at_14_ 북동
```

- **슬롯 id 와 라벨은 22.5° 버킷이다.** `_ar_12_`/`_at_12_` 는 "동" 이고, 라벨
  글자도 "동" 이다. 여기까지만 보면 `91.36°` 를 복원할 수 없다.
- **하지만 `_ar_` 의 `matrix3d(...)` 는 정확한 각도를 담는다.** 지면에 눕힌
  3D 변환이고, 시선축 대비 요(yaw)가 그대로 들어 있다.

> ⚠️ **접두사 두 계열이 코드에서 엇갈린다 (2026-08-20, 미해결).**
> 화살표를 숨기는 CSS(`kakao.py` 의 `_ARROW_CSS`)는 `_al_`/`_atl_` 을 잡고,
> 화각 진단(`check_fov.py`)은 `_at_` 을 잡는다. `"_atl_0_".startsWith("_at_")`
> 는 **false** 이므로 둘이 같은 슬롯을 가리킬 수는 없다 — DOM 에 계열이 둘이거나,
> 한쪽 셀렉터가 아무것도 안 잡고 있다. 후자라면 `check_fov.py` 의 화살표 스윕이
> 에러 없이 "(없음)" 만 찍는다. **다음에 브라우저를 띄울 때 실물로 확인할 것.**

실측으로 갈랐다 (2026-08-19). 이웃의 정확 방위가 **84.99°** 인 pano 를 골랐다 —
22.5° 버킷(90.0°)에서 5.01° 떨어져 있다. 카메라를 84.99° 로 돌리면:

```
정확한 각도로 그린다면  →  화살표가 화면 중앙 (x ≈ 640)
22.5° 버킷으로 그린다면 →  x ≈ 695  (5.01° 만큼 옆)

실측: 동 x = 640.0        ← 정중앙. 버킷이 아니다
      matrix3d(6, …, 3.33e-15, …)   ← 요 성분이 0. 시선축과 일치
```

반대편(서) 화살표의 `matrix3d` 는 요 성분이 0.0348 → `atan` 하면 1.99°,
`m11` 의 부호가 음수라 뒤쪽. 즉 **부호까지 포함해 방위가 복원된다.**

그래도 우리는 `spot[].pan` 을 쓴다. 같은 숫자를 바로 쓸 수 있는 형태로 주기
때문이다 — matrix3d 는 분해해야 하고, **지금 렌더된 화살표에 대해서만** 읽을 수
있다(`display:none` 인 슬롯은 변환이 `none` 이다). CSS 는 대안이지 상위 호환이 아니다.

**주의: 화면상 위치는 방위의 정사영이 아니다.** 정면에서는 정확히 중앙에 오지만,
카메라를 돌리면 프레임 안에 남으려고 끌려온다 (`23-open-questions.md` §3).
각도는 `matrix3d` 에서 오고, 픽셀 위치에서 역산하면 틀린다. 화각 측정에서
화살표를 끄는(`hide_arrows`) 이유이기도 하다.

#### 우리는 이 엔드포인트를 직접 부르지 않는다

`neighbors()` 는 **SDK 가 보내는 요청의 응답을 가로챈다.** 우리가 이 엔드포인트를
직접 조립해 부르지 않는다는 뜻이다 — 문서화되지 않은 내부 API 를 따로 두드리는
것과는 성격이 다르다.

다만 "아무것도 안 한다" 는 아니다. 캐시에 없는 pano 의 이웃이 필요하면
`__show(panoId, 0)` 으로 그 pano 를 **띄운다**. SDK 는 띄운 적이 있는 pano 의
노드 응답만 받아오기 때문이다. 그래도 Kakao 로 나가는 요청은 SDK 가 평소 보내는
것과 같다 — 우리는 정상적으로 페이지를 렌더하고 있을 뿐이다.

그래도 **문서화된 계약은 아니다.** 응답 형식이 바뀌면 `_sniff_node` 가 표식을
남기고 `neighbors()` 가 **`ProviderError` 로 런을 멈춘다** (2026-08-19).
조용히 접으면 실재하는 갈래가 그래프에서 증발한 채 탐색이 계속 돌고, 상위는
"갈래가 3개였다" 고 믿는다. → `23-open-questions.md` §7

#### 폴백은 없앴다 (2026-08-18)

예전 방식(좌표를 heading 방향으로 밀고 `getNearestPanoId` 로 스냅)이 폴백으로
남아 있었는데 지웠다. 우리가 좌표를 지어내는 이동이라 없는 길을 만들어내고,
무엇보다 **이웃 로드 실패를 조용히 삼켰다** → `20-app-design.md` §3.

이제 `neighbors()` 는 **필수 구현**이고, 빈 목록은 로드 실패를 뜻한다.

### 1.3b 반경 검색과 `shot_tool` — 촬영 장비가 응답에 있다 (2026-08-20 실측)

§1.3 의 노드 엔드포인트 옆에 **반경 검색**이 하나 더 있다. 브라우저로 로드뷰를
열고 `rv.map.kakao.com` 호출을 전부 기록해 찾았다 (walkset 을 찾은 것과 같은 방법):

```
GET https://rv.map.kakao.com/roadview-search/v2/nodes
    ?PX=<x>&PY=<y>&RAD=<m>&PAGE_SIZE=<n>&INPUT=wtm&TYPE=w&SERVICE=glpano
Referer: https://map.kakao.com/
```

- **좌표계는 `INPUT` 으로 고른다.** `INPUT=wgs` 면 `PX=경도 PY=위도` 를 그대로
  넣을 수 있다 — 2026-08-20 실측으로 WTM 과 같은 결과(최근접 0.0m)를 확인했다.
  ~~`INPUT=wgs84` 는 `cnt: 0`~~ 은 값 이름을 틀린 것이었다(`wgs84` 아님, `wgs`).
  **`transcoord` 왕복이 필요 없다** — 호출이 2회에서 1회로 준다.
  `INPUT=wtm` 도 여전히 동작하고, 메인 SDK 는 `INPUT=wcong` 을 쓴다.
- `PAGE_SIZE` 는 **100 에서 잘린다** (200/500 을 줘도 100). `RAD` 는 크게 줘도
  가까운 순 100개까지다.
- **`TYPE` 은 필터가 아니다** — w/a/r/c/p 및 생략까지 전부 같은 결과였다.
- 반환되는 각 항목에 `id · shot_tool · st_type · st_name · shot_date · 좌표` 가
  들어 있다. 즉 **한 번의 호출로 주변 pano 를 장비별로 훑을 수 있다.**

#### `shot_tool` — 카카오 자신의 판정 규칙이 뷰어 번들에 있다

추측할 필요가 없다. 로드뷰 뷰어 번들
`https://t1.kakaocdn.net/mapjsapi/bundle/prod/panorama.js` (740KB) 안에
**코드표와 판정 함수가 평문으로 들어 있다.** 직접 받아 확인한 원문:

```js
w = {CAR:{code:"102"}, NAVER_CAR:{code:"200"}, INSTA_TITAN:{code:"202"},
     PANOZIP:{code:"100"}, ROTATOR:{code:"101"}, SKY:{code:"103"},
     INSTA360:{code:"201"}}
A = {isCar:  function(e){return w.CAR.code===e||w.NAVER_CAR.code===e||w.INSTA_TITAN.code===e},
     isWalk: function(e){return w.CAR.code!==e&&w.NAVER_CAR.code!==e&&w.INSTA_TITAN.code!==e}}
```

**카카오의 정의: 차량은 `{102, 200, 202}` 세 개뿐이고, 나머지 전부가 도보다.**
`isWalk` 가 화이트리스트가 아니라 **차량 3종의 여집합**이라는 점이 중요하다 —
새 코드가 생겨도 안전하다.

| 코드 | 상수명 | 뜻 | 분류 |
|---|---|---|---|
| 100 | `PANOZIP` | 카카오 자체 비차량 장비 (정체 불명) | 도보 |
| 101 | `ROTATOR` | 삼각대 회전형 추정 | 도보 |
| **102** | `CAR` | 차량 | **차량** |
| 103 | `SKY` | 미상 | 도보 |
| **200** | `NAVER_CAR` | 차량 | **차량** |
| 201 | `INSTA360` | Insta360 (비차량) | 도보 |
| **202** | `INSTA_TITAN` | Insta360 Titan — **차량 탑재** | **차량** |
| 203 | `SEA` | 촬영: 국립공원공단 | 도보 |
| 204 | `SDMG_OFFICE` | 촬영: 서대문구청 | 도보 |
| **205** | `SEOUL` | **촬영: 서울특별시** | 도보 |
| 206 | `GIMCHEON` | 촬영: 김천시청 | 도보 |
| 207 | `SACHEON` | 촬영: 사천시 | 도보 |

203~207 의 이름과 저작권 문구는 2025-08 이전 빌드에 있다
([Wayback](https://web.archive.org/web/20250801id_/https://t1.daumcdn.net/mapjsapi/bundle/prod/panorama.js)) —
현행 빌드는 이들을 런타임 동적 등록으로 옮겨서 상수 테이블에 안 보인다.

> ⚠️ **200번대는 "장비" 가 아니라 "제공 기관" 이다** (201/202 제외).
> `205` 가 우리 데이터에서 95% 보행로였던 것은 **서울특별시가 제공한 데이터가
> 대부분 서울둘레길이기 때문**이지, 코드가 도보를 뜻해서가 아니다. 서울시가
> 차량 촬영분을 넣으면 그 상관은 깨진다. **shot_tool 은 1차 필터로만 쓰고
> 최종 근거는 VLM 판정으로 남긴다.**

우리 실측(VLM 판정 대조, n=98)이 이 정의와 일치한다:

| `shot_tool` | pano | 산책로 판정 | 카카오 정의 |
|---|---:|---:|---|
| 202 | 66 | **0%** | 차량 ✅ |
| 102 | 2 | 0% | 차량 ✅ |
| 205 | 19 | **95%** | 도보(서울시) ✅ |
| 100 | 11 | 73% | 도보(PANOZIP) ✅ |

**구현은 카카오 규칙을 그대로 복사한다** — 화이트리스트를 만들면 새 코드가
생겼을 때 조용히 틀린다:

```python
CAR_TOOLS = {"102", "200", "202"}          # 카카오 isCar 와 동일
is_walk = shot_tool not in CAR_TOOLS       # 미지 코드는 도보로 (카카오와 같은 쪽)
```

~~보조 신호: `st_type is None` 이면 보행 전용 구간이다 (205 파노는 전부 null…)~~
**틀렸다 — §1.3c 참조.** 205 파노 61장 중 null 은 34장뿐이고, `st_type` 은 촬영
장비가 아니라 **촬영 주행 구간 단위로 붙는 라벨**이라 개별 pano 판정에 못 쓴다.

`area_type == "underpass"` 는 지하도다. 카카오의 `getNearestPanoId` 는 이걸
**후순위로 미는 게 아니라 아예 제외한다** (전부 underpass 일 때만 쓴다) —
번들 원문:

```js
e.nodeList.every(function(e){return e.isUnderpass})
  || (t = e.nodeList.filter(function(e){return !e.isUnderpass}));
var n = t[0];   // 나머지는 거리순 첫 번째
```

같은 줄에서 **`nearest()` 의 정체도 드러난다**: `getSimpleRangeData(x, y, r, 35, …)`
로 반경 안 35개를 받아 **거리순 첫 번째**를 고를 뿐이다. `shot_tool` 은 보지
않는다. 우리가 반경 검색으로 직접 고르면 같은 데이터에서 더 나은 선택을 할 수 있다.

#### 우리 데이터셋의 실제 구성 (914장 전수 조회, 2026-08-20)

| `shot_tool` | 장 수 | 비율 | |
|---|---:|---:|---|
| **202 (차량)** | **715** | **78%** | INSTA_TITAN |
| 100 | 99 | 11% | PANOZIP |
| 205 | 61 | 7% | 서울특별시 |
| 101 | 21 | 2% | ROTATOR |
| 102 (차량) | 18 | 2% | CAR |

**수집한 914장의 80% 가 차량 촬영**(202+102)이고, **52코스 중 30코스가 도보 0%** 다.
VLM 프로브에서 본 0% / 19% 코스들이 이것이고, 라벨 오염의 규모가 이 표로
정량화된다. 조회는 pano id 만으로 되므로 **재캡처 없이** 얻었다 (~3분).

#### 다른 엔드포인트 (번들의 `urls.json` 전체)

```
node/{id}                      단일 pano + spot[] + past[]
near-node/{id}?PX&PY&RAD=70&PAGE_SIZE=35&TYPE=w&INPUT=   인접
nodes?PX&PY&RAD&PAGE_SIZE&INPUT&TYPE=w                   반경 검색 (위)
map_roadview/depthmap_meerkat/{img_path}_W.png           깊이맵
```

`RAD` 는 **서버에서 100m 로 하드캡**된다 (1000/10000 을 줘도 결과 동일).
`SHOT_TOOL=` 파라미터를 추가해도 무시된다 — 서버 필터는 없다.

#### 쓸 곳

1. **캡처 전 필터.** `nearest()` 가 준 pano 의 `shot_tool` 이 202/102 면 건너뛴다.
   지금 라벨 오염의 주된 경로(라우터가 차도로 우회 → 차량 pano 캡처)가 막힌다.
2. **계열 비연결 문제**(§7·`23-open-questions.md` §8) — 시작점이 차도 계열에
   스냅되면 보행로 계열에 영영 못 간다. 반경 검색으로 주변 100개를 받아
   도보 계열 pano 를 시드로 얹으면 된다.
3. **이미 찍은 이미지의 사후 분류.** 재캡처 없이 pano id 만으로 조회된다.

### 1.3c 응답 필드 전수 — 무엇을 라벨로 쓸 수 있나 (2026-08-20)

로드뷰 엔드포인트가 주는 필드를 하나도 빼지 않고 적는다. **캡처 없이** pano id
또는 좌표만으로 얻는다. `node/{id}` 응답의 `street` 가 최대 집합이다.

`nodes` 반경 검색은 `spot`/`past` 가 `null` 이고 나머지는 동일하다.

한 번 더 쳐야 한다.

#### `st_type` 은 촬영 주행 구간 단위 라벨이다 — 개별 판정에 쓰면 틀린다

값은 15종 + `null` 이다: `고속국도` `도시고속도로` `도시고속화도로` `국도`
`국가지원지방도` `지방도` `주요도로1` `주요도로2` `주요도로3` `이면도로` `세도로`
`단지내도로(지상)` `단지내도로(지하)` `기타도로1` `기타도로2`.
문자열이 ITS 표준노드링크 도로등급(101~108)과 상당수 겹치고, 104(특별·광역시도)
· 107(시군도) 자리를 `주요도로1/2/3` · `이면도로` · `세도로` 로 세분한 것으로
보인다. **공식 정의 문서는 없다** (`apis.map.kakao.com` 전문 grep, developers
Local API, 구 Daum 문서 전부 확인).

결정적 반례 — **같은 장소 · 같은 날 · 같은 촬영 세션(9152972) · 같은 장비**인데
시각 블록이 다르면 값이 다르다:

```
퇴계로 충무로역 앞
  1212421574  2026-06-24 09:27  tool=202  st_type='주요도로1'
  1212426722  2026-06-24 10:39  tool=202  st_type='도시고속화도로'   ← 퇴계로는 고속화도로가 아니다
```

우리 **seoul** 데이터 914 pano 교차표 (열 = `shot_tool`). jongno 335장은 여기 없다 — `22-labels.md` §11 의 226장은 두 데이터셋 합계라 수가 다르다:

| st_type | 100 | 101 | 102 | 202 | 205 | 합계 | 도보% |
|---|---:|---:|---:|---:|---:|---:|---:|
| 이면도로 | 0 | 0 | 2 | 238 | 4 | 244 | 2% |
| 주요도로2 | 2 | 0 | 1 | 192 | 2 | 197 | 2% |
| **None** | 94 | 20 | 4 | 17 | 34 | 169 | **88%** |
| 주요도로1 | 0 | 1 | 1 | 109 | 4 | 115 | 4% |
| 단지내도로(지상) | 0 | 0 | 5 | 47 | 12 | 64 | 19% |
| 주요도로3 | 3 | 0 | 0 | 56 | 2 | 61 | 8% |
| 도시고속화도로 | 0 | 0 | 0 | 41 | 0 | 41 | 0% |
| 국도 | 0 | 0 | 0 | 14 | 1 | 15 | 7% |
| 기타도로1/2 | 0 | 0 | 5 | 0 | 0 | 5 | 0% |
| 고속국도 | 0 | 0 | 0 | 1 | 2 | 3 | 67% |
| **전체** | 99 | 21 | 18 | 715 | 61 | **914** | 20% |

청계천에서는 도보가 `주요도로2` · 차량이 `주요도로1` 로 갈렸지만 **우연이다** —
전체로 보면 `주요도로2` 는 도보 2% 다. 지역별 반경 검색 8곳 실측에서도 깨진다:

| 코스 | 도보 최근접 | 차량 최근접 |
|---|---|---|
| 은평 봉산 | `205` **국도** | `202` **주요도로2** ← 완전히 뒤집힘 |
| 노원 태릉 | `205` 단지내도로(지상) | `102` 단지내도로(지상) ← 동일 |
| 영등포 수변 | `101` None | `202` **도시고속화도로** / st_name=`안양천동자전거길` ← 자기모순 |
| 용산 남산 | `100` 주요도로3 `소파로` | `202` 이면도로 `소파로` |

`st_type = None` 만 신호가 있다 (도보 88%). `st_name` 도 None 이면 118건 중 97%.
**그래도 게이트로는 못 쓴다** — 재현율 82% / 정밀도 88% 로, 도보 33건을 버리고
차량 21건을 통과시킨다. `shot_tool` 이 모든 면에서 낫다.

##### 고속도로 계열을 걸러야 하지 않나 — 필요 없다

"고속도로·고속화도로에서는 산책로가 보일 리 없다" 는 맞다 (강변북로 표본은
실제로 **터널** 이었다). 하지만 `st_type` 으로는 그 도로를 못 찾는다 —
`도시고속화도로` 41장 중 실제 고속화도로는 강변북로 5 + 강남순환로 5 +
서부간선지하도로 1 = **11장** 뿐이고, 나머지는 퇴계로 · 연희로 · 용마산로 같은
시내 간선과 **자전거 지하통로**다.

그리고 걸 이유가 없다:

```
고속도로 계열 st_type (도시고속화도로+고속국도+국도) 59건
  shot_tool 분포 = {202: 56, 205: 3}
  → shot_tool 이 이미 거르는 것          56건 (95%)
  → st_type 게이트가 추가로 버리는 도보   3건  (205 = 서울시 도보 촬영분)
```

`shot_tool` 위에 얹어서 얻는 게 없고, 대신 **고속국도로 잘못 라벨된 도보
파노 3장을 버린다.** `st_type` 은 표시용 문자열로만 둔다.

#### `past[]` — 같은 지점의 과거 촬영본

차량 pano 50건을 조회했다 (2026-08-20):

```
past 가 있는 것            48/50   개수 중앙값 18 · 최대 26
past 에 도보 계열이 있는 것  5/50 (10%)
```

**시간축으로 도보 파노를 되찾는 건 10% 밖에 안 된다.** 공간축(반경 100m 안에
도보 pano) 30% 보다 나쁘다. 다만 `past` 는 다른 용도가 있다 — 같은 좌표·다른
계절/연도의 이미지를 공짜로 얻으므로, **VLM 이 계절과 화질에 얼마나 흔들리는지**
재는 데 쓸 수 있다. 좌표가 같으니 정답 라벨이 그대로 유지된다.

### 1.4 커버리지 — 가장 중요한 미확인 항목

Kakao 는 일반 도로를 차량으로 찍고, **공원·좁은 산책로·관광지는 배낭형 파노라마
장비로 도보나 세그웨이로 찍는다**는 서술이 국내 기술 글들에 있다. 사실이라면 서울
테마산책길에 실제 커버리지가 있다는 뜻이라 이 프로젝트의 성립 여부가 걸린 항목이다.

**공식 문서에서는 확인하지 못했지만, 실측으로 뒷받침됐다 (2026-08-17).**

청계천에서 pano 계열이 둘로 갈린다:

| pano | 촬영 위치 |
|---|---|
| `1212370258` | 청계천**로** 위 — 차량 촬영. 차도·상가가 보인다 |
| `10395983xx` 연속 | 하천 바닥 **보행로** — 걸으며 촬영. 보행자·수면이 보인다 |

후자는 차량이 들어갈 수 없는 곳이다. 도보 촬영이 실재한다.
서울 6개 표본 중 산책로 4/5 에서 커버리지가 확인됐다 (남산 둘레길만 미촬영).
→ `23-open-questions.md` §1

### 1.5 정책

- Kakao 운영정책 제5조는 **Kakao 로부터 받은 데이터의 캐싱을 원칙적으로 금지**하고,
  "인앱 UX 개선 목적이며 최신 상태를 유지하는 경우" 만 예외로 둔다. Kakao 담당자가

## 2. Naver 파노라마 (NCP Maps)

NCP Maps 제품 목록은 Web/Mobile Dynamic Map, **Static Map**, Directions, Geocoding,
Reverse Geocoding 이다. 파노라마는 **Web Dynamic Map JS SDK 의 하위 모듈**로만 있고
Static Map 에 대응하는 REST 파노라마가 없다.

`naver.maps.Panorama` 는 오히려 Kakao 보다 다루기 좋은 면이 있다:

- `pov = {pan(−180~180, 정북 기준), tilt(−90~90), **fov(20~100)**}` — **화각을 각도로
  지정할 수 있다.** Kakao 의 이산 zoom 과 대비된다.
- `getLocation()` 이 `{panoId, title, address, coord, **photodate**}` 를 준다.
  촬영일자가 나오는 건 판정 결과를 해석할 때 쓸모가 있다.
- `position` 을 주면 기본 300m 반경에서 자동 스냅.
- 이벤트: `init`, `pano_status`(OK/ERROR), `pano_changed`, `pov_changed`.

**이웃 pano 목록은 여기도 없다.** 그리고:

- 파노라마 단독 과금/무료 한도를 문서에서 찾지 못했다 (Web Dynamic Map 에 묶여 있음).
- 파노라마 이미지 캐싱에 관한 약관 조항을 확인하지 못했다.

→ 둘 다 미확인. Kakao 커버리지가 나쁘게 나오면 그때 Naver 를 같은 방식으로 조사한다.
`fov` 를 각도로 줄 수 있다는 점만으로도 대안 가치가 있다.

## 3. Google Street View — 유일하게 REST 가 있지만 못 쓴다

REST 는 깔끔하다:

```
https://maps.googleapis.com/maps/api/streetview
  ?location=lat,lng | pano=<id>
  &size=640x640          # 최대 640×640 — 우리 목표 1280×720 보다 작다
  &heading=0..360 &pitch=-90..90 &fov=1..120 &radius=50
  &source=default|outdoor &key=...
```

메타데이터 엔드포인트(`/streetview/metadata`)는 **무료·무제한**이고 pano 존재 여부를
알려준다. 이미지는 월 1만 장 무료, 이후 1000장당 $7.00 부터.
이웃 링크(`links[]` = `{heading, pano, ...}`)는 REST 가 아니라 JS
`StreetViewService.getPanorama()` 에만 있다.

**그런데 두 가지가 각각 단독으로 이 선택지를 죽인다:**

1. **커버리지.** Google 은 2012년 한국 서비스를 시작했으나 **2021년 9월 한국 실외
   스트리트뷰 이미지를 사실상 전량 내렸다.** 남은 것은 실내와 사용자 제출 이미지다.
   차도조차 성기고 오래됐으며, 공원·산책로는 애초에 의미 있게 찍힌 적이 없다.
2. **약관.** Maps Platform 약관상 **`pano_id` 외에는 캐싱·저장·색인이 금지**되고,
   콘텐츠를 **ML 모델의 학습·개발·개선에 사용하는 것이 명시적으로 금지**된다.
   커버리지가 있었더라도 이 파이프라인에는 쓸 수 없다.

`size` 상한 640×640 도 부수적 문제다 — 목표 해상도(긴 변 1024px 이상)에 못 미쳐
서버가 다운스케일하지 않고 토큰 수가 떨어진다(`../../docs/10-client-guide.md` §2.5).

## 4. 그래서 어떻게 만들었나

```
Kakao JS SDK 를 얹은 한 페이지짜리 로컬 HTTP 서버 (127.0.0.1)
   └ Playwright(chromium) 가 로드
       ├ __nearest(lat,lng,r) → getNearestPanoId → panoId
       ├ __show(panoId, pan)  → setPanoId + setViewpoint + 렌더 대기 → 실제 좌표
       └ #rv 엘리먼트 스크린샷 (1280×720 PNG)
                    ↓
            imaging.view_to_data_uri  ← JPEG 강제, 종횡비 고정
                    ↓
            vlm.assess  ← 1턴, is_trail 하나
                    ↓
            explore.py 가 이웃 그래프로 다음 노드를 큐에 넣는다
```

설계에 박힌 제약 네 가지. **전부 실측으로 부딪힌 것들이다:**

1. **로컬 HTTP 서버가 필요하다.** Kakao 앱키는 도메인 등록제라 `file://` 로는 SDK 가
   거절한다. `http://127.0.0.1:8731` 을 개발자 콘솔에 등록해야 한다.
   **`127.0.0.1` 과 `localhost` 는 다른 도메인으로 취급된다** — 실측으로 확인했다
   (127.0.0.1 은 통과, localhost 는 `domain mismatched!`). provider 가 IP 로
   고정하는 이유다.
2. **완전 headless 에서 WebGL 이 안 그려질 수 있다.** 검은 화면이 찍히면 이게 첫 번째
   의심 대상이다. `python app/check_kakao.py --headed` 로 확인한다 (런 스크립트는
   설정의 `run.headed`). 브라우저에 `--use-gl=angle --use-angle=swiftshader
   --enable-unsafe-swiftshader` 셋을 기본으로 걸어뒀다.
3. **렌더 완료를 기다려야 하고, 좌표는 그 뒤에 읽어야 한다.**
   `getPanoId()` 가 목표값이 될 때까지 폴링한 뒤 `requestAnimationFrame` 두 번 +
   400ms 를 준다. 이걸 빼면 이전 프레임이나 검은 화면을 찍는다.

   **그마저도 부족할 때가 있다.** 프레임 전이를 실측하니 pano 4개 중 3개는
   `__show` 반환 시점에 이미 안정인데, 하나는 프레임 3개를 거쳐 **+300ms 에**
   확정됐다 (타일이 저해상도→고해상도로 점진 로드된다). 그래서 `capture()` 는
   고정 대기가 아니라 **조건 둘**을 본다: 이미지 요청이 끊기기를 기다리고
   (`_await_tiles`), 그 뒤 프레임이 연속으로 같아질 때까지 찍는다
   (`kakao.render_settle_stable`). 프레임 비교만으로는 부족했다 — 타일이
   저해상도→고해상도로 덮어쓰는 중간에 잠깐 멎어서 두 프레임이 일치해버린다.
   그래서 **연속 2 로는 안 된다** (값의 근거는 yaml 주석에).

   여기에 더해 **세션의 첫 캡처는 찍고 버린다.** 브라우저·SwiftShader·HTTP
   캐시가 전부 찬 상태의 첫 렌더가 같은 pano 인데도 다른 바이트를 냈다
   (3.0s vs 1.15s, 2~6회차는 완전 동일). 안정 조건을 통과하고도 결과가 달랐으므로
   대기로는 못 잡는다. 이 폐기 비용(~1.2s)이 `sampling.provider_restart_every`
   의 유일한 대가이기도 하다.
   → `20-app-design.md` §5

   더 고약한 것은 **`getPanoId()` 가 먼저 바뀌고 `getPosition()` 이 뒤늦게 따라온다**는
   점이다. 전환 직후에 좌표를 읽으면 이전 pano 의 좌표나 `NaN` 이 나온다 — 반경 50m
   요청에 스냅 거리가 **수 km** 로 찍혔다. 이걸 놓치면 탐색이 매 스텝 엉뚱한 곳으로
   순간이동하면서도 로그상으로는 멀쩡해 보인다. `nearest()` 가 스냅 거리를 반경과
   대조해 검증하는 이유다.
4. **SDK 인증 실패는 브라우저 안에서 보이지 않는다.** 인증에 실패하면 Kakao 가 JS
   대신 JSON 에러를 돌려주는데, 크롬은 그 응답을 `<script>` 로 받기를 거부하고
   `net::ERR_BLOCKED_BY_ORB` 로 통째로 막는다 — **에러 내용이 사라지고** SDK 가
   그냥 안 뜬다.

   그래서 `diagnose_sdk()` 가 같은 URL 을 같은 Referer 로 **파이썬에서 한 번 더
   받아** 본문을 읽는다. 실측으로 나온 것들:

   | 응답 | 뜻 | 조치 |
   |---|---|---|
   | 403 `disabled OPEN_MAP_AND_LOCAL service` | 앱에서 카카오맵 제품이 꺼져 있음 | 제품 설정 > 카카오맵 활성화 |
   | 401 `domain mismatched! caller=...` | 그 origin 이 미등록 | 플랫폼 > Web 도메인 등록 |

   이 구분이 없으면 "로드뷰가 안 뜬다" 하나로 뭉뚱그려져 커버리지 문제로 오인한다.

2.18초/호출. 나머지가 브라우저 렌더다. "직진 먼저" 덕에 스텝당 호출이 1.15회였다. 병렬화는 여기서 풀 문제가 아니다 — 서버가 `-np 1`
